## 一、法源邊界與要修的流程故障

現行文件分別正確描述了：

- runtime 是玩家目前真正玩到的內容；
- 未施工的劇本與規格必須先審才可進 runtime；
- 作者與審查者必須分離；
- 審查意見必須給可直接施工的修法；
- 高風險變更要先裁決、再施工；
- 自動測試、瀏覽器、真人試玩、commit 與發佈是不同狀態。

但它們尚未共同回答：

1. 本輪是在查「現況」、審「目標」，還是驗「兩者是否相符」？
2. 提出完整修法是否會自動把審查者變成施工者？
3. 唯讀審查、小修、新機制、存檔與發佈是否該走同一套前置？
4. 既有測試有紅燈時，哪些工作能繼續，哪些必須停止？
5. 什麼情況可做定點覆核，什麼情況必須重開完整實作審？

本檔只補上這五個操作層缺口。

**既有法源仍保留其內容權限：**

- 法源效力與 runtime 現況：`02_設計/發現之前_第一至第四章收官與後續章節製作基線_v1.0.md` §二。
- 作者／審查者分離與審查格式：`01_治理/發現之前_雙模型協作流程_v0.1.1.md` §一至§四。
- 查證、洩答、dirty worktree 與版本紀律：`01_治理/發現之前_雙人共用工作守則_v0.1.md`。
- 發佈與狀態用語：`01_治理/發現之前_GitHub與Vercel發佈流程_v0.1.md`。

本檔操作化條文優先於上述文件中與它直接衝突的舊流程句；內容法源本身的效力不變。

## 二、三種真相模式

每個工作包只能有一個主要真相模式。需要換模式時，先結束前一模式並留下移交紀錄。

### 2.1 AS-IS｜現況

只回答：「玩家或工作樹現在實際存在什麼？」

- 主證據：目前 runtime、資料、引擎、UI、資產、存檔行為與可重現測試。
- 劇本、提案、舊報告只能說明意圖或歷史，不能冒充現況。
- 預設唯讀；若使用者只要求診斷，不得順手修。
- 輸出分開：已驗證、合理推論、尚未驗證。

### 2.2 TO-BE｜目標

只回答：「這一輪獲准要做成什麼？」

- 主審對象：任務書指定的劇本、規格、CR、設計稿或資產包。
- runtime 是成本與相容性比較基線，不會取代尚未施工的主審稿。
- 每項要求都要標出授權來源、適用範圍與非目標。
- 待裁內容必須標成候選，不得以現行規範語氣進入施工。

### 2.3 CONFORMANCE｜符合性

只回答：「實際成品是否忠實實現已核准目標？」

- 同時固定一份 TO-BE 目標與一份 AS-IS 成品。
- 逐項比對：目標條文、實際行為、差異、風險與驗證。
- 審查者預設唯讀，不能一邊修改、一邊替自己的修改放行。
- 若審查者接手修正，該工作轉成新的施工包，另派獨立覆核者。

**法源不是第四種真相模式。** 憲章、跨章規則與總監裁決負責限制三種模式如何判斷，不代替主審對象。

## 三、工作包卡與角色移交

R1–R4 工作開工前必須建立工作包卡；R0 至少填前八欄。

```text
工作包 ID：
目標：
交付物：
主要真相模式：AS-IS／TO-BE／CONFORMANCE
主審或施工對象：
比較基線：
範圍內：
範圍外：
風險級別：R0／R1／R2／R3／R4
裁決者：
作者：
施工者：
獨立審查者：
能力限制：
來源與授權紀錄：
允許修改路徑：
禁止觸碰路徑：
既有紅燈分類：
存檔影響：
預定驗證：
停止／退回條件：
```

### 3.1 角色原則

- 角色綁定工作包，不永久綁定 Claude、Sol 或 Codex。
- 當期任務書與總監明示指派，高於預設分工與 agent overlay。
- 本規範生效後，工作包卡的明示角色高於舊文件的通用接手預設；提出完整修法本身仍不構成角色改派。
- 作者與獨立審查者必須不同。
- 同一人可以起草機制與台詞，但不能同時批准兩者；機制先過 Design Gate，再展開台詞，成品再由另一人過 Implementation Gate。
- 角色可以移交，工具能力不能靠移交虛構。目前正式生圖的唯一可執行者是 Sol／Codex；Claude 可定義圖像需求、prompt、接線規格與獨立審圖，但不得被列為生圖執行者。
- 工作包含生圖時，`能力限制` 必須寫明 `image-generation: Sol/Codex only`；若 Sol 同時施工其他內容，仍由 Claude 或另一名未參與該圖施工者做獨立視覺審查。

### 3.2 修法不等於移交

審查者可提供替換句、局部 diff、偽碼、狀態反例與可驗證條件。這些是審查證據，**不自動移轉施工權**。

只有下列任一項成立才算移交：

1. 總監明示改派；
2. 原施工者明示交出完整工作包；
3. 當期任務書已指定角色互換。

移交紀錄至少包含：

- 精確修改路徑與禁止碰的路徑；
- 已完成、未完成與未驗證項目；
- 測試命令、結果及既有紅燈；
- dirty worktree 中保留的他人工作；
- 下一位接手者的唯一下一步。

## 四、R0–R4 風險分流

工作包以實際動作的最高風險定級，不得靠拆檔降級。唯讀查 R4 範圍仍是 R0。

| Lane | 適用工作 | 最低前置與退出條件 |
|---|---|---|
| **R0 查證** | 唯讀盤點、診斷、對抗審、報告 | 固定目標、模式與證據；不改檔；無關紅燈不妨礙閱讀 |
| **R1 低風險** | 索引、註解、非玩家可見文件、可逆 metadata、小型既有契約修復 | 簡式 Design Gate、定點檢查；不得改玩家契約 |
| **R2 局部施工** | 玩家可見文案、既有 UI、資料或美術接線；不動證據語意、共用引擎或存檔 | 完整 Design Gate、相關 builder／lint、全套測試；視覺變更加瀏覽器驗收 |
| **R3 高風險契約** | 新章、新機制、物理／史實結論、證據取得、玩家代理權、共用引擎、狀態語意 | CR／法源先行、契約與負向控制、完整雙 Gate、獨立 CONFORMANCE |
| **R4 高爆炸半徑** | schema／存檔、刪除／歸檔搬移、公開發佈、不可逆外部操作、大範圍生成物重建 | 總監明示授權、回復方案、fail-closed、獨立覆核與人工驗收 |

### 4.1 既有紅燈分類

基線紅燈必須標成：

1. **本輪目標**：本輪就是修它，可以繼續。
2. **重疊阻擋**：與本輪路徑、生成物或接口重疊，先處理或停止。
3. **已知不重疊**：完整揭露後，可繼續不接觸它的 scoped work。

「測試不全綠」不會自動禁止 R0，也不會自動授權忽略重疊紅燈。

### 4.2 基線強度

- R0：工作樹快照、目標法源與必要的定點查證；除非要驗 runtime 主張，不強制先跑全套測試。
- R1：定點測試；是否跑全套依實際 diff-scope。
- R2–R4：施工前記錄全套基線，施工後重跑全套。
- 發佈仍以發佈法源為準；半成品發佈與正式候選版不得混稱。

## 五、Design Gate

R2–R4 施工前必須留下 `DESIGN GATE：PASS`。R1 可用簡式 Gate；R0 不需要。

通過條件：

1. AS-IS 有可重現證據。
2. TO-BE 有明確法源、CR 或總監授權。
3. 目標、非目標與不可破壞的不變量完整。
4. 受影響的 source、runtime、生成物、測試、文件與資產已盤點。
5. 存檔影響已判定為無影響、相容、需遷移或未知。
6. 正向、負向與人工驗收條件已寫明。
7. 施工者與獨立審查者已分開。
8. dirty worktree 路徑所有權已確認。
9. 美術或史實性證據圖已列出逐件原典／權威館藏、第三方授權、生成工具與參數；缺少正式 ledger 時不得進正式生圖或 runtime 接線。

存檔影響為「未知」時，R3／R4 不得通過。Design Gate 只代表可施工，不代表已完成或可發佈。

新章與新互動先檢查《收官基線》§三的跨章因果，再讀章別規格。共同骨架是：

```text
角色真的需要答案
→ 玩家先承諾
→ 產生可見紀錄或操作痕跡
→ 玩家形成有限主張
→ 合理阻力追問
→ 玩家整合並承擔後果
```

實驗台、帳桌、作圖紙、出版校樣與辯論都只是章別形式；不得把第一、二章的左右頁工作台當成所有章的固定模板。

## 六、Implementation Gate

施工完成後，只有下列項目全部成立，才能標記 `IMPLEMENTATION GATE：PASS`：

1. 實作逐項符合核准 TO-BE，沒有未記錄的範圍漂移。
2. canonical source 與生成物已同步。
3. 定點測試與全套基線結果均已記錄。
4. R3／R4 的高風險契約有代表性負向控制；新增契約至少證明一次「保護行為被拔除時會紅」。
5. 視覺、音效與操作變更完成相應瀏覽器、裝置與可及性驗收；未驗項不得冒充通過。
6. 存檔路徑符合 §八的 fail-closed 要求。
7. diff 與 staged paths 未夾帶包外修改。
8. 獨立 CONFORMANCE 已給出分級結論。

Implementation Gate 不等於 commit、push、部署、production smoke 或總監真人試玩。

### 6.1 定點覆核何時足夠

只有同時符合下列條件，才可用定點 verification pass 代替完整 Implementation Gate：

- 修法完全落在原問題及原 path set；
- 沒有新增／刪除節點、分支、狀態鍵或不可逆操作；
- 不碰 schema、存檔、共用引擎、導航或證據解鎖層；
- 不跨章；
- diff 沒有改變原審查假設。

任一條不成立，就升級成完整 CONFORMANCE。最終受審成品要固定內容 hash 或 commit SHA。

## 七、dirty worktree 的路徑所有權

開工保存 `git status --short` 快照，並把相關路徑標成：

- `OWNED`：本工作包明確可改；
- `FOREIGN-WIP`：他人或其他工作包在途，不可改；
- `SHARED-GENERATED`：重建會碰到共同生成物；
- `UNKNOWN`：歸屬不明，停止修改。

操作規則：

1. dirty 不等於整棵工作樹停工；不重疊的工作可以在限定路徑下進行。
2. 目標檔、共同生成物或 shared interface 與他人 WIP 重疊時才停止。
3. 使用者明確交付且列入 `OWNED` 的 dirty path 可以施工。
4. `SHARED-GENERATED` 只有在來源歸屬與重建影響確認後才能重建。
5. stage、commit、歸檔只列明確路徑，永不使用 `git add -A` 或 `git add .`。
6. push、deploy 與不可逆外部操作，另需明示授權。

## 八、存檔與 schema 的 fail-closed 安全預設

任何可能改變序列化表示或語意的工作都先立個案遷移表。未以 legacy fixtures
證明免遷移，不得自行宣稱免遷移。

安全順序：

```text
辨識版本
→ 解析原始資料
→ 在暫存副本遷移
→ 驗證游標、進行中互動、證據與不可逆操作
→ sanitize
→ 再次驗證
→ 原子式取代現行存檔
```

任一步失敗：

- 不覆寫原存檔；
- 不自動補授證據、預測、借條、旗標或完章狀態；
- 不把未知游標猜到最近節點；
- 保留原始輸入或可恢復備份；
- 顯示玩家可理解的失敗訊息；
- 未知未來 schema 一律拒絕，不降級猜測。

最低負向驗證：

- 壞格式；
- 未知 schema；
- 偽造證據或不可逆狀態；
- 遺失游標；
- 進行中互動缺欄；
- 重複遷移的冪等性；
- 遷移後 invariant 失敗；
- 匯出／匯入與重新整理後語意保持。

schema 是否升版，以「載入器是否需要辨識新的表示或語意」判定，不以新增節點數量機械判定。

## 九、交付狀態

禁止單獨以「完成」「好了」「已發佈」涵蓋多個層級。交付固定分開：

```text
Design Gate：NOT RUN／FAIL／PASS
Implementation：NOT STARTED／PARTIAL／COMPLETE
Focused tests：NOT RUN／FAIL／PASS
Full tests：NOT RUN／FAIL（數量＋原因）／PASS（數量）
Registry updated：YES／N-A
Browser／device：NOT RUN／PARTIAL／PASS
Accessibility：NOT RUN／PARTIAL／PASS
Human playtest：NOT RUN／PENDING／ACCEPTED
Conformance review：NOT RUN／CONDITIONAL／PASS／RETURNED
VCS：UNCOMMITTED／COMMITTED <sha>／PUSHED
Release：NOT DEPLOYED／CANDIDATE DEPLOYED／PUBLIC RELEASED
Production smoke：NOT RUN／FAIL／PASS
Known gaps：
Preserved foreign WIP：
```

各欄只憑該層證據更新；下游狀態不能反推上游已通過。例如 deployed 不代表測試、獨立審查或真人試玩通過。

## 十、放行本規範與 skill v3 的條件

1. Claude 對本檔做獨立對抗審，作者不得自審放行。
2. 三個盲測必須選對主審對象：
   - 未進 runtime 的劇本 → TO-BE；
   - 玩家目前遇到的 bug → AS-IS；
   - 驗收施工是否符合劇本 → CONFORMANCE。
3. 五個風險案例必須分對 lane：
   - 唯讀審查；
   - 小型文件修正；
   - 新機制；
   - schema 遷移；
   - 正式發佈。
4. 審查者提供完整替換句後，角色不得自動改變。
5. 已知但不重疊的測試紅燈不得卡死 R0；重疊紅燈不得被忽略。
6. 法源登錄驗證器能找出不存在、過期、未追蹤、候選冒充現行與鏡像不同步。
