# 一、十條查證紀律

每一條都來自本專案的實際事故。**違反過的人會再違反，所以寫下來。**

1. **先量再說。** 體感抱怨（「亂」「雜」「點擊太多」）要先變成數字：相位數、控制項數、必要操作數、首次真決定落在第幾個節點、對話 choice 數，並與好玩的章節對比。憑印象開口會被打回。
2. **canonical 依真相模式決定。** AS-IS 查玩家現況時，以 `greybox/data/*.json`、
   引擎與實際行為為主；TO-BE 審核未施工目標時，以指定劇本、CR 或規格為主；
   CONFORMANCE 同時固定核准目標與 runtime 成品。任何一方不得越權取代另一方。
   （事故：曾把已淘汰的稿件當成 runtime 現況；也曾反過來用尚未施工的 runtime
   否定已核准的目標。）
3. **斷定某功能不存在之前，必須遞迴列完該資料檔的完整鍵樹，並 grep 引擎端的步驟名；兩者都空才算不存在。**
   （事故：同一天兩次只查一層巢狀就誤判整章缺功能——`fr.trap` 之外還有 `fr.claim`；`fr` 頂層之外還有 `fr.enemy.slope`／`fr.enemy.classify`。）
4. **引用專案法條前必須 grep 原文。** 不得憑記憶把某條原則當門檻去否決設計。
   （事故：誤稱「架構 §七 有輪替原則」，§七 實為四大系統。）
5. **宣稱「引擎零改動」前，先確認該功能是否已有獨立步驟。**
   （事故：對話寫 `probeOrder`，而工作台已有 `chooseInvestigationOrder`，照做會問玩家兩次。）
6. **抖動要分「交替」與「單向」。** 測量噪音用交替序列，不得偽造單向趨勢；系統性偏移才用單向。
7. **確定性 fixture，永不 RNG。** 同一組輸入永遠得到同一結果。
8. **⚠ fixture 若嚴格照某個變因等比生成，就等於用資料證明了那個因果——即使台詞說它不是。**
   台詞說有幾個條件同時改變，fixture 就必須真的有幾個條件同時改變。
   - 趨勢完美吻合該變因 → 玩家算比例會得到完美吻合，錯誤推論變成**有證據支持的正確結論**，而遊戲判他錯：**遊戲在騙人**。
   - 趨勢反向 → 資料當場自證錯誤，誘答死掉，這一課消失。
   - **正確形狀＝趨勢看起來成立，但比例／控制不吻合。**
   - **自檢：把生成表算出比例，與該變因的比例並排。兩排相同＝bug。**
9. **物理要算一遍**，而且要反過來算：**若某變因只影響量值不影響符號，而結論是符號主張，它就不可能推翻結論。**
   （事故：「船換航向→相對風的船首尾分量必然反向」在船速大於真風沿線分量時不成立。）
10. **史料未查證就不寫進設計。** 分標「已查證／待查證」，並指名該由誰去核原典；不得用推測填裝置細節。

> **與候選原則 61–71 的關係**：上列多條與《總監裁決單・甲案》的候選原則重疊。**若總監裁定入《設計原則手冊》，本節即改為指向手冊，不再重述。** 在裁定前，本節是實際在用的工作紀律。

# 二、四種洩答類型（選項不得靠形式猜中）

玩家不讀資料就能挑對答案，等於這一題不存在。四種都要擋：

| # | 類型 | 徵狀 | 實例 |
|---|---|---|---|
| 1 | **插旗詞** | 錯項含「任何／一定／全都／絕對／必然／已經證明」 | ch2 `fr.claim`「砲彈和星辰，**全都**適用」 |
| 2 | **語域不對稱** | 正解對沖（「只能說」「還不能」），錯項是無保留斷言 | ch2 正解以「**只**適用於…」開頭；ch3 `scope` 原版同型 |
| 3 | **視覺權重** | 只有正解帶 `primary` 樣式或較重的視覺 | ch4 `"orbitAction "+(c[0]==="ruleEstablished"?"primary":"")` |
| 4 | **異形選項** | 兩項同句型、一項句型不同 → **不同的那個就是答案** | ch3 `C3-1` 原版：兩項「X 派贏了」＋一項「這題錯了」 |

**修法一律是「平行句型」，不是列禁詞。**
四個選項用同一個句型，只差內容；讓差別落在**它有沒有做到**，不落在**它怎麼說話**。

**額外一條**：連正解與錯項用的動詞都要一致。
（實例：ch2 候選三句，正解用「寫**在**」、兩個錯項用「寫**到**」——那一個字就是答案。）

# 三、協作、版本與裁決紀律

## 3-1 分工

- **總監（陳育詮）＝唯一裁決者。** 排程、優先順序、範圍取捨一律是他的，**不要包在給對方的訊息裡繞一圈問**。
- 角色綁定當期工作包，不永久綁定 Claude、Sol 或 Codex；總監明示指派與當期任務書
  高於預設分工。
- 審查者提出完整修法只是審查證據，不自動取得施工權；只有總監改派、原施工者
  明示移交或任務書預先指定，才算角色移交。
- 作者與獨立審查者必須不同；同一人可以起草機制與台詞，但不能批准自己的成品。
- 能力限制不因移交改變：正式生圖仍只有 Sol／Codex 能執行。
- **對方說得對就直說並修。** 含糊帶過比犯錯更貴。

## 3-2 對抗審查輸出格式

總裁決（放行／有條件放行／退回重寫）→ 分級：

- **A 級**：物理錯誤、史實誤導、流程卡死、存檔破壞、答案提前洩漏、玩家無法理解任務、玩家代理權被拿走。
- **B 級**：可信度不足、可讀性、節奏、成本估算漏項。
- **C 級**：用字、引用精確度、一致性。

每項含：**位置（檔案＋行號或場景／節點 ID）→ 實際看到的文字或行為 → 為何是問題 → 可直接施工的修法**（台詞問題要給替換句）。

**讚美不需要證據，修改需要。**

### 3-2-1 放行門檻

- **形成性／總監試玩前，A 級必須為 0。**
- B 級若不涉及物理／史實正確性、狀態或存檔完整性、玩家代理權、任務理解，
  亦不構成製作或發佈安全風險，可採「有條件放行」進入試玩；每一條都必須列明
  驗證方式、負責工作包與完成期限，不得只寫「後續再修」。
- **內容凍結、法源啟用與正式發佈前，A 級與 B 級都必須為 0。**
- C 級可列後續清單，不阻擋試玩、凍結或發佈，除非多條 C 累積成可讀性或一致性的
  B 級問題。

**事故出處**：2026-07-28 CH3／CH4 對抗審首次採 A=0、B=0 試玩門檻；後續發現
把所有 B 一律擋在形成性試玩前，會讓不影響正確性與代理權的局部優化阻塞必要的
真人驗證。總監於 2026-07-30 裁決採上述分層門檻。

## 3-3 版本收斂

1. 多版並行時，**舊版檔頭加作廢 banner 並指向現行版**。
2. **同名版號必須連資料夾與作者一起寫。**
   （事故：`02_設計` 的 Sol 架構 v0.5 與 `04_劇本` 的 Claude 劇本 v0.5——同日、同版號、不同文件。）
3. **裁決紀錄不可與施工規格混在同一份檔。** 同時保留作廢分析與新定案的文件，
   一律降為「討論歷程」。施工依工作包路由讀取核准目標、相關法源與 runtime；
   不得把「只讀 CR 與 runtime」當成跳過跨章規範或真相模式的通則。
4. **裁決改變設計後，要回頭 grep 自己寫過的舊提案就地更正或加 banner。** 舊提案留在 repo 裡，對方會拿去施工。
   （事故：`×h/12` 的錯誤數字留在提案 §三，而它已被裁決推翻。）
5. **`archive/` 與已作廢版本的歷史正文不可改寫。** 只允許在檔頭追加作廢／勘誤
   banner 或 metadata，且須標明日期、原因與現行版指向；banner 以下原文保持不動。
   全域改名、批次替換與一般文案精修一律排除 archive／歷史版本。搬移、刪除或改寫
   仍須另取得明示授權；單純 add-only Git 納管不等於改寫。
   （事故：2026-07-28 艦長稱謂全域統一明確排除 archive；總監於 2026-07-30
   裁決採「檔頭可追加、正文不可改」邊界。）

## 3-4 治理鐵律（節錄，全文見架構計劃書）

- 永不 `git add -A`；只 stage 明列路徑；commit 前 `npm test` 全綠。
- **不碰他人未提交檔案；歸檔／搬移也算碰。**
- 凍結基線（劇本、章規格、灰盒規格）改動：**先寫 CR 或 GB-ADR，後改程式。順序不可反。**
- **一章一張 CR**，不得包成跨章 CR；輪到哪一章才開，讓每張 CR 都能引用前一輪實測。
- **共用引擎行為**（例如 `narrative.js` 的跨章路徑）不屬於任何一章的凍結基線，應走**引擎級 CR 或 GB-ADR**，不要塞進某一章的 CR。
- 「未寫入資產庫＝不存在」；裁決當日入檔。

## 3-5 工作循環

```
總監試玩回報 → 量測 runtime 換成數字 → 定位根因 → 提案（骨架先行，台詞後補）
 → 對抗審 → 總監裁決 → 版本收斂 → 施工（含契約測試）→ npm test 全綠
 → 治理紀錄 → commit（明列路徑）→ 定點驗證（只查裁決項＋抽查防線）→ 回到試玩
```

- 修 bug 先問「這是表現層還是引擎層」。
- **回饋訊息連開發者都會誤讀＝修訊息，不是修玩家。**
- **自動測試全綠 ≠ 已發佈。** 真人瀏覽器走查與桌機／手機簽核不可省、不可冒充。
- **定點覆核有邊界**：只有修法未超出原問題、原 path set、接口與狀態假設，
  且未新增節點、分支、狀態鍵、schema、存檔、共用引擎、導航或證據層變更時，
  才可採定點覆核；任一條不成立，升級完整 CONFORMANCE。
