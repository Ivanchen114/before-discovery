# 二、這三天浮現出來的工作流程（值得固定下來）

```
總監實玩 → 說出體感（不是規格語言）
      ↓
Claude 量測 runtime，把體感換成硬數字
      ↓
診斷根因（不是逐句潤色）
      ↓
提案（骨架先行，台詞後補）
      ↓
Sol 對抗審 → 總監裁決
      ↓
版本收斂（明確標作廢，避免雙版並行）
      ↓
Sol 施工 → 測試 → 走查
      ↓
Claude 定點驗證（只查裁決項，不重跑全審）
      ↓
回到總監實玩
```

**這條流程裡最有效的三個動作**：

1. **把體感換成數字**。「亂、雜、點擊多」→ 量出 8 相位、89 控制項、45–47 次操作、首次互動在第 44 個節點、對話選項 1 個（ch1 有 16 個）。數字一出來，爭論就結束了。
2. **骨架先行，台詞後補**。好散文會遮住爛選單（Sol 的話）。三天裡每次先寫骨架的那一輪都省下重寫。
3. **定點驗證取代全面複審**。Sol 修完只查裁決的那幾項＋抽查防線，比重跑一次完整審查快十倍，也不會漏。

# 五、候選設計原則（附出處，待總監裁定入手冊）

手冊現行到原則 60。以下為這三天可沉澱的教訓，格式依手冊規矩（**原則沒有出處＝教條**）。

**候選 61｜玩家的體感抱怨要先變成數字，再變成設計。**
「亂／雜／點擊多」不可直接翻成潤色工單。先量：相位數、控制項數、必要操作數、首次真決定落在第幾個節點、對話選項數，並與好玩的章節對比。
（源：ch3 節奏重評 20260725——量出 8 相位／89 控制項／45–47 操作／首互動第 44 節點／對話 choice 1 對 ch1 的 16）

**候選 62｜台詞與規格的 canonical 是 runtime JSON，不是 `.md`。**
`.md` 是給人讀的藍圖，`.json` 是玩家實際看到的，`.js` 由 JSON 生成不得手改。審查與施工一律以 JSON 為準；`.md` 只用於比對角色意圖。
（源：四章台詞審核基線錯誤——13 條發現有 7 條在 runtime 已不存在，20260725）

**候選 63｜引用專案法條前必須 grep 原文。**
不得憑摘要或記憶把某條原則當成門檻去否決設計。
（源：誤稱「架構 v0.3 §七 輪替原則」；§七 實為四大系統，§7.3 論辯系統是其一。輪替出自全系列架構 L413，且擔心的是 24 章、破點第五章，20260725）

**候選 64｜宣稱「引擎零改動」前，先確認該功能是否已有獨立步驟。**
（源：對話寫 `probeOrder`，而工作台已有 `chooseInvestigationOrder`，照做會問兩次，20260725）

**候選 65｜終局要求應升級，不是終局形式應輪替。**
判準：「這一章的終局，能不能用上一章的打法過關？」形式可重複，要求必須升級。
（源：連續三章辯論之爭；全系列架構 L413 的實質意圖是防模板化，20260725）

**候選 66｜變因必須是有人能下的命令，或要付代價的選擇。**
不要用抽象旋鈕代表現實中沒人能轉的量。改高度＝換船；改加速度＝下令加減槳的程度。
（源：總監對落石模擬 v1 的意見，20260726）

**候選 67｜後果放錯地方的變因就是假變因。**
若某個變因在物理上不影響結果，就不能做成「看起來會影響結果」的控制；要嘛移除，要嘛把它的後果放到真正該放的地方。
（源：`Δ = δv·τ − ½aτ²` 不含 `v`；船速的後果應落在**斷言的適用範圍**，不是落點，20260726）

**候選 68｜抖動要分「交替」與「單向」。**
測量噪音必須用交替序列，不得偽造出單向趨勢；系統性偏移才用單向。兩者不可混用。
（源：鼓拍讀數誤差設計；沿用 GB-ADR-002 的教訓，20260726）

**候選 69｜玩家介面不得出現內部代碼。**
（源：ch3 HUD 直接畫出 `A1 A2 A3 A6 S4 A4 A5`，且 A6 排在 A4 之前；ch4 已於 `eb297fc` 修過同一類問題。屬原則 44 再犯，20260726）
