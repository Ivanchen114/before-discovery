## 三、共享工作樹事故：完整時間線與方法論教訓

> **這一節獨立成節，因為它是本輪最有價值的程序性案例：一次審查行為本身污染了被審對象，而三方各自的處置方式決定了它是否會變成錯誤裁決。**

### 3.2 四項可帶走的教訓

1. **未提交的修法只存在於工作樹，`git restore` 會無聲毀掉它。** 本輪的修法成果不在版本庫裡，事故因此不可由 git 復原——真正救回它的是「bundle 是 parts 的串接產物」這個設計，使它可以**重建**而不需要備份。
2. **「bundle ≡ parts」這條契約是真的有用，而且它在事故當下就轉紅了。** 諷刺的是，claude 在前兩輪的反向控制中一直把這條紅燈當成雜訊排除（因為自己改 `assets.json` 會誘發它）——**這次它不是雜訊。** 排除規則只在「我自己剛改過檔案」時成立。
3. **回歸變異若不重建 bundle，只會打到漂移偵測，不會打到行為護欄。** A1 的兩組回歸變異之所以有效，正是因為 claude 與 codex 各自意識到並繞過了這一點。
4. **共享工作樹不應承受破壞性變異。** 本輪之後的規則是：所有變異一律在隔離副本執行，禁止對共享工作樹使用 `git restore`／`checkout`。三方本輪均遵守。

> **記錄一句公道話**：事故來自 gemini 的變異測試，但**她的變異本身是有效且正確的**——`visibleItems.slice(0,1)` 精確使測試轉紅（178/1），證明多圖護欄有效。問題出在**執行位置**（共享工作樹）與**還原方式**（`git restore` 而非備份還原），不在攻擊設計。

### 4.2 實作端的最終處置：分離判斷邏輯

```js
function visibleEvidenceItems(rule) {
  if (!rule || rule.disposition && rule.disposition.status === "withheld") return [];   // ① disposition 優先
  var items = rule.items || [];
  if (!rule.projectionOnly || rule.neutralBase) return items.slice();                   // ② 卡層旗標
  return items.filter(function (item) { return item && item.neutralBase === true; });   // ③ 逐張旗標
}
```

縮圖端同步改為 disposition 先判：

```js
var isWithheld = !!(resolved && resolved.disposition && resolved.disposition.status === "withheld");
var bgE = isWithheld ? tpl : (assetEntry(visualAsset) || (!resolved || !resolved.projectionOnly ? specificBg : null) || tpl);
```
