# 一、第一章｜誘答成立，但玩家按下錯項後就被拿走了思考權

## 1-1 runtime 實據（`scenes.json`，場景 `A1-3`）

玩家選「鉛球＋木球（不同材質）」後，接下來五個節點都是 `line`／`system`，沒有任何 `choice`：

| 節點 | 內容 | 問題 |
|---|---|---|
| `nB1` | 「城牆快試。木球明顯落後。」 | 觀察結果，可保留 |
| `nB2` 伽利略 | 「停。這數據不能用。」 | 過強：資料能記，只是不能回答「是不是重量造成」 |
| `nB3` 旅人 | 「木球比較慢，不正好——」 | 系統替玩家決定他剛才在想什麼 |
| `nB4` 伽利略 | 完整說出混淆、歸因困難與「一次只動一樣」 | NPC 代為完成診斷與修法 |
| `nB5` 系統 | 寫入「一次只動一個變因」 | 玩家未作判斷，結論已自動入筆記 |

孤立看 `nB3`，它是旅人代理權問題；但整段 `nB2–nB5` 連起來，已把「判斷資料效力 → 診斷混淆 → 提出修法 → 寫入筆記」全部交給 NPC／系統，違反玩家必須親手形成證據與主張的基本契約，故整段定為 **A 級**。

## 1-2 物理與證據邊界

原句「這數據不能用」不夠精確。這筆觀察不是廢紙：

- 它能支持：「這一趟木球比鉛球慢。」
- 它不能支持：「木球較輕，所以較輕的物體掉得較慢。」
- 原因不是資料不存在，而是**重量與材質同時改變，無法把差異歸到其中一項。**

較誠實的 NPC 收口應接近：

> 「這一趟能記，但還不能回答是不是重量造成的。」

## 1-3 未來 CR 應採的互動形狀

不應只把 `nB3`／`nB4` 兩句換成一個「找出哪些欄位改了」的表單；那仍可能只是辨識題。較好的形狀是：

1. `nB1` 先把玩家真的看得到的條件寫清楚：同一高度、同一放手方式；一顆較重的鉛球、一顆較輕的木球。
2. 伽利略不先判廢，只問：「這一趟能支持哪一句？」
3. 玩家在三個同樣可信的主張中選擇：

   - ✓ 「這一趟只能說木球落後；重量和材質一起換了，還不能說是哪一項造成。」
   - ✗ 「木球比較輕又落得慢，這一趟已經證明重量決定快慢。」
   - ✗ 「木球和鉛球的差別來自材質，重量已經可以排除。」

4. 錯答時，伽利略只指回兩欄：「重量和材質都換了。你憑哪一欄把它們分開？」玩家自己改口。
5. 玩家答對後，伽利略才命名：「下一趟只改一樣。」此時才把規則寫進筆記。

這樣錯項都從眼前資料長出來；正解也不是靠「只／所有」等插旗詞，而是靠玩家守住歸因邊界。

## 1-4 施工與驗收邊界

- 不需新增通用引擎，但需要重排 `nB2–nB5`，不能只做一般台詞潤色。
- 必須新增負向分支測試，至少鎖住：

  1. 錯答後仍停在診斷步，系統不替玩家說正解。
  2. 答對前不寫入「一次只動一個變因」。
  3. 回到選擇時，錯誤嘗試仍可查，正確診斷後才推進。
  4. 分支中止與存檔往返不丟失狀態。

- 教學上，ch1 是 ch3 混淆質詢的前置；施工上，先讓已進入驗收的 ch3 完成一次最新路徑真人試玩，再立即開 ch1 CR。這是避免打斷眼前驗收，不代表 ch1 可以無限延後。

# 二、第二章｜順序是對的；二選一、語域與自動改口才是問題

## 2-1 runtime 實據（`debate2.json`，`fr.claim`）

現行順序：

`slope → classify → claim → F5`

- `classify`：玩家只承認敵方資料「標出了這條規律的適用範圍」。
- `claim`：才要求玩家說清楚，這條規律究竟能寫到哪裡。

這個順序符合證據推理，也由 `CH2-CR-001` 明定，**不可把 `claim` 移到 `classify` 前面。**

現行 `claim` 只有兩項：

| 選項 | 文字 | 真正問題 |
|---|---|---|
| ✗ | 「砲彈和星辰，**全都**適用。」 | 「全都」直接插旗錯項 |
| ✓ | 「**只**適用於低速、短程，而且空氣阻力還不明顯的情況。」 | 「只」直接插旗正解 |

玩家不用讀資料，只要認得「全都」對「只」就能過。

## 2-2 `overMistake` 不證明順序錯誤

`overMistake` 的「剛親口承認的邊界，轉身就誇了口」是錯答後的回應。它指的是玩家已承認「存在邊界」，不是玩家已說出邊界的完整內容。

這句可以改得更精確，例如：

> 「你剛承認這批資料畫出了一條界線，現在卻把界線外也一起寫進去了。」

但不能因此倒轉 `classify → claim`。

## 2-3 未來 CR 的誘答方向

保留原順序，把 `claim` 擴成至少三個**同句型、同視覺權重**的範圍主張。候選形狀：

- ✓ 「這條規律寫在這批低速、短程的紀錄裡；空氣阻力明顯以前，可以繼續拿來驗。」
- ✗ 「這條規律寫到砲彈的射程裡；桌面和戰場只是尺寸不同。」
- ✗ 「這條規律寫到星辰的路上；距離再遠，也只是同一條弧線繼續長下去。」

第二項利用辛普里奧已提出的戰場尺度質疑；第三項利用本章想把桌上拋射一路推到天空的自然誘惑。兩個錯項都不靠「所有／必然／絕對」插旗。

這三句仍是候選文案，不是定稿。開 CR 前需再查兩件事：

1. 戰場外推是否能由本章玩家當時持有的資料合理支持，而不是只靠雄心。
2. 星辰外推是否符合當時的概念盲點，且不把第四章才要建立的內容提前說完。

## 2-4 實作成本不是「資料結構改三項」那麼簡單

- `chapter-ui.js` 已用陣列迭代選項，二選三不需重做 UI 結構。
- 但 `narrative.js` 把唯一錯項硬編碼為 `id === "over"`。直接加第二個錯項，它會被當成正解並解鎖 F5。
- 現行錯答後會由系統自動說出 `honestText` 再推進；這重演了 ch1 的代理權問題。

未來 CR 應把判定改為資料驅動（如 `correct`／`reason`／`reply`），並讓錯答留下後果後回到 `claim`，由玩家自己改口。若沿用單一 `overTried` 可不做存檔 schema 遷移；若要分辨兩種錯因，才需新增狀態與遷移。

測試需同步覆蓋：

- 兩個錯項都不會被當成正解。
- 錯答不自動替玩家說 `honestText`。
- 中止、雙歸零、重入與存檔往返。
- 正確主張成立後才解鎖 F5。

成本定為 **中等**。

# 三、第四章｜誘答與失敗都已存在，但提交前被介面連續洩答

## 3-1 runtime 已有完整的生產性失敗

玩家確實可以：

1. 選「我們已證明引力如何穿過空間作用」。
2. 由 `setBoundary("mechanismSolved")` 留下錯誤嘗試。
3. 收到 `mechanism-slot-empty` 的資料邊界診斷。
4. 把錯誤末句印成壞校樣；錯稿留在出版紀錄中。
5. 回頭重排並修正。

`run-node.mjs` 已有測試鎖住這條路。因此第四章不是缺誘答，也不需要重蓋狀態機。

## 3-2 真正的前置洩答

以下內容都在玩家提交末句**以前**出現：

| 位置 | 洩答 |
|---|---|
| proof 任務說明 | 「最後一句也不能蓋過尚未解開的空白」 |
| SVG 初始狀態 | 尚未作答就顯示「末句尚未守住作用機制的空白」 |
| 選項前導 | 直接說「引力如何穿過空間」的槽沒有任何紙可放 |
| 正解按鈕 | 自己寫出「引力如何作用，仍未決」 |
| 按鈕樣式 | 只有正解帶 `primary` 視覺權重 |
| 免費預覽 | 尚未選末句，也會回報「機制末句尚未守住」 |

其中 `primary` 是最直接的視覺洩答；原始盤點漏列。

以下兩項只在玩家犯錯後出現，**應保留**：

- `mechanism-slot-empty`：玩家已提交過強主張後，指出沒有來源紙。
- 「機制末句越界」：壞校樣已印出後的歷史紀錄。

它們符合「先承諾，再看後果」，不是提示。

## 3-3 未來 CR 的修法

保留既有 `setBoundary → overclaimTried → preview／submit → wrong-proof` 骨架，只改四層：

1. **前置文案中性化**

   - 任務：「最後一句也必須接回紙上證據。」
   - SVG 未選：「末句尚未選定。」
   - 問句：「四條來源線都接回去了。請替整本書寫下最後一句。」

2. **兩個選項同語域、同視覺權重**

   候選形狀：

   - ✗ 「最後一句寫在作用本身：這本書說明了引力如何穿過空間，使天體改變方向。」
   - ✓ 「最後一句寫在可反驗的關係：距離、偏折與軌道由同一條規則連起來。」

   正解不再預先替玩家說「機制仍未決」；那個邊界應由選擇後的審核結果顯示。

3. **移除正解專屬 `primary` 樣式**

4. **區分「尚未作答」與「已經答錯」**

   現行 `proofAudit()` 把兩者都壓成 `boundaryOk=false`，所以預覽會提前診斷。未來可在 UI 分流，或回傳：

   - `boundaryStatus: "missing"`：只說末句尚未選定。
   - `boundaryStatus: "wrong"`：才指出機制主張沒有來源紙。
   - `boundaryStatus: "ok"`：範圍成立。

這是小型 audit 語意修正，不是新玩法。

## 3-4 排序與成本

第四章仍可排在 ch1、ch2 之後，因為「描述規則不等於知道機制」是最抽象的認知邊界；但不得再以「工程風險最高」作理由。

就 runtime 而言，它主要是前置文案、按鈕樣式與 preview 分流，成本估為 **小至中等**。第四章已有目前四章中最完整的生產性失敗骨架；這輪應讓誘惑真的活著，不要再造一次。
