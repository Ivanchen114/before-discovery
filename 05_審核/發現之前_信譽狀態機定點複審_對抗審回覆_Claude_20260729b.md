### C-3|`reasonRules` 是逐字白名單,與劇本文案強耦合,但這件事沒寫進法源

**好消息,漂移是抓得到的**(我實測兩個方向):

**修法**:在 GB-ADR-030 或 `02_設計/README.md` 明記這條耦合——「`reason` 字串是玩家可見契約**兼**存檔驗證鍵;修改任一 `reason` 必須同步 `src/sanitize.js` 的 `reasonRules`」。不必改程式。

## 五、我的誤判,以及一條給自己的守則

**我用錯了 sanitizer 入口。** 第一次偽造測試我拿 `deserialize()` 當驗證入口,得到「八類全部 ACCEPT」的結果——那會是一份災難性的假報告。真正的入口是 `sanitizeImport / sanitizeImport2..5`,而且回傳的是 `{ok:false, reason:"…"}`,**不是 `{error:…}`**。我的判定式寫成 `r.error` 就把所有 REJECT 讀成 ACCEPT。

**這是我第二次踩同一個坑**(上一次是 `assertK1` 回傳 `ok:false` 不是 `error`)。我把守則寫在這裡:**攻擊任何 API 之前,先把回傳物件原樣印出來看一次,不要沿用上一個 API 的形狀假設。**用錯 API 產生的「全綠」或「全漏」,比沒測還危險。

發現方式也記錄一下:是**對照組露的餡**——未動的合法存檔也被我判成 ACCEPT 是正常的,但**八類全部同一個結果**這件事本身就不合理。往後測試一律放對照組。

**我沒做的**:桌機與 844×390 手機橫屏真機驗收,依總監指示由本人進行,我不代稱。報告 §六 的功能瀏覽器冒煙(console 0 error、聲音控制還原、雜湊載入)我沒有獨立復現——那需要開瀏覽器,不在我這輪的 R0 範圍;Sol 也已明說那不等於視覺驗收。
