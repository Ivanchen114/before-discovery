# 《發現之前》六章互動機制「挑戰與樂趣」盤點——三方交叉驗證整合報告

**日期**：2026-08-05
**觸發原因**：總監要求換一個審查視角——不是劇本邏輯、不是介面找不找得到按鈕，而是六章的互動機制本身有沒有真正的挑戰性與樂趣。
**方法**：claude、codex、gemini三方獨立盤點六章的`engine.js`~`engine6.js`判定邏輯與`chapter-ui.js`渲染。claude與codex均以Node直接窮舉/攻擊引擎驗證（不只讀程式碼猜行為），我對關鍵發現逐一讀原始碼核對。gemini第一輪對第六章的評分有明顯問題，已要求重新檢查，本報告先整合claude與codex已完全收斂的部分，gemini的修正版另行補充。

---

## 一、總裁決：六章不是「都沒挑戰」，是前段強、後段弱，且「完成很多步驟」被誤當成「有挑戰」

claude與codex獨立得出幾乎一致的結論：**第一到第三章已有可用的探究骨架，第二章尤其成熟；第四到第六章隨著站點、表格、審計越來越多，玩家真正能改變結果的瞬間反而變少。** 兩方都特別警告：不要把「操作步驟數量多」跟「有挑戰」搞混——這正是本輪審查要抓的核心陷阱。

---

## 二、⭐ 本輪最重要的單一發現：第四章K3是「孤兒輸入」，玩家的預測從未被引擎讀取

**這是codex獨立發現、我已逐行讀`engine4.js`核對完全屬實的P0級問題，比原本的K3描述更嚴重。**

K3（火星/木星未揭露預測）的UI流程是：玩家先押火星、木星的週期範圍（`playerBand`），封存後才能拆開觀測資料核對，理論上是「先押注、再核對」的科學方法示範，也是先前多輪審查稱讚的機制。但實測引擎邏輯：

```js
// engine4.js:1416-1424 sealPlanetPrediction
pass: residualPct <= 3,                    // 理論值(平方反比律)跟真值的誤差
playerBand: bandId, playerBandValue: band.value,
playerBandMatched: Math.abs(band.value - actual) <= (...)  // 玩家猜測跟真值的誤差——存了，但…

// engine4.js:1462-1467 revealPlanetPredictions
s.planetLab.crossScalePass = [...].every(function (id) {
  return s.planetLab.predictions.some(function (row) {
    return row.planet === id && row.pass && row.revealedAfterSeal && !row.superseded;
  });  // ← 只檢查 row.pass，不檢查 row.playerBandMatched
});

// engine4.js:1496-1503 assertK3
var ok = ... && s.planetLab.crossScalePass && concept === "withheld-data-prediction";
// ← 授證只要求crossScalePass，從頭到尾沒有一處讀取playerBandMatched
```

**玩家猜測的欄位存在、UI也讓玩家做了選擇，但整條授證邏輯完全不會去讀那個欄位。** 只要平方反比律本身鎖定正確（`exponent=2`，這幾乎必然成立，因為現實物理就是這樣），玩家不管押得多離譜都會拿到K3。codex的精準分類：這不是「玩家的猜測不重要」，是「代理權斷鏈」——UI收了輸入，但沒有任何判定消費它。

**修法方向（codex提出，不要求玩家「猜中才算科學」）**：保留錯誤預測仍能拆封（科學上錯猜不該被禁止取得資料），但揭曉後新增一個診斷判斷——玩家必須正確判讀「理論的數值預測 vs 未揭露觀測」才是真正檢驗法則的那組比對（而不是「我的直覺帶 vs 觀測」或「觀測 vs 觀測」），`assertK3`改成同時要求這個診斷正確。回歸測試需鎖三條：①錯band+未完成診斷不得授K3 ②錯band+正確診斷可以授K3且錯帶留痕 ③**正確band+錯誤診斷也不得授K3**（codex補充：三條合起來才能證明授證依據是「理解未揭露檢驗」，不是猜中band或事後矇對其中一項）。估計成本0.5-1人日，小幅schema/sanitizer/test增補，可完全回退。

## 四、最好玩 vs 最不好玩：兩方獨立收斂到同一組答案

**最好玩：第二章的零件指紋診斷（`compareBalls`／H=25换球驗證）**
兩方各自形容：claude稱「失敗是線索不是修牆，錢誤回饋用物理現象本身（一線光駁回錯誤讀值）」；codex稱「這不是題目包成動畫，是玩法本身在演科學方法」。核心機制一致：裝置零件損壞會產生**具名、可反推的雜訊指紋**（`speedDrift`/`directionScatter`/`coarseRead`），玩家靠觀察資料形狀就能診斷問題所在，而不是單純被告知「答錯了」。

**最不好玩：第六章長時段連續加熱（`runContinuousSegment`）**
```js
if (args.action !== "record-next") return fail(state0, "unknown-run-action");
var temperatures = [31, 47, 65, 83, 96, 100];  // 硬編，只吃格數
```
兩方一致：六次按同一個按鈕，沒有中途判斷、沒有風險、沒有策略。claude額外指出一個諷刺點：這一站偏偏是設計文件裡認定的本章「新動詞」（全章第一次量連續累積量），結果全章結構重量壓在互動最薄的一站上；且claude補充：上一輪施工把原本「三鍵結果相同的假選擇」誠實地刪成單一按鈕，這個處理本身是對的（不再騙玩家），但副作用是把「假挑戰」變成了「無挑戰」——問題沒解決，只是換了一種呈現。

## 五、其他值得總監注意的收斂發現

- **第一章辯論第三柱代答問題，這是本輪第三次被獨立發現**（先前「共同發現感」審查裡codex已發現一次，這次claude與codex又各自獨立重新確認），累積證據強度很高，建議優先修——成本低（codex估0.5人日，比照P1/P2改成`reasonMode:"player"`即可，不改schema）。
- **第五章「三次測量」是重複工時，不是真正的多次測量**：claude的Node實測顯示三筆鋼球資料完全相同（24→24、144→144逐位相同），三筆油灰資料也完全相同。兩方都建議：若要保留「三次」，應該讓每次測量帶有可見的小幅誤差，讓玩家從「每次不一樣，但總帳仍近似閉合」裡建立信心，而不是让三次變成單純的工時。
- **第六章的判斷題正解全是「較謹慎保守」的選項**：claude指出這是全章教學重點「不要說超過你的紙」被玩家找到一條不必碰物理的捷徑（挑語氣小的），建議四台判斷各補一個「收得太窄」型的誤答（呼應先前審查已對其他章節做過的同類修正）。

## 六、重新設計提案彙整（機制層級，非台詞層）

按兩方一致認可的優先順序：

1. **P0｜第四章K3改成「孤兒輸入→有讀取的診斷判斷」**（見第二節，0.5-1人日，不改schema）
2. **P0｜第一章辯論P3改`reasonMode`為`player`**（0.5人日，重用P1/P2既有結構，不改schema）
3. **P1｜第六章長時段改「配額下的多選一」**（claude提案：新增`shiftBudget`與`drift`/`waterLevel`狀態，每段依決定性規則出現異常，續鑽/校準/修漏三動作互相排他，8格配額內取得6格乾淨讀數——**這是本輪唯一需要新schema欄位、需開CR的提案**，順帶解決另一項「`days`欄位從未被讀取」的既有問題）
4. **P1｜第五章給器材選擇真實後果**（移植第二章手法：不同速度/高度設定引入可辨識的系統性偏差，`assertJ1`的動量閉合會因此失敗並指向偏差形狀，不新增schema，約30行）
5. **P2｜第三章減少卷宗行政感**（每輪只顯示一張「船長目前最在意的缺口卡」，保留核心偵查迴路，純UI編排，不改schema）
6. **P2｜第四章K4改逐案揭曉**（不一次攤開三案，玩家先猜「這一案較可能讓兩模型分開」再逐案跑，1-1.5人日）
7. **P2｜第一章讓「音格」計時器有取得成本**（只改`patterns.json`的`dayCost`數值，零新機制，解決「找到最佳計時器後挑戰斷崖式歸零」的問題）

## 七、gemini修正版：第六章逐站強弱盤點（重新評分為挑戰2.5/樂趣3.0，已附證據核對屬實）

gemini第一輪把第六章打了全案最低分（1/1），只用兩個弱例子代表整章，已被打回；重新評估11站後修正為**挑戰2.5/5、樂趣3.0/5**，並清楚區分強弱站點（我已對關鍵行號逐一核對，全部屬實）：

**強勢站點（不弱，表現優異）**：
- `judgeDryStrip`乾式紙帶台：改變壓力會讓紙帶留下`null`斷點（`engine6.js:254`），失敗有可見後果
- `judgeFrictionConditions`摩擦條件台：三種條件各有明確不同的溫度曲線——只轉動不壓緊`[18,18.1,18,18.1]`、只壓緊不轉動`[18,18.2,18.2,18.3]`、壓緊並持續轉動`[18,23,29,36]`（`engine6.js:212`已核對屬實），要求玩家拆解「接觸」與「運動」兩個變因
- `judgeAirComparison`密合空氣對照台：完整的「先封存預測、後操作驗證」循環
- `judgeFiniteSource`來源封條判讀：判讀權真的在玩家手上（「預測未兌現」／「本輪尚未走到終點」等由玩家選）

**弱勢站點（維持原判，證據更完整）**：
- `runContinuousSegment`長時段連續加熱：維持原判，全案最弱單一機制
- `setSourceLedger`來源追債起點：UI下拉選單直接讀取`window.GB.Engine6.SOURCE_RULES`（`chapter-ui.js:7866`，已核對屬實）當防呆清單，玩家本質上是暴力配對，選錯也沒有實質代價（不扣天數、不留痕，只是被擋下重選）
- `water-box-bench`水箱前置作業：單純的To-Do清單勾選，沒有誘答或失敗分支
- `model-audit-board`與`joint-verification-page`：拉紙條進格子，選錯用error訊息擋住，不是推理是窮舉

**gemini針對兩個最弱站點提出的機制重新設計提案**：
1. **`runContinuousSegment`改成「馬匹疲憊與維持條件」的資源管理**：每推進一個半小時前，玩家要在「換馬（產生小gap）」「加水（稍微降溫）」「硬撐（可能留下null斷點）」之間選擇，撐到沸騰且曲線夠平滑才算取得完美原紙——把點擊器變成維護實驗穩定性的持續決策。
2. **`setSourceLedger`改成「事後辯證」而非「UI防呆」**：移除引擎的即時擋錯，允許玩家寫下錯誤的來源對應關係，直到最後的共同驗證頁才由NPC（凱斯勒）拿著玩家自己配錯的紙條攻擊邏輯矛盾——玩家要為自己的錯誤選擇買單，而不是靠系統下拉選單糾錯。

**與claude、codex的結論整合**：三方現已完全收斂——長時段連續加熱是六章（也是全案）最弱的單一互動機制，這一點證據最扎實、三方一致；但整章並非全面貧弱，摩擦台與乾式紙帶台維持「做得最好的兩站」的既有評價。

## 八、未能驗證

- claude對第四章K1的「3/27組合可行」是引用程式註解與UI文案，Node窮舉本身未跑成功（傳入的action參數格式跟引擎不符），標記「靜態可見，未經親自窮舉驗證」，建議之後有人補跑。
- 兩方都未做瀏覽器真人試玩，樂趣分數本質上比挑戰分數更主觀，claude建議若三方樂趣分數有分歧，以「失敗是否有指紋」這個可驗證項目為準收斂。
- 第三章186,000種設計空間在真人實玩時是否會變成選擇癱瘓，兩方都無法從靜態分析判斷，需總監實機試玩驗收。
