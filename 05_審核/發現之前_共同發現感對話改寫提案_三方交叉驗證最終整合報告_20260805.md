## 二、⭐ 本輪最重要的新發現（提案本身沒抓到，三方審查時挖出來的）

### 發現一：第四章K2的月球偏折數字是造假的常數，不是真的算出來的（P0，claude獨立發現，codex用Node複驗確認並加深）

**證據**（`greybox/src/engine4.js`）：
```js
// :6
var TEACHING = { earthRadiusRatio: 60, surfaceOneSecondFallM: 4.9, moonSixtySecondSagM: 4.9 };
// :1191
sc.moonOneSecondSagMm = round(TEACHING.moonSixtySecondSagM * 1000 / 3600, 1);
```

`moonSixtySecondSagM`（月球60秒偏折）**被直接寫死等於`surfaceOneSecondFallM`（地表1秒落距），兩者都是4.9**。全檔搜尋月球週期「27.3」、「正矢」、「sagitta」、角速度「2*Math.PI」，在`engine4.js`與`chapter-ui.js`的K2段**全部出現0次**。也就是說，月球一秒偏折從來不是用「距離60R＋週期27.3日＋正矢幾何」真的算出來的，是拿一個被設成等於地表答案的假常數÷3600得到的。

**這為什麼是嚴重問題**：畫面上跟總監說「兩張獨立算出的紙自己碰上了同一個數字」，但實際上月球那張紙的輸入本身就等於地表答案，兩者「碰上」是程式保證的，不是發現的。**這直接違背總監的核心原則**——玩家以為自己完成了一次真實的獨立發現，但答案早就被塞進常數裡，成就感是被騙來的。若總監定案版對白（牛頓問「有沒有先假定平方反比」、旅人答「沒有，只用了距離、週期和軌道幾何」）直接套進現在的引擎，這兩句台詞在遊戲裡會是不成立的謊話。

**codex加碼發現的第二、三層問題**（Node直跑複驗）：
- `round(4.9×1000/3600, 1)` 實際回傳 **1.4**，不是UI與GB-ADR-039文件宣稱的1.36——也就是說連「顯示的數字」都跟文件不一致，這是第二個獨立bug。
- `judgeScaleRatio`硬性只接受**剛好3600**這個判定值——若把常數改成用真幾何算（例如60R+27.3日得1.356mm，或384400km+27.321661日得1.362mm），比值會落在3600附近但不是剛好3600，現行判定邏輯需要跟著調整容差，不能只換常數了事。

**修法成本，兩方看法略有不同（如實列出，供總監參考）**：
- **claude**：這是單一問題，改法便宜——把月球一秒偏折改成真的用週期+幾何算出（1.36mm），60秒維持「事後放大顯影」，不動K2 action/schema/三段UI結構，ADR-039逐條仍成立，只需微調81.7mm退件值為81.4mm。
- **codex（不同意claude「一次修好」的說法，並在最後一輪確認堅持這個切分）**：這其實是**兩個分開的問題，最終報告必須分開列，不能把①寫成已經包含②**。①「常數造假」本身是P0，用真幾何重算+保留兩位精度，**0.5-1人日**可修好，不需動schema/action/gate。②但如果總監同時要求「1秒為發現起點、60秒只作事後顯影」（即敘事順序也要反轉），現行`n7`、embed的`hint`、藍紙UI與`convertMoonTime()`的語意目前是反過來的（60秒在前），GB-ADR-039也明文裁定「60→1」的方向，改順序要動`n7`、hint、UI phase與action契約，且需要正式**supersede（取代）GB-ADR-039**，不能只改一句話。這部分重估後約**再加1.5-2人日**，兩項合計**2-3人日**（原本codex的第一版估算是3-5人日，已下修；仍遠低於案B的7-12人日）。
- **81.4mm vs 81.7mm退件值：codex提醒這不是單純的數字微調，取決於先定案哪一組地月參數當fixture**——若採歷史語境的「60個地球半徑＋27.3日」得81.4mm；若採現代平均月距384400km＋恆星月27.321661日則81.7mm仍然成立。兩組都物理上站得住，但**必須先由總監或設計端定案要用哪一組當runtime的權威fixture，才能定下退件文案的數字**，不是修常數時可以隨手選一個帶過去。

**總監需要決定的是**：只修①的造假常數（讓月球數字是真算出來的），還是①②都做（連敘事順序也一起反轉成「1秒起點」）。①是無條件該做的bug修復；②是設計選擇，牽動要不要正式取代ADR-039。

### 發現二：第一章有一個繞過系統防雷制的漏洞（claude獨立發現，三方裡唯一發現這條）

**證據**（`scenes.json`的`conclusionLint`與`A2-2/n3b`）：
系統有一套「結論詞彙lint」機制，禁止角色在玩家自己完成判讀前說出關鍵結論詞（`bannedWords`含「平方」），並用`whitelist`豁免特定已經確認安全的節點。**現行`A2-2/n3b`伽利略說「每一個總數，都是時間刻度自己乘自己」——這句話的意思就是「平方」，但因為沒有用到「平方」這個被禁字，lint抓不到，而且`n3b`不在whitelist裡，代表這個提前揭曉從來沒有被系統或人工正式審過。**

這是一個機制漏洞（改寫規避掉了防護網），不是單純的語感問題。好消息是：照提案的方向把這句的命名權還給旅人之後，這個漏洞會自動關閉，不需要修改lint本身的資料——這是整輪審查裡唯一一項「治理增益」（讓系統變得更安全，不只是換句話講）。

## 五、第四章案A／案B：三方一致裁決案A

**三方一致**：採案A（單場教學重建＋明示近似債），不採案B（拆成兩段歷史重算）。

**理由**：
- **史實**：claude獨立算過，1665年英格蘭常用的地球尺度（緯度一度=60英里）會讓牛頓算出約64²而不是60²，跟3600差16%——這對應他晚年回憶「answer pretty nearly」的真實出處。但史學上對「他何時真正拿到更準的地球尺度」有爭議，能穩穩站住的史料只支持「他當年算出來只是接近，不是精確吻合」，案A的「明示重建＋尺度債」已經承載了史料能支持的全部；案B會多背一個仍有爭議的因果。
- **治理**：案B會直接推翻GB-ADR-039兩條明文（「不新增存檔欄位」「完成後才明說1/3600並命名距離平方關係」），要做必須先修訂或廢止ADR-039，不是一次對白CR能承載的（codex詳列受影響清單：`D1-2`/`D2-1`/`D4-1`/`DE-1`四個場景、K2證據取得時機一分為二、`engine4.js`四個action需要加階段參數、`sanitizeImport4`同步更新、ADR-039驗證段鎖定的四項全部重寫，估算7-12人日）。
- **體驗**：案B會讓高潮出現兩次互相稀釋，或第一幕沒有高潮——claude指出這正好重演總監自己在K2卡關時的原話「這裡只是盲猜嗎？我不知道要幹嘛」（見施工總清單第六節記錄）。
- **場內重建標示已經部分存在**：`scenes4.json`的`historyTag: "modern-model+reconstruction"`與`D1-2/n1`的系統旁白「合理重建：牛頓晚年說……本場數字是現代教學整理值」已經在runtime裡，claude認為這已部分滿足案A對「場內明示」的要求。
