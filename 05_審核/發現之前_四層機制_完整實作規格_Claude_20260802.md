## 0. 一頁摘要

系統由**四層**組成，各有唯一職責，互不重疊：

| 層 | 代號 | 名稱 | 職責 | 生效範圍 |
|---|---|---|---|---|
| L1 | `reputation` | 信譽 | **研究誠信**：話有沒有超過紙 | 全五章，唯一縱向量 |
| L2 | `alignment` | **對位**（原「說服力」） | 當場攻防：證據與證詞的配對品質 | ch1／ch2／ch5（`state.debate.persuasion`）＋**ch3（獨立路徑，見下）** |
| L3 | `pressure` | 守門人實物 | 對手可以不給你的東西 | **僅 ch4** |

> **v1.1 修正（2026-08-02，依 codex 查證）**：原 v1.0 寫「ch3 無 L2」是**錯的**。ch3 有自己的當場計量——`state.lab.caseFile.dossier.debate.rep`，並由 `renderShipDossierDebateTrack()` 繪製，**不走** `debateInit()`／`debatePersuasion()` 共用路徑。
> 因此原則要改述為：**每章只能有一個當場計量**（不是「有辯論才有」）。ch1／ch2／ch5＝`debate.persuasion`；ch3＝卷宗質詢軌；**ch4 是唯一沒有當場計量的章，L3 只補給它**。
> 連帶結論：**ch3 的「簽名欄」降為選用的目標指示器，不是壓力計量**——否則同章會出現兩個計量互相稀釋（這正是我用來反對「三章換皮」的同一條理由，必須一致套用在自己身上）。ch3 的當場壓力改由敘事承擔（馬蒂厄手上的封蠟，見第三章修法提案 Part A），不再需要新 UI 元件。
| L4 | `claims` | 主張帳（含懸置） | claim→evidence→status→repair 契約 | 全五章 |

**兩條硬規則**（整份規格的骨幹）：

1. **信譽只在「邊界決策點」變動。** 一般答錯（物理答錯、實驗配置失敗、選了較差的研究策略）**一律不扣**。只有在**同時提供越界選項與守界選項**的節點上：選越界 −1，選守界 +1。
2. **L2 與 L3 互斥。** 有辯論的章用 L2，沒有辯論的章用 L3。不並存，避免同章兩個計量互相稀釋。

## 1. 資料 Schema

以 TypeScript interface 表示。實際儲存為 JSON，掛在 `state` 之下。

### 1.1 型別基礎

```ts
type ChapterId   = 'ch1' | 'ch2' | 'ch3' | 'ch4' | 'ch5';
type ClaimStatus = 'pending' | 'anchored' | 'overreach' | 'repaired';
type Tick        = number;   // 全域操作時鐘；單調遞增、無間隙（沿用 ch4 既有 lab.sequence 機制）
type NodeKey     = string;   // "SCENE/NODE" 或 "SCENE/NODE.OPTION"
```

### 1.2 L1 信譽

```ts
interface Reputation {
  value: number;            // 整數 0..5，初始 3
  locked: boolean;          // true = 關鍵人物拒談，須走修復場（沿用今日 flags.repLocked）
  history: RepEvent[];      // append-only，不可重排、不可刪
}

interface RepEvent {
  // v1.2 修正：現行 applyRep() 寫入的是 { t:'rep', d, from, to, at: sourceId }
  // ——`at` 是**來源字串**（例 'C0-3/c1.bounded'、'orbit4.setHookeScope'），不是數字 tick。
  // 本 schema 必須沿用該形狀，不得改成時間戳，否則所有既有存檔都會型別不符。
  source: string;           // ＝現行的 at；同時是 applyRepOnce() 的去重鍵
  delta: -1 | 1;
  from: number;             // 現行已記錄
  to: number;               // 現行已記錄
  reason?: string;          // 玩家可見文案
  claimId?: string;
  kind: 'overreach' | 'bounded-choice' | 'repair';
  // 順序由 eventLog 中的位置決定，**不要**引入獨立時間軸
}
```

**不變式**
- `value` 只能由 `history` 重算：`clamp(3 + Σdelta, 0, 5)`。存檔中的 `value` 若與重算不符 → 匯入失敗。
- `history` 的 `at` 嚴格遞增。
- `locked === (value === 0)`，除非修復場已完成（`kind:'repair'` 的最後一筆之後 `locked=false`）。

### 1.3 L2 對位（僅 ch1／ch2／ch5）

```ts
interface Alignment {
  value: number;            // 整數 0..5，進入辯論時初始 5
  active: boolean;          // 僅在 debate embed 內為 true
  round: number;            // 第幾次進入辯論（複盤後再入 +1）
  misfiles: MisfileEvent[]; // append-only
}

interface MisfileEvent {
  at: Tick;
  evidenceId: string;       // 玩家出示的證據
  targetId: string;         // 出示對象（證詞／支柱 id）
  ok: boolean;              // false = 配對錯誤 → value -1
}
```

**不變式**
- `value = clamp(5 - count(misfiles where ok===false in current round), 0, 5)`。
- `value===0` → 觸發該章的複盤場（ch1 `A3-F`／ch2 `B3-F`／ch5 `E3-1/debrief`），`round+1`、`value` 重置為 5、**已破支柱與已成功的判讀步驟保留**。
- `alignment` **不影響** `reputation`。兩者完全解耦（這是與現行行為的重要區別，見 §4 遷移）。

### 1.4 L3 守門人實物（僅 ch3／ch4）

```ts
type PressureObject = SignatureObject | ConsumableObject;

interface PressureBase {
  id: string;               // 'ch3.signature' | 'ch4.pressWindows'
  label: string;            // 世界內名稱，顯示用：「簽名欄」「開印空檔」
  ledger: PressureEvent[];  // append-only
}

interface SignatureObject extends PressureBase {
  kind: 'signature';
  requiredConditions: string[];  // 條件 id 清單，例：['baseline','steady','release','sealed','repeat']
  satisfied: string[];           // 已核可的條件 id（⊆ requiredConditions）
  signedAt: Tick | null;         // 非 null = 已簽
}

interface ConsumableObject extends PressureBase {
  kind: 'consumable';
  total: number;            // ch4 = 2
  remaining: number;
  consumedAt: Tick[];       // length === total - remaining
}

interface PressureEvent {
  at: Tick;
  type: 'condition-met' | 'condition-revoked' | 'signed' | 'consumed' | 'refused';
  detail: string;           // 玩家可見的一行說明
}
```

**不變式**
- `SignatureObject.signedAt !== null` ⟺ `satisfied ⊇ requiredConditions`。
- `ConsumableObject.remaining === total - consumedAt.length`，且 `remaining >= 0`。
- `pressure` **不影響** `reputation`；它是節奏與成本，不是誠信。

### 1.5 L4 主張帳（claim→evidence→status→repair）

```ts
interface Claim {
  id: string;               // 穩定 id，例 'ch2.F1' 'ch3.G1' 'ch4.K2'
  chapter: ChapterId;
  text: string;             // 玩家可見的主張句
  status: ClaimStatus;
  sourceKind: 'record' | 'prediction' | 'inference';
  evidence: EvidenceLink[];
  boundary: Boundary;
  madeAt: Tick;
  statusAt: Tick;
  repairs: RepairRecord[];
  struck: boolean;          // true = 這一行已被劃掉，但**仍然顯示**
}

interface EvidenceLink {
  evidenceId: string;       // E1..E5 / F1..F5 / G1..G5 / K1..K5 / J1..J4 / S1..S7
  role: 'supports' | 'bounds';
  addedAt: Tick;
}

interface Boundary {
  conditions: string[];     // 成立條件，例：['近似直線穩速','無額外水平推拉']
  notSupported: string[];   // 明確不支持的事，例：['地球正在運動']
  unmeasured: string[];     // 明確沒量到的東西，例：['垂直落下一秒的距離']
}

interface RepairRecord {
  at: Tick;
  action: 'withdraw' | 'narrow' | 'attach-source';
  fromStatus: ClaimStatus;
  toStatus: ClaimStatus;
  reason: string;           // 玩家可見
}
```

**不變式**
- `sourceKind === 'prediction'` 的主張，**初始且持續為 `pending`**，直到有 `role:'supports'` 且 `evidenceId` 屬於「實驗紀錄類」的連結被加入。（這實作了「懸置」：ch2 F1 船桅預測、ch4 K0 切線來源紙。）
- `status === 'repaired'` ⟹ `repairs.length >= 1` 且 `struck === true`。
- **被劃掉的主張永不刪除**（對應「越界的話必須留在紙上被看見」的敘事倫理）。

### 1.6 掛載點

```ts
interface GameState {
  schemaVersion: number;    // ch1-3,5 由 1 → 3；ch4 由 2 → 3（統一版號，見 §4）
  chapter: ChapterId;
  cursor: { scene: string; node: string };
  mode: 'explore' | 'scholar';

  reputation: Reputation;                 // L1，全章
  alignment?: Alignment;                  // L2，僅 ch1/ch2/ch5
  pressure?: Record<string, PressureObject>; // L3，僅 ch3/ch4
  claims: Record<string, Claim>;          // L4，全章

  evidence: Record<string, boolean>;      // 既有，不動
  lab: unknown;                           // 既有章別工作台狀態，不動
  flags: Record<string, string>;          // 既有
  transcript: unknown[];                  // 既有
  eventLog: unknown[];                    // 既有
  ended: boolean;
  migration?: unknown;                    // ch4 既有
}
```

> **重要**：`lab`、`evidence`、`transcript`、`eventLog` 一律**不動**。新四層是**加法**，不是重構。這是把風險壓到最低的關鍵決定。

## 2. 狀態轉移規則

### 2.1 主張四態轉移表

| # | 目前態 | 觸發動作 | 前置條件 | 新態 | 副作用 |
|---|---|---|---|---|---|
| T1 | （無） | `declareClaim(id, text, sourceKind='record', boundary)` | — | `pending` | 建立 Claim，`madeAt=tick()` |
| T2 | （無） | `declareClaim(..., sourceKind='prediction', ...)` | — | `pending` | 同上；**不因後續推論而自動錨定** |
| T3 | `pending` | `assertClaim(id, evidenceIds)` | `covers(claim, evidenceIds) === true` | `anchored` | 建立 EvidenceLink；**rep 不變** |
| T4 | `pending` | `assertClaim(id, evidenceIds)` | `covers(...) === false` **且**該節點是邊界決策點 | `overreach` | rep **−1**（`kind:'overreach'`）；`locked = (value===0)` |
| T5 | `pending` | `assertClaim(id, evidenceIds)` | `covers(...) === false` 且**非**邊界決策點 | `pending`（不變） | **rep 不變**；回饋「這批紙還說不到這裡」，退回原節點 |
| T6 | `pending` | 選擇了守界選項（該節點另有可用的越界選項） | — | `anchored` | rep **+1**（`kind:'bounded-choice'`），每個決策點只給一次 |
| T7 | `overreach` | `repairClaim(id, 'withdraw'\|'narrow', reason)` | — | `repaired` | `struck=true`；rep **+1**（`kind:'repair'`）；`locked=false` |
| T8 | `pending` | `linkEvidence(id, evidenceId, 'supports')` 且 evidence 屬紀錄類 | `sourceKind==='prediction'` | `anchored` | **懸置兌現**（ch2 F1 在 ch3 被驗證） |
| T9 | `anchored` | `revokeEvidence(evidenceId)`（上游證據失效） | 該 claim 依賴此證據 | `pending` | 記錄 PressureEvent／RepEvent 皆無；只降態 |
| T10 | 任意 | `narrowBoundary(id, boundary)` | — | 態不變 | 更新 Boundary，記入 repairs（`action:'narrow'`） |

**`covers()` 判定函式**（唯一的正確性核心）

```
function covers(claim, evidenceIds):
    linked = evidenceIds 對應的證據
    # 1. 每一個「主張要素」都必須有支持
    for element in claim.requiredElements:        # 由內容資料提供，見 §3
        if not any(e supports element for e in linked): return false
    # 2. 主張不得觸碰任何 notSupported 條目
    for ns in claim.boundary.notSupported:
        if claim.text mentions ns: return false   # 由內容資料以 id 比對，不做 NLP
    # 3. 主張的條件必須是所有 linked 證據條件的交集之內
    if not claim.boundary.conditions ⊆ ∩(e.conditions for e in linked): return false
    return true
```

> **注意**：`covers()` **不做自然語言判讀**。`requiredElements` 與 `notSupported` 都是內容資料裡的 **id 清單**，由劇本作者填寫。引擎只做集合運算。

### 2.2 信譽轉移（唯一入口）

```
function applyRepFromClaim(state, claimId, kind):
    if kind not in {'overreach','bounded-choice','repair'}: return   # 其他一律不動 rep
    delta = (kind === 'overreach') ? -1 : +1
    if alreadyAwarded(state, nodeKey, kind): return                  # 每個決策點只給一次
    push RepEvent{at:tick(), delta, reason, nodeKey, claimId, kind}
    state.reputation.value = clamp(3 + Σdelta, 0, 5)
    state.reputation.locked = (state.reputation.value === 0)
```

**明文禁止**：任何 `labAction`、實驗失敗、配置錯誤、答錯物理題**都不得呼叫此函式**。

### 2.3 對位轉移（僅辯論章）

```
on enterDebate():      alignment = {value:5, active:true, round:round+1, misfiles:[...keep]}
on showEvidence(e,t):  ok = isCorrectPairing(e,t)
                       push MisfileEvent{at,evidenceId:e,targetId:t,ok}
                       if !ok: alignment.value -= 1
                       if alignment.value === 0: goto debriefScene   # 不動 reputation
on exitDebate(win):    alignment.active = false
```

### 2.4 守門人實物轉移（僅 ch3／ch4）

```
# ch3 簽名欄
on conditionVerified(cid):  satisfied ∪= {cid}; push PressureEvent{'condition-met'}
on conditionBroken(cid):    satisfied -= {cid}; push PressureEvent{'condition-revoked'}
on requestSignature():      if satisfied ⊇ requiredConditions: signedAt = tick(); push 'signed'
                            else: push 'refused' (detail = 缺哪幾項)   # 不動 rep

# ch4 印刷空檔
on submitProof(kind):       if remaining === 0: reject('no-window')
                            remaining -= 1; consumedAt.push(tick()); push 'consumed'
on deferPress(reason):      push PressureEvent{'refused', detail:reason}  # 不消耗空檔，但留痕
```

## 3. 各章綁定

### 3.0 內容資料新增欄位（所有章共用）

在 `scenes*.json` 的 **choice option** 上新增選用欄位：

```jsonc
{
  "id": "bounded",
  "text": "……",
  "next": "xok",
  "claim": {                      // 新增：這個選項是一次主張
    "id": "ch3.G1",
    "assert": true,               // true=assertClaim, false=declareClaim
    "evidence": ["G1"],
    "boundaryPoint": true         // 關鍵：此節點是「邊界決策點」→ rep 才會動
  }
}
```

在證據定義（各章 `evidenceNames`／`evidenceSummaries` 旁）新增：

```jsonc
"G1": {
  "name": "航船桅頂落石",
  "elements": ["stone-keeps-forward"],           // 它能支持的要素 id
  "conditions": ["near-steady", "no-extra-push"],
  "notSupported": ["earth-moves"],
  "unmeasured": ["earth-rotation"]
}
```

> **邊界決策點的判準**：該 choice 節點**同時**提供至少一個越界選項與一個守界選項。工程師不需判斷語意——由 `boundaryPoint: true` 明示。

## 4. 存檔遷移

### 4.1 版本策略

**v1.2 全面改寫——原本「統一升到 3」的方案作廢，理由有二：**

**(a) 版號 3 已經被占用。** 實查 `src/sanitize.js`：ch2／ch3／ch5 要求 `schemaVersion === 1`、ch4 要求 `=== 2`，另有兩處 `schemaVersion !== 3` 檢查（其一的 cursor 樣式為 `/^B|^SC-R1/`），且 ch1 走 `schemaVersion !== SAVE_SCHEMA`。也就是**各章版號本來就不一致，而 3 已有既有語義**。若四層也叫 3，同一個版號會有兩種意思，sanitizer 無法分辨。

**(b) 四層是加法，不該去動各章既有版號。**（這與本規格 §1.6 的原則一致。）

**新方案：不動任何 `schemaVersion`，改用獨立欄位。**

```ts
interface GameState {
  schemaVersion: number;   // ← 各章維持現況（ch1 = SAVE_SCHEMA、ch2/3/5 = 1、ch4 = 2），不動
  claimsVersion?: 1;       // ← 新增。缺此欄 = 尚未套用四層；有 = 已套用
  reputation?: Reputation;
  alignment?: Alignment;
  pressure?: Record<string, PressureObject>;
  claims?: Record<string, Claim>;
}
```

**好處**：舊存檔在 `claimsVersion` 缺席時照舊走既有 sanitizer；四層只在該欄存在時額外驗證。**不需要五章齊步升版，也不需要 sanitizer 雙分支。** P3 因此可以逐章上線。

### 4.2 映射規則（逐欄）

| 舊欄位 | 新欄位 | 規則 |
|---|---|---|
| `state.rep`（0..5） | `reputation.value` | 直接複製 |
| `state.flags.repLocked` | `reputation.locked` | `!!flags.repLocked`；並刪除該 flag |
| `eventLog` 中 `{t:'rep'}` 事件 | `reputation.history` | 逐筆轉為 `RepEvent`，`kind` 依 `delta` 判定：`-1→'overreach'`、`+1→'bounded-choice'`（若該 nodeKey 屬修復場則 `'repair'`） |
| **無 rep 事件的舊檔** | `reputation.history` | **v1.2 作廢原規則。禁止合成種子事件。** 詳見下方「§4.2a 為什麼不能合成」 |
| 舊 persuasion 值（**位置待確認，見 §7 Q1**） | `alignment.value` | 若章別 ∈ {ch1,ch2,ch5} 則複製，否則丟棄；`active=false`、`round=1`、`misfiles=[]` |
| `state.evidence[Ex]===true` | `claims['chN.Ex']` | 建立 `status:'anchored'`、`sourceKind:'record'`、`evidence:[{evidenceId:Ex,role:'supports'}]`、`boundary` 由內容資料查表填入 |

### 4.2a 為什麼不能合成 rep 歷史（v1.2 新增，codex 指出，我同意）

原 v1.0 寫「無 rep 事件的舊檔 → 合成一筆種子事件使重算式成立」。**這是一個洗白漏洞**，與我在 P1 抓到的「旗標式判定可用不同航次拼出假達成」是同一類：**遷移不得製造讓驗證通過的證據**。一份手改 `rep=5` 但沒有任何支持紀錄的偽造存檔，會因為遷移替它補上假歷史而通過檢查。

**而且合成根本沒有必要**——實查 `narrative.js:104` 的 `applyRep()`：

```js
function applyRep(state, delta, sourceId, reason) {
  ...
  var event = { t: "rep", d: delta, from: before, to: state.rep, at: sourceId };
  state.eventLog.push(event);          // ← 每一次 rep 變動都必然入 eventLog
}
```

**信譽只要動過，就一定留下事件。** 所以「沒有 rep 事件」只有一個合法解釋：**玩家從未觸發過任何邊界決策點，rep 必然仍是初始值 3。**

**正確規則（取代合成）**

```
if (eventLog 有 rep 事件):
    history = 逐筆轉換（保留原 source 字串）
    expected = clamp(3 + Σdelta, 0, 5)
    if (state.rep !== expected) → 拒絕匯入（「信譽與紀錄不一致」）
else:
    if (state.rep === 3) → history = []   ✅ 合法：從未觸發過決策點
    else                 → 拒絕匯入（「信譽偏離初始值但沒有任何紀錄」）
```

**唯一的例外處理**：若確實存在「早於 rep 事件記錄機制」的更舊存檔格式，**以明列的 allowlist 逐一處理**（比照 ch4 遷移對 205 個 legacy cursor 的逐一鎖定做法），**不得用一條通則替所有無紀錄存檔補歷史**。若目前沒有這種格式，就不要預留這條路。

（附帶：`applyRepOnce()`（`narrative.js:115`）已用 `event.at === sourceId` 去重，這正是本規格 T-04「同一決策點不重複給分」所要求的行為——**該機制已存在，不需新寫**。）

### 4.3 遷移順序（不可調換）

```
raw text → migrateV1toV3 / migrateV2toV3 → Narrative.loadSave → sanitizeImportN
```
與 ch4 現行「先遷移、再 load、最後 sanitize」一致（`chapter-ui.js` 的 `inspectSaveText` 已有此順序斷言，勿破壞）。

### 4.4 失敗處理

- 遷移失敗 → 回傳可讀原因、**逐字保留原始存檔文字**（沿用 ch4 `report.backupText` 機制），不得靜默重開新局。
- 重算不符（如 `reputation.value ≠ clamp(3+Σdelta)`）→ 視為**偽造**，拒絕匯入。
