# 四律脈絡交接|「文字被壓縮」這件事的來龍去脈與現存缺口

**Claude → Sol**|**日期**:2026-07-28|**緣起**:總監問「我們前面修的『文字不要壓縮』有寫進 skill 嗎?」
**性質**:R0 唯讀交接,零檔案修改。**不是要你把規則寫回 skill**——正好相反,這份是要告訴你規則在哪、路由撈不撈得到、以及**還缺一個機械檢查**。

---

## 一、總監當初反應的問題(原話與時序)

不是抽象的「文字不好」,是四次具體的讀不懂,分四次冒出來:

| # | 總監原話 | 我當時的錯誤反應 |
|---|---|---|
| 1 | 「**什麼抽屜!?ＸＤ**」(第四章 K4 對帳桌「三個抽屜都打開」) | 以為只是用詞問題,改詞 |
| 2 | 「這邊什麼**共轉渦旋** 我也看不懂 所以只個後面要選要按都看不懂也不知道要幹嘛」 | 以為是術語問題,白話化 |
| 3 | 「這邊的**合**不合怎麼知道的」(對帳桌的判定) | 以為是說明不足,補說明 |
| 4 | 「我覺得第四章劇本**有點乾**」「**突然進入軌道工作坊太奇怪**」 | 以為是節奏問題,想加台詞 |

**四次我都改了症狀,沒找到病。**直到第三方審查給了一份「壓縮率診斷」,總監的反應是:

> **「!!我終於知道我一直覺得怪怪的感覺了!!!」**

那是分水嶺——他一直感覺到的東西,終於被命名了。

## 二、根因:是流程壓的,不是文筆差

診斷出來的因果鏈是這樣:

```
設計文件(一節=一個機制)
→ 節點級劇本(一節點=一句話)
→ runtime(一句話=一個 function 回傳)
```

**每一層都在壓,而且每一層都「沒錯」。**最後產出的東西「資訊完整、場面不完整」:玩家知道發生了什麼,但沒看見它怎麼發生。

第三章的實測數字把這件事釘死了:

| 章 | 場數 | 節點 | **每節點字數** |
|---|---|---|---|
| ch1 | **23** | 218 | 27 |
| ch2 | 18 | 157 | 30 |
| **ch3(展開前)** | **8** | **72** | **33(全系列最高)** |
| ch4 | 14 | 205 | 24 |

**ch3 的句子是全系列最長的,場數卻只有 ch1 的三分之一。**所以病灶不是「句子太短」——是**拍子整段不存在**。我原本的假設(以為和 ch4 一樣是句子被壓縮)被自己的數據推翻。

具體長什麼樣:第三章 `C0-2` 借船那場,一個陌生學者要借商船甲板扔石頭,**四句話就借到了**;`C1-1→C3-1` 之間,三輪碼頭質詢**結束完全沒有演出**,直接跳到「三輪質詢結束後」;`CE-1` 伽利略的死訊只有**一句 stage 加一句心聲**,而 ch1、ch2 花了兩章建立那段關係。

## 三、解法:四律入法源,不是入 skill

### 3.1 立條文(2026-07-27,總監裁決「兩個都好」)

`02_設計/發現之前_設計原則手冊_v0.1.md` **K 節**:

- **63 三拍展開律**——凡產出紀錄或斷言的節點,不得只有結果句;至少三拍:誰先發現異常 → 別人怎麼回應 → 現場怎麼確認。
- **64 認知停頓**、**65 角色反應權**、**66 轉場要有「不得不」**。
- **66-bis 語言溫差律**——古人可以短,旅人不行。並附一句判準:**「精簡不等於留白,只有讀者接得住的省略才叫留白。」**

### 3.2 立跨章對照法源(2026-07-28)

`02_設計/發現之前_跨章規格_旅人聲線與章際接縫_v1.0_Claude_20260728.md`,**§六**是八項機械檢查,**§6.1** 就是上面那張壓縮率診斷表的用法:

> 不要用「總字數」判斷一章夠不夠飽滿——要用**場數**與**每節點字數**一起看。每節點字數遠高於 ch1 基準(27)=拍子被壓縮的訊號。

### 3.3 落地驗證(ch3 已進 runtime)

`scenes3.json` **8 場 72 節點 → 10 場 209 節點**。手法是只插新節點、不動既有 id,所以**免存檔遷移**。補的都是缺的拍,不是加形容詞——例如 `C1-1` 加了一拍:旅人低頭寫字、抬頭發現碼頭在後退,**讓玩家用身體先做一次本章要證的事,而且沒發現**。

## 四、為什麼 skill 裡查不到「四律」兩個字(這是對的)

我實跑過:v3 `SKILL.md` 與 `OVERLAY-claude.md` 對「四律/展開/壓縮/66-bis/溫差」的命中數 **全部是 0**。

**這符合你 v2 對我開的 B-1**——當時我把 16 條規則複述進 skill,還抄出「三追問」的漂移。v3 的路由器設計是對的。

而且路由**確實會撈到**。實測:

```bash
route --task narrative --chapter ch5 --phase write --mode TO-BE --lane R2 --target-label WP-CH5-SCRIPT
```

輸出含三份 constraint:`core.design-principles`(手冊,K 節在裡面)、`narrative.cross-chapter`(跨章規格 v1.0)、`narrative.dialogue-rules`。**規則會到寫稿者手上,只是透過路由,不是抄在 skill。**

## 五、真正的缺口:四律是全系列唯一沒有機械檢查的規則層

| 規則層 | 有無機械檢查 |
|---|---|
| 法源路徑存在/追蹤/鏡像同步 | ✅ `skill_guard.py validate` |
| 交付狀態一致性 | ✅ `check-report`(你 v3.0.3 新增) |
| runtime 契約(證據、存檔、遷移、對話框化) | ✅ `npm test` 129 條 |
| **四律與台詞紀律** | ❌ **零** |

**這一條用你自己的標準看很刺眼**:你在 v3 立了「新增契約至少證明一次『保護行為被拔除時會紅』」;而 ch5 展開時如果我又把某場壓成一句話、或旅人連兩場零句、或心聲寫出禁詞——**沒有任何東西會紅**。

我在 ch3 展開時是臨時寫 python 掃的,而且**當場誤判過兩次**「金句超額」——因為掃描器沒排除設計註記和場名。那個掃描器隨手就丟了,下次得重寫,而且會再犯同一個錯。這正是 skill 要消滅的「每次重建流程」成本。

### 建議(不急,排在 v3 啟用之後)

`skill_guard.py check-narrative --scenes <scenes*.json> 或 --draft <展開稿.md> --chapter chN`,跑跨章規格 §六八項:

| # | 檢查 | 可機械化程度 |
|---|---|---|
| 1 | 旅人在場(每場 ≥1 句;連續 2 場為零=fail) | 高 |
| 2 | 逐章禁詞(含心聲) | 高 |
| 3 | 金句配額(每場對仗/判詞 ≤1) | 中——**必須排除註記、表格、場名**,我踩過 |
| 4 | 章際接縫逐字(以 runtime 為準) | 高 |
| 8 | 每節點字數 vs ch1 基準 27(超出=warning) | 高 |
| 5/6/7 | 不會老的鏈、史實查證、虛構標示 | 低,維持人工 |

輸出建議走 warning 而非 blocker(文學判斷不該硬擋),但**要能反向轉紅**:故意刪掉一場的旅人台詞,第 1 項必須報。

**歸屬**:這是 skill 套件工具,`skill_guard.py` 是你的施工路徑;我可以提供八項的判準細節與我踩過的誤判案例(尤其第 3 項的排除規則)。依 v3 §3.2,我提供修法不構成接手——**要不要做、誰做,請總監裁**。
