# 《發現之前》旅人對話與資料密度｜介面／程式審核（Sol）

**日期**：2026-07-20  
**性質**：總監實玩回饋之校準審核；不計內容審稿輪數；本文件不修改 Claude 程式或第一章凍結基線

## 結論

1. 總監判斷正確：目前旅人發言只有名牌變色＋單一左槽肖像壓暗，**不是真正的左右交替對話構圖**。
2. 旅人剪影資產確實存在，而且保持無臉、無明顯性別；它可以上場，不必在「有固定臉」和「完全沒有視覺角色」間二選一。
3. 總監對資料欄位的擔心成立：天數在引擎中只有累計，沒有硬上限；實驗紀錄可無限新增，不能以「全章頂多十來筆」作 UI 防爆保證。
4. 設計原則手冊 v0.1 的方向正確；須補強一條通用區分：**資料持久性與資料可見密度是兩件事。紀錄不可刪，不代表必須同時全部展開。**

| Security | A | 本輪純本機表現層與確定性資料；未見外部輸入執行、秘密或新增注入面 |

## B-1｜「誰在說話」已加線索，但空間語法仍未完成

### 可驗證依據

- `greybox/src/stage-ui.js:117–155`：只有一個 `#bust`；旅人預設只對它加 `.dim`，A/B 開啟後也只是把同一槽換成旅人剪影。
- `greybox/src/stage-ui.js:228–231`：旅人名牌改靛藍、文字 class 改 player，這部分正確。
- `greybox/stage.html:107–126`：肖像槽固定在左側；沒有右槽或 speaker-side schema。
- `greybox/tests/run-node.mjs:177–209`：測試保護「旅人不得進一般肖像映射」，但沒有驗證名牌／明暗切換，也把暫定的「旅人無肖像」鎖得比真正設計原則更死。

### 介面判斷

名牌文字＋顏色＋明暗已符合最低無障礙要求，色彩對比也足夠：

- 旅人靛藍 `#244a63`／淺字 `#f3e9d5`：約 7.80:1。
- NPC 棕 `#7a4b2a`／淺字 `#f3e9d5`：約 6.08:1。

但快速來回對話時，玩家首先讀的是人物位置與臉，再讀名字。現在人物永遠留在左側，只是變暗；總監仍感到不直觀，表示最低線索雖合格，舞台語法沒有合格。

### 建議：改成左右雙槽，不再把所有角色塞進同一格

1. 新增 `#bustLeft`、`#bustRight`，由場景／資產資料決定 preferred side；不得 CSS 鏡像。
2. 伽利略肖像本身朝左，放**右側**；辛普里奧肖像朝右，放**左側**。
3. 旅人使用無臉剪影站在對手相反側：
   - 左側旅人：沿用 `dialogue_traveler_silhouette.webp`（朝右）。
   - 右側旅人：新增 `dialogue_traveler_silhouette_right.webp`（重新生成、朝左，不是鏡像）。
4. 旅人說話：旅人槽亮、NPC 槽暗；NPC 說話反之。兩者都保留名字與名牌色，形成「位置＋明暗＋文字／色彩」四線索。
5. 旁白／系統行：兩槽都降亮，不假裝任何角色在發言。
6. 844×390 手機橫屏：只保留 active portrait；inactive portrait 可隱藏或縮成低透明局部輪廓，文字區不得被雙肖像夾窄。
7. 1280×720 桌機：可讓前一位講者以 35–45% 亮度留場，形成真正的對話關係。

### 旅人是否因此變成固定角色？

不會。現有剪影只呈現「有人在場」：背面、包頭、高領、無皮膚、無髮型、無臉、無性別身形；它是空間指標，不是替玩家捏臉。建議第一章預設開啟雙剪影槽，保留 `?travelerBust=0` 作撤回／A-B，而不是預設關閉後等玩家自己發現參數。

## B-2｜資料不會被刪，但目前確實可以無限塞滿

### 可驗證依據

- `greybox/src/engine.js:52–69`：每次 `runExperiment` 只增加 `days` 並 push 新 run；沒有 max day、deadline 或 run count 守衛。
- `greybox/src/chapter-ui.js:205–228`：每次 render 會把所有 runs／claims 全部建立為 table rows。
- `greybox/src/stage-ui.js:339–354`：只有使用者勾選後，異配置 row 才加 `.offconfig` 淡出；未勾選時全表展開。
- `greybox/src/stage-ui.js:382–400`：旅人筆記快照還會 clone 完整表格，資料越多，筆記頁也跟著越長。

因此「天數成本天然限制筆數」是節奏誘因，不是程式保證。玩家可以故意或因不懂而跑二十、三十次。

### 建議：不可刪，但要分組、摺疊、永遠保留選中項

不用改引擎，也不用刪任何 state：

1. 以「配置」分組；summary 顯示配置、筆數、是否已有成立主張。
2. 未認證配置預設展開最新 3 筆；已認證配置預設摺疊，只留摘要與最後一筆。
3. 被勾選的 run 永遠顯示，不得因摺疊消失。
4. 提供「展開全部 N 筆」，使用原生 `<details>/<summary>` 或等效鍵盤可操作控制。
5. 旅人筆記快照使用相同 grouping，不再 clone 一張無限長的完整表。
6. 手機橫屏優先顯示 run #、配置、四段與選取；天數可收進 row detail，避免橫向爆寬。

### 必補測試

1. 連跑 20 次後，state／serialize 仍保留 20 筆。
2. 預設可見 row 數受控，但展開後 20 筆皆可取得。
3. 勾選的 run 在摺疊／換配置／重 render 後仍可見且仍勾選。
4. 已認證配置摺疊不影響 `judge`／`assert` 的 selection 守衛。
5. summary 含配置與筆數，鍵盤可展開，不能只靠 icon。

## C-1｜設計原則手冊應保留，但只沉澱「可跨章」的原則

`02_設計/發現之前_設計原則手冊_v0.1.md` 的 23 條有來源、有位階、能回指事故，值得採納。尤其以下五條應成為每章開工 checklist：

- UI 可見性與引擎守衛同源。
- 年代／物理可機械判定者入測試。
- 點陣圖不承載物理資訊。
- 狀態訊號至少雙線索。
- 新系統先獨立切片、保留基準。

但「旅人一定有／沒有剪影」屬呈現方案，先留在裁決紀錄與 A/B，不宜立刻升格系列鐵律。真正可沉澱的是：

> **說話輪替先用空間、明暗與文字建立，不只換顏色；玩家化身若需視覺佔位，使用不替玩家決定臉、性別與身份的中性輪廓。**

另建議把原則 4 補成：

> **紀錄不可刪，但介面可以分組、篩選、摺疊與分頁；保存完整性和同時可見量必須分開設計。**
