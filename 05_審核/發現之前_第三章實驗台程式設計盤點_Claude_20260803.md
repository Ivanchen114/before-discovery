## 二、🟢 先講做對的部分（重構時不要動）

### 2.1 `dossierMotion` 是真運動學，不是查表

```js
function dossierMotion(stage, vesselId, speedBand, forceBand, releaseVelocity, t) {
  var selectedV0 = DOSSIER_SPEED_VALUES[speedBand] || DOSSIER_SPEED_VALUES.mid;
  var v0 = 0, a = 0;
  if (stage === "steady") v0 = selectedV0;
  if (stage === "depart") { a = dossierAcceleration(vesselId, forceBand); v0 = selectedV0; }
  if (stage === "brake")  { v0 = selectedV0; a = -dossierAcceleration(vesselId, forceBand); }
  var mastX  = v0 * t + 0.5 * a * t * t;
  var stoneX = (v0 + releaseVelocity) * t;
  return { mastX, stoneX, relativeX: stoneX - mastX };
}
```

而 `buildDossierRecord` 把玩家的每一個選擇都接進去：
- **船隻** → 桅高（7／12／18 m）→ `fallTime = sqrt(2h/g)`，並且 → 硬加速度（0.70／0.57／0.50）
- **力度帶** → `soft = hard × 0.58`
- **放手法** → `DOSSIER_RELEASE_DV`：latch `[0, 0.01, -0.008]`／string `[0.03,-0.04,0.02]`／hand `[0.28,-0.22,0.05]`
- **鼓速** → `dt` 與讀值誤差（slow 0.70/0.02、mid 0.39/0.02、fast 0.35/**0.12**）
- 三位記錄者各有一組確定性讀值誤差序列，並依原紙編號輪替起點

**這是全系列（含第四章）最完整的一個可組態物理模型。** 玩家換一艘船、換一種放手法，紙上的數字真的會不一樣，而且是可重現的（零 RNG）。

### 2.2 船況分類是「從玩家生成的紙上讀出來」，不是查表

```js
function dossierReclassifyRecord(record) {
  var shoreGaps = dossierGapsFromShorePaper(record);   // 從實際 beats 反推間距
  var result = dossierClassificationFromGaps(shoreGaps, paperError);
  ...
}
```

而且 `dossierClassificationFromGaps` **會誠實地回「未分類」**：
```js
if (error > 0.08) return unclassified;      // 快鼓：讀值誤差蓋過逐拍差異
...
// 註解明說：「不可因閾值跟著誤差放寬，反把正在改變速度的船誤判成穩速」
```

**⭐ 快鼓是一個真的、有標示的取捨。** 選 `fast` → `error = 0.12 > 0.08` → **每一張紙都必然未分類**，等於白花天數。而 `quality` 字串事先寫明「點較密，但岸上來不及點準；單張原紙不足以判斷船速趨勢」，`chapter-ui.js:3459` 會把它印在原紙上。**這正是第四章缺的那種「失敗有資訊、有代價、但事先講清楚」的設計。**

### 2.3 斷言檢查真的在檢查實驗設計

`dossierSelectedSourcesCheck`（:1896）不是比對答案字串，是逐條驗設計：

| 檢查 | 程式 |
|---|---|
| 至少三張原紙 | `rows.length < 3` |
| 放手法必須對（S1 要 hand、其餘要 latch） | `r.release !== (assertionId === "S1" ? "hand" : "latch")` |
| 必須有看得見的岸上速度紙 | `dossierHasVisibleShoreSpeedPaper(r)` |
| 同石同高 | `!r.sameStone \|\| !r.sameHeight` |
| **跨船況比較時所有設定必須同指紋** | `sameSetupAcrossMotion()` |
| **S1 必須真的量到散布** | `max(handOffsets) - min(handOffsets) < 0.20` → `dossier-spread-too-small` |
| A3／S4 每個船況各要三張乾淨紙 | `cleanRows("depart","正在變快","aft").length < 3` … |

**玩家沒辦法用一堆雜紙湊出斷言。** 這在第四章的對帳桌是沒有的（那裡蓋章只比對硬表）。

### 2.4 ⭐ 範圍選項由玩家自己的資料生成——全系列最好的一個機制

```js
function getDossierScopeOptions(d) {
  var testedVessels = dossierTestedVesselIds(d);
  if (testedNames.length > 1) options.push({ choice: "one-tested-vessel", ... });
  options.push({ choice: "tested-vessels-only", ... });
  if (testedNames.length > 1 && dossierShowsHeightOffsetTrend(d))
    options.push({ choice: "height-causes-offset",
      text: "這句話寫在桅高上：小艇偏得較少，大船偏得較多，所以偏移大小由桅高決定。" });
  options.push({ choice: "all-vessels", ... });
}
```

**「桅高決定偏移」這個誘答，只有在玩家真的測過兩艘以上的船、而且他自己的資料剛好呈現單調趨勢時才會出現。**

而那個趨勢是真的：`relativeX = -½at²`、`t² = 2h/g` → `offset = -a·h/g`
- 小艇 0.70×7/9.8 = 0.50
- 船長的船 0.57×12/9.8 = 0.70
- 大貨船 0.50×18/9.8 = 0.92

單調遞增。**誘答從玩家自己的資料裡長出來，而且它錯得很細緻**（真正的變因是 `a` 與 `h` 同時在動，不是「桅高決定」）。這比第四章任何一個誘答都高明。

### 2.5 天數是真資源

## 三、🔴 F1（P1，潛伏的資料破壞）：`judgeDossierBlind` 會把玩家的六張船艙紙換成兩張固定紙

### 問題

```js
function judgeDossierBlind(state0, choice) {
  ...
  d.blind.records = clone(DOSSIER_CABIN_RECORDS);   // ← 覆蓋
  refreshDossierCandidates(d);
  return { state: s, ok: true, unsealed: true };
}
```

`DOSSIER_CABIN_RECORDS` 只有兩筆，id 是 **`"C-dock"`** 與 **`"C-steady"`**。

而 A2 的驗證要求（`dossierSelectedSourcesCheck`:1937）：
```js
if (picked.length < 6) return { ok:false, reason:"dossier-too-few-records" };
if (picked.some(function (id) { return !/^C\d+$/.test(id); }))
  return { ok:false, reason:"dossier-source-mismatch" };
...
if (cabinDock.length < 3 || cabinSteady.length < 3)
  return { ok:false, reason:"dossier-comparison-missing" };
```

- 需要 **≥6 筆**，覆蓋後只剩 **2 筆**
- id 必須符合 **`/^C\d+$/`**（`C1`、`C2`…），而 `"C-dock"`／`"C-steady"` **不符合**
- 需要 dock ≥3、steady ≥3，覆蓋後各只剩 1

**結果：一旦呼叫，A2 就永久無法成立，而且玩家做過的六趟船艙對照全部消失。**

### 可達性（誠實標示）

`grep` 顯示 **`chapter-ui.js` 完全沒有呼叫 `judgeDossierBlind` 或 `runDossierBlind`**，所以**正常遊玩碰不到**。但它掛在 `api` 的公開匯出（engine3.js:3124），存檔遷移、測試、主控台或未來任何 UI 接線都可能踩到。

**所以我把它評為 P1（潛伏），不是 P0（線上壞掉）。** 但它是本次盤點裡唯一會**刪掉玩家資料**的東西，優先度應排在所有體驗改善之前。

### 建議

最省：讓它不再覆蓋。
```js
function judgeDossierBlind(state0, choice) {
  var s = ensureNewFields(clone(state0)), d = s.caseFile.dossier;
  if (!d.blind.ran) return err(state0, "dossier-blind-required");
  var ok = choice === "indistinguishable";
  d.blind.attempts.push({ kind: "judgment", choice: choice, ok: ok });
  if (!ok) return { state: s, ok: false, reason: "local-traces-overread" };
  d.blind.judgment = choice;
  d.blind.unsealed = true;
  /* 移除：d.blind.records = clone(DOSSIER_CABIN_RECORDS);
     舊存檔若真的沒有紀錄才補，且要用合法 id。 */
  if (!d.blind.records.length) {
    d.blind.records = clone(DOSSIER_CABIN_RECORDS).map(function (row, i) {
      row.id = "C" + (i + 1);
      return row;
    });
  }
  refreshDossierCandidates(d);
  return { state: s, ok: true, unsealed: true };
}
```
更省：既然 UI 不用，直接從 `api` 移除 `judgeDossierBlind` / `runDossierBlind`，只留 `runDossierCabinComparison` / `runDossierCabinSeries`。

**順帶**：即使補上合法 id，兩筆仍不足 6 筆，A2 還是不會過。所以上面的 fallback 只能救「還沒做過任何船艙對照」的存檔，不能救已經被覆蓋的。若已有存檔中招，需要另寫遷移。

### 問題

`setDossierP3Premise` 在玩家**只選了來源**時，就把後兩步標記為完成：


`alignDossierPapers` 又設一次（:2896）：

而 UI（`chapter-ui.js:4718`）只走三步：

```js
if (db.p3.source) ship3DossierP3PaperMath(work, d, false);

else if (!db.p3.aligned) {        /* 對鼓點 */ }

```

**所以 `step: "question"` 與 `step: "concept"` 這兩個判斷拍，UI 從來不呈現，引擎也預先給了通過。**

### 被埋掉的是什麼

引擎裡兩題都完整寫好了，含三個選項與各自的反駁：

**question 拍**（要玩家判斷「比較兩張紙之前該先確定什麼」）
| 選項 | 玩家台詞 |
|---|---|
| `same-time-transform` ✓ | 「先確定兩張紙記的是同一事件、同一時刻，再比較位置。」 |
| `trust-recorder` ✗ | 「先決定岸上和船上哪一個人比較可靠。」 |
| `pick-straight` ✗ | 「先選看起來比較平順的那條路。」 |
| 反駁 | 維達爾船長：「別先挑誰可靠。先證明兩張紙記的是同一時刻。」 |

**concept 拍**（要玩家判斷「兩張紙為什麼不一樣」）
| 選項 | 玩家台詞 |
|---|---|
| `reference` ✓ | 「兩張紙量的是同一顆石頭；不同的是各自拿碼頭或桅杆當起點。」 |
| `paper-angle` ✗ | 「兩張紙只是擺放角度不同。」 |
| `force` ✗ | 「兩張紙上的石頭受了不同的力。」 |
| 反駁 | 商人：（指著兩張條件欄）「石頭、放手和船況都相同。你說的差別，記在哪一欄？」 |

**這兩題是第三柱的概念核心——「同一時刻」與「參考系」。** 現在玩家的路徑是：挑一筆雙紙 → 對鼓點 → 換原點，全程沒有被問過為什麼要對鼓點、也沒有被問過兩張紙差在哪。**動作做了，概念沒被要求說出來。**

而 `d.debate.lastReply` 的接續台詞其實是照三步寫的：
> 選完來源：「…現在先把同號鼓點對上。」
> （question 之後應該接）：「同一時刻先對上。現在告訴我：岸上和船上的人，各從哪裡開始量？」
> （concept 之後應該接）：「好。現在當著我們的面，把它們對上。」

**中間兩句在 runtime 永遠不會出現。**

### 建議（P1-A）

**引擎端**：把 `setDossierP3Premise` 的 `step === "source"` 分支裡的 `p3.question = true; p3.concept = true;` 改成 `false`（重選來源時本來就該重置），並把 `alignDossierPapers` 的那兩行刪掉；`alignDossierPapers` 開頭改為要求 `p3.question && p3.concept`：

```js
if (!p3.source) return err(state0, "dossier-p3-premise-required");
if (!p3.question || !p3.concept) return err(state0, "dossier-p3-premise-required");
```

**UI 端**：在 `4718` 的鏈上補兩個分支（約 20 行，樣式沿用既有的 `ship3Btn` 選項列）：
```js
if (!db.p3.source)        { /* 既有：選來源 */ }
else if (!db.p3.question) { /* 新增：三選一，doShip("setDossierP3Premise",{step:"question",choice:id}) */ }
else if (!db.p3.concept)  { /* 新增：三選一，step:"concept" */ }
else if (!db.p3.aligned)  { /* 既有：對鼓點 */ }
```

**成本很低（引擎 3 行、UI 約 20 行），而且不需要寫任何新內容——選項、玩家台詞、反駁、接續回應全部已經在 engine3.js 裡。** 這是本次盤點投報率最高的一項。

## 五、🟡 F3（P2，死分支）：`landing === "spread"` 不可能發生

```js
var offsets = [dossierMotion(...).relativeX];              // ← 永遠只有一個元素
var spread  = Math.max.apply(null, offsets) - Math.min.apply(null, offsets);   // ← 恆為 0
var landing = draft.release === "hand" && spread > 0.20 ? "spread" : ...       // ← 永遠 false
```

而 `dossierAppendFiledRecord`（:2149）還有一個永遠不會執行的消費端：
```js
landing: row.landing === "spread" ? "foot" : row.landing
```

### 判定

**不是 bug，是誤導性的遺留碼。** 徒手散布在設計上是**跨原紙**呈現的（每張紙一回，註解 :511-521 說得很清楚），而 S1 的驗證器也**正確地跨選取原紙量散布**（:1983）。所以功能是對的。

但任何人讀這段程式都會以為單張紙有模擬散布。建議二選一：
- **刪掉**：`var landing = meanOffset < -0.12 ? "aft" : (meanOffset > 0.12 ? "fore" : "foot");`，並移除 :2149 的映射。
- **或做實**：`runDossierSeries` 產生三回後，回填一個 `groupSpread` 到三張紙上，UI 在徒手系列的原紙卡上顯示「這三張的落點散開 0.78 公尺」。**後者其實比較好**——它讓 S1 的「散布」在收卷當下就看得見，而不是等到選來源時才被驗證器擋。

```js
  shoreGaps:      stage === "dock" ? [0,0,0] : [1.5,1.5,1.5],
  water: instrument === "drip" ? "水滴落在碗內標記附近" : ...,
  ball:  instrument === "toss" ? "石球直上拋起後落回手邊附近" : ...
};
```

全部是字串／陣列常值。**甲板實驗室辛苦選的船隻、速度帶、鼓速，在船艙站完全不影響任何東西**；船以 1.8 m/s 或 4.2 m/s 平駛，紙上寫的一模一樣。

### 判定

**教學上是對的**（本站的主張正是「停泊與走穩分不出來」，所以「看不出差別」是正確結果）。**但互動上，這一站是六次同樣的點擊。** 玩家只有兩個真決定：風的處理（`close-cabin` ✓）、儀器（drip／toss），之後就是 dock×3 + steady×3。

### 建議（低成本，二選一）

**(a) 讓速度帶進入船艙站，但結果仍然「分不出」——這才是真正的說服力。**
目前船艙紀錄不記船速。改成：`shoreGaps` 由 `DOSSIER_SPEED_VALUES[d.draft.speedBand]` 乘上 `dt` 算出（慢速 → `[0.7,0.7,0.7]`、快速 → `[1.6,1.6,1.6]`），`water`／`ball` 仍然不變。

> 玩家把船從最慢開到最快，岸紙上的間距翻了一倍多，**艙裡的水面和落球還是一樣**。
> 這比「六次都一樣」有力得多——它讓「分不出」變成玩家**主動試出來的**，而不是被告知的。

成本：`runDossierCabinSeries` 內約 5 行 + A2 驗證器加一條「至少測過兩種速度帶」（可選）。

**(b) 若不想動物理**：至少讓 UI 在六張紙旁顯示對應的岸紙速度，讓玩家看到「外面差這麼多、裡面一模一樣」的對比。純 UI，約 8 行。

## 七、其他觀察（不構成問題，但值得記）

### 7.1 P3 的 `beatBand === "mid"` 硬性要求

```js
function dossierIsP3Record(record) {
  return !!(record && record.filed === true &&
    record.stage === "steady" && record.classification === "近似穩速" &&
    record.release === "latch" && record.speedRecord === "beats" &&
    (record.beatBand || "mid") === "mid" && record.positionRecord === "dual" && ...);
}
```

慢鼓（`slow`）的紀錄即使一切合格，也**不能**用於第三柱。理由是註解 :157-161 說的：中拍要保證最短的 7 公尺桅杆也留下 ≥4 個位置點。合理，但**玩家用慢鼓做完一組完美的雙視角紙後，會發現它在辯論裡不能用，而沒有人告訴他為什麼**。

`chapter-ui.js:3472` 有同一份判斷（用來決定徽章），所以 UI 已經知道。**建議**：在原紙卡上，當紀錄其他條件都合格、只差 `beatBand` 時，顯示一行「這張缺的是中拍：慢拍的點數不足以逐拍對讀」。約 5 行，P3 級。

### 7.2 `DOSSIER_FIXTURES` 只當白名單，沒有覆蓋運算——這點很好

```js
if (!DOSSIER_FIXTURES[draft.stage]) return err(state0, "unknown-dossier-stage");
```
只用來檢查 stage 名稱合法。表裡的 `offsets`／`shoreGaps`／`landing` 在新流程**完全沒有被讀取**。這正是第四章 `canonicalOrbitShape` 該有而沒有的克制。（不過既然如此，`DOSSIER_FIXTURES` 可以瘦成一個字串陣列，避免下一位維護者誤以為它是資料來源。）

### 7.3 舊 API 大量並存

`runPilot`／`runCabin`／`runCaseVoyage`／`assertG1`～`assertG4`／`runPublicStep` 等一整套舊流程仍在 `api` 匯出（engine3.js:3094 前後），註解說是給舊存檔遷移。**F1 就是這類遺留 API 的產物。** 建議做一次盤點：哪些真的還被遷移路徑呼叫、哪些可以移出公開 api（留成內部函式或刪除）。**這是防止下一個 F1 的根本作法。**
