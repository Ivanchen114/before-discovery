# 《發現之前》第三章實驗台程式設計盤點

- 審查者：Codex
- 日期：2026-08-03
- 性質：唯讀程式與設計盤點；未修改 runtime
- 主審：`greybox/src/engine3.js`、`greybox/src/chapter-ui.js`
- 對照：`greybox/data/scenes3.json`、第三章設計／規格／治理文件、兩份 spike

## 一、總裁決

第三章的**物理模型、證據閘門與狀態完整性大致可靠**，而且船與落石的雙視角 SVG、原紙留痕、帶缺口回船補做，都是目前五章中相當成熟的互動底座。但「可靠」不等於「好玩」：核心流程的大部分已從自由設計實驗收斂為導引任務，玩家常在選一個正確名稱後，由引擎自動配置、連做三回、收卷、換算。

最高優先問題在第三柱 G4：**正常 UI 讓玩家辨認「同號鼓點」與「逐拍扣桅杆」兩個答案，但沒有真的讓玩家對時或逐拍換尺**。錯誤方法也不留下設計文件要求的爛圖。這不只是趣味不足，而是實作沒有完成本章最重要的代理權承諾。

一句話判定：

> 第三章目前是一套「物理正確、卷宗可靠，但有幾個關鍵判斷被選項與引擎代做」的證據工作台；可試玩，但 G4 不應以現況視為完成。

### 2.2 實際重跑

以 Node 直接呼叫 `Engine3` 的公開動作，重跑合法主流程，確認：

- 解纜起步三回均分類為「正在變快」，落點在桅後。
- 下一任務即使草稿要求 `brake`，導引鎖仍改成 `steady`，一次生成三張近似穩速、落桅腳原紙。
- 船艙滴水與拋球都可各完成停泊三回＋平駛三回；兩者只改紀錄文字，沒有不同的判斷結構。
- 進入雙視角任務後，未寫入任何 `designCommitments.dual`，仍可由 `runDossierSeries` 生成符合第三柱正式閘門的雙紙紀錄。
- G4 選錯「終點對齊」後，`p3.aligned` 仍為 false，但 `overlay.preview` 沒有變成錯紙；畫面狀態仍停在原預覽。
- 正確對時後選錯「整張平移一次」，`p3.transformed` 仍為 false，但同樣沒有生成錯誤換算圖。
- 選中「每拍扣掉桅杆位置」後，引擎一次算完全部 transformed points、容差與最大殘差；玩家沒有逐拍操作。

## 三、設計意圖與現況的關鍵差異

第三章文件存在兩層不同時期的意圖，必須分開看：

1. v0.6 架構主張「自由設計 → 原始數據 → 玩家提出有限斷言 → 帶卷宗辯論 → 補缺口」，並把「複製這組，只改一項」列為重要便利。
2. 較晚的 CH3-CR-023 明確收斂為固定順序：重現舊紙 → 走穩三回 → 比較 → 船艙 → 雙視角 → 自由補強。

所以目前的分段任務**不是偶然退化或 bug**，而是後來為了保證物理鏈與舊存檔可通過而採取的 guided contract。真正的問題是：順序被鎖定後，每一站沒有重新補上一個足以讓玩家負責的微決策，於是「玩家選變因」逐漸變成「系統帶玩家走標準答案」。

應保留固定順序，但把每一站的**一個關鍵差異**交還玩家；不必退回滿桌下拉選單。

## 五、具體問題與修法

### P0-1：G4 的「逐拍換尺」其實是選答案名稱

**證據**

- UI 只提供三個按鈕：「整張紙只平移一次／每拍扣掉桅杆當拍的位置／旋轉紙」。
- `transformDossierPapers` 一收到 `subtract-each-beat`，就呼叫 `dossierDualTransformData` 算完全部點、容差與殘差。
- v0.6 設計卻要求透明尺逐拍追著桅杆走；CH3-CR-023 更明寫「對時與逐拍換尺尚未被事先代做」。

**玩家損失**

玩家可以只辨認教科書句型，不必理解為什麼每一拍的桅杆位置不同。最重要的「岸上彎路與船上直落是同一事件」因此變成 NPC／引擎揭曉。

**建議**

1. 保留引擎的 `dossierDualTransformData` 作最終 validator，不拿掉正確物理。
2. UI 改成 4 個鼓點的「移動尺」或兩欄紙帶：
   - 玩家逐拍把岸紙的桅杆點拖到 0；
   - 或依鼓點把「石頭位置」與「桅杆位置」兩張數字片放入減法槽；
   - 每完成一拍才畫出該拍換算點。
3. 玩家提交整組結果後，引擎才以容差驗證；成功後才揭露公式。
4. 不要在操作前把正解按鈕寫成完整公式。

**驗收**

- 不能只傳一個 choice 字串取得 A5。
- 至少四個拍點都有玩家操作紀錄。
- 改錯任一拍時，畫面留下對應的錯點，不只顯示 NPC 台詞。
- 舊存檔可從「尚未換尺」續玩；既有已取得 A5 的合法存檔不回退。

### P0-2：錯誤對時／錯誤換尺沒有留下可讀爛圖

**證據**

- `alignDossierPapers` 選錯時只寫 attempts 與 `lastReply`；不更新錯誤 preview。
- `transformDossierPapers` 同樣只留 attempts／reply。
- Node 重跑時，錯誤後 overlay 仍停在先前狀態。
- 設計文件明確要求：
  - 終點配終點會錯配中間鼓點；
  - 相同高度會讓事件順序交叉；
  - 錯紙保留，玩家可重試。

**建議**

將每個錯法實際畫出來並保留最近一次：

- 終點對齊：顯示 2 號岸點被接到 3 號船點，鼓號連線交叉。
- 同高度對齊：顯示時間順序折返。
- 整張平移一次：第一拍附近可貼合，後面逐拍重新鼓出。
- 旋轉紙：高度、間距與鼓點方向一起被扭曲。

NPC 回應應指著玩家做出的錯圖說話；拿掉 NPC 結論後，玩家仍能看出哪裡壞。

### P1-1：雙視角設計承諾只存在 UI，狀態層無法證明玩家做過

**證據**

- `chapter-ui.js` 以模組變數 `ship3DualDesignReady` 阻擋正常 UI。
- 正解只做 `ship3DualDesignReady = true`。
- `engine3.js` 的 `designCommitments` 只有船艙風與器材，沒有 dual。
- `runDossierSeries` 在 dual 任務會直接鎖成同一趟雙紙並產生有效紀錄。

**精確風險**

正常 UI 目前仍會要求回答，所以這不是一般玩家可直接點出的捷徑；但引擎、存檔淨化與測試無法證明設計判斷發生過。重整頁面還會讓純 UI 旗標遺失，迫使玩家重答。

**建議**

- 新增 `designCommitments.dual = "same-event-two-observers"`。
- 加正式 engine action，由引擎驗證選擇並記 event log。
- `runDossierSeries` 的 dual 分支必須檢查 commitment。
- sanitizer 只接受白名單值；舊合法存檔若已有正式 dual record，可做一次明確 migration，不可從孤立 evidence 倒推整段歷史。

### P1-2：導引鎖保證正確，卻覆寫玩家草稿而不把「改了什麼」做成操作

**證據**

`dossierApplyGuidedLocks` 會依任務覆寫地點、船、石頭、高度、船況、鼓拍與紀錄方式。Node 重跑可把玩家要求的 brake 改回 steady。

這符合較晚 CR 的分段任務，不應整個移除；問題是畫面把「只改一項」說成概念，卻沒有讓玩家親手完成這個差分。

**建議**

- 走穩站先把上一組配置以實體卡排出。
- 玩家只需把「解纜起步」卡換成「等距岸標的平駛窗口」卡。
- 送出前顯示一句：「其餘 6 欄沿用，這次只改船況。」
- 引擎仍可鎖其他欄，但要持久化 `deltaCommitment: { field:"stage", from:"depart", to:"steady" }`。

這能同時保留低負荷與單變因責任。

### P1-3：最自由的實驗能力存在於引擎，卻沒有在主循環中充分露出

**證據**

- 引擎已有 `copyDossierRecord`，可複製舊紀錄配置。
- v0.6 把「複製這組，只改一項」列為本章最重要便利。
- `chapter-ui.js` 沒有呼叫 `copyDossierRecord`。
- 真正開放船況、槳力、船速等自由補強，是核心卷宗齊後的 explore。

**建議**

1. 在每張已收卷原紙旁加「沿用這組，只改一項」。
2. 辯論留下質疑釘後，回船直接聚焦該張原紙並預載其配置。
3. 自由補強不必提早全面開放；只在質疑釘要求時解鎖相關一項。

這比重新放回五排下拉選單更符合低負荷，也更接近「對手逼我設計下一個實驗」。

### P2-1：船艙器材是敘事換皮，不是不同的推理工具

**證據**

- 滴水與拋球都用同一個三加三完成條件。
- 兩者只改 `water`／`ball` 的文字欄位。
- 都不會產生不同誤差、不同可見軌跡或不同失敗模式。

**建議**

- 不必硬做兩套物理；可以明確把它改成「玩家選一種可觀察的局部事件」，另一種變成後續可選的交叉驗證。
- 實驗前封存質性預測：偏向船尾／留在原位附近／偏向船頭。
- 六回不要瞬間只出表格；先播放一回，再把其餘兩回以疊影或散布落點累積。
- 滴水顯示碗內落點散布；拋球顯示回到手邊的落點範圍。兩者共享結論，但視覺證據不同。

### P2-2：證據卡正面直接寫「能支持」，降低公開質詢的判斷負荷

**證據**

`DOSSIER_EVIDENCE_PACKET_BASE` 每張卡都含 `scope: "能支持：..."`。玩家在辯論時再被問哪張紙支持哪句，答案已印在卡面。

**建議**

- 選卡前只顯示原紙名稱、條件、改變／固定欄。
- 選定後才翻面顯示 scope，作為結果回饋。
- 或把 scope 拆成玩家要貼上的「只說到本船／只說到這六回／不能推到加速」邊界條。

P2 的「測過船隻 only」與混淆辨識本來很有價值，不需要把辯論改回三輪問答；只要移除卡面自帶答案。

### P2-3：一鍵三回是合理的減點擊，但回饋節奏太像瞬間填表

設計文件本來就要求「每組三回自動演出，不讓玩家連按三次」，所以一鍵三回不是問題本身。問題是三回的差異沒有形成事件。

**建議**

- 一鍵開始保留。
- 三回依序短演出，原紙一張張壓上卷宗。
- 若散布不乾淨，第二／三張應讓玩家看見偏移，而不是只在表格讀文字。
- 完成後才浮出斷言，不要和第一回同時出現。

## 六、值得保留的設計

1. **岸上／船上雙視角動畫的物理尺度控制**：船上視角固定約 8 公尺甲板尺度，避免把 0.7 公尺偏移誇張成飛出船外。
2. **動畫與量測誤差分離**：理想運動用動畫呈現，人為讀值誤差只留在原紙，沒有把誤差演成物體轉彎。
3. **原紙不清空、質疑釘可帶回船**：失敗是下一輪實驗設計的輸入，不是扣血重來。
4. **證據範圍閘門**：穩速、船艙、跨船與雙紙的資料需求分得清楚，沒有用一張神紙通吃。
5. **P2 的混淆變因與外推邊界**：玩家必須說到實際測過的船為止，這比單純答物理名詞更像研究判斷。
6. **固定順序作為新手骨架**：後來的 CR 收斂有其合理性；不應為了追求自由，重新變成龐大的參數面板。

## 七、優先施作順序

### P0：第三柱代理權

1. 先做錯誤對時／錯誤換尺的可見爛圖。
2. 再把「逐拍扣除」改成至少四拍的玩家操作；引擎只驗證。
3. 補測試：
   - 單一 choice 不得直接取得 A5；
   - 缺任一拍不可完成；
   - 每種錯法都產生對應 preview；
   - 重試不清除前一張錯紙。

### P1：設計承諾與單變因責任

4. 持久化 dual commitment，engine 與 sanitizer 共用正式閘門。
5. 讓走穩任務以「複製上一組，只改船況」呈現。

## 九、最後建議

不要推翻第三章重構，也不要回到滿桌參數。最有效的修法是：
