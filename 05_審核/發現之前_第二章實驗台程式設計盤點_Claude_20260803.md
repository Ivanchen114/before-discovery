## 二、逐站盤點（全部以 Node 實跑驗證）

### 2.1 ✅ B2-3 押注：**真的封存→揭曉**（本章最大的正面）

**守衛鏈**（Node 實測）：

```
 未押注就跑 H=25 → prediction-required
 亂序重跑 H=9  → wrong-order
 押 5.0 後改押？→ (可改押，尚未跑 25)
 H=25 實測值 = 5.01 （來自 FIXTURE，非由前三高導出）
 predictionError = 0.20%  accepted = true
 跑完後還能改押嗎？→ no-open-series
```

- `predict()` 要求 4/9/16 已有（`too-early`）且 25 未跑（`already-run`）
- `runHeight(25)` 要求 prediction 已設
- 揭曉後不能回頭改押

**押錯真的會失敗**——我掃了七個押注值：

| 押 | 實測 | predErr | accepted |
|---|---|---|---|
| 3.0 | 5.01 | 40.1% | ✕ |
| 4.0 | 5.01 | 20.2% | ✕ |
| **4.5** | 5.01 | 10.2% | ✓ |
| **5.0** | 5.01 | 0.2% | ✓ |
| **5.5** | 5.01 | 9.8% | ✓ |
| 6.0 | 5.01 | 19.8% | ✕ |
| 7.0 | 5.01 | 39.7% | ✕ |

**3/7 通過。** 對照第一章：ch1 的 `predHit` 在押 `9×avg[0]` 時**恆為 true**，掃 54 種配置有 42 種是「資料髒到形狀不成立、預測照樣命中」。**第二章沒有這個問題。**

而且 `judgeRaw` 是**雙門檻**：`shapeError ≤ 0.12`（前三高是否照 √H 走）**且** `predictionError ≤ 0.12`（押注是否命中實測）。兩道門測的是兩件不同的事——**這正是第一章缺的獨立性。**

### 2.2 ✅ 器材選擇真的改變資料，而且改變的是「資料的種類」

`profileOf` 是一條支配序（`notRunnable` > `coarseRead` > `directionScatter` > `speedDrift` > `clean`），四種配置給出四組不同的 fixture：

```
  全乾淨    profile=clean             讀值=2 , 3.02 , 3.98
  手放      profile=speedDrift        讀值=1.72 , 2.85 , 4.36
  毛邊桌沿  profile=directionScatter  讀值=2 , 3.5 , 3.55
  目測板    profile=coarseRead        讀值=[1.6,2.4] , [2.5,3.5] , [3.4,4.6]
```

**⭐ `coarseRead` 給的是區間而不是單值。** `judgeRaw` 檢查 `typeof vals[i] !== "number"` → 回 `{error: "non-scalar"}` → `accepted = false`、`rejectReason = "non-scalar"`。

**選錯量具，玩家得到的不是「不準的數字」，是「根本不是數字」。** 而 UI 的回饋也對得上：

> 「這個範圍太寬,還不能押一個數——**量法得再講究**。」

這是五章裡把「器材決定資料品質」演得最具體的一次——比第一章的「12% 過不了」更直觀，因為玩家看到的是螢幕上一個**寫不出來的數**。

**未組裝／未校準也擋得住**：`beginSeries` 回 `not-assembled`；組好但零校準 → `profileOf` 落到 `coarseRead`（**不是硬擋，是給你不能用的資料**——更好的教法）。

### 2.3 ✅ `assertLaw` 五道守衛，無捷徑

Node 逐項打：

| 嘗試 | 結果 |
|---|---|
| 亂編概念 `whateverScale` | `unknown-law-concept` |
| 木球 series ＋ sqrtScale | `law-source-ball` |
| 髒資料（手放，accepted=false）＋ sqrtScale | `series-not-accepted` |
| 乾淨銅球 ＋ `linearScale` | `concept-mismatch`（不改 state、不耗天） |
| 乾淨銅球 ＋ `constantRange` | `concept-mismatch` |
| 乾淨銅球 ＋ `sqrtScale` | ✅ 寫入 `f2.law` + `lawSource` + `lawConcept` |

**這是全系列「選概念」的參考實作**（規格 R-LAB2-04：「玩家必須在 UI 親自完成兩個動作：選一組完整紀錄、選它支持的概念；**資料與概念都不得預選**」）。

對照：第五章 `assertJ1/J2/J3(state, ids)` **完全沒有 concept 參數**，結論寫死在 UI 陣列。**同一個專案，第二章有、第五章沒有。**

### 2.4 ✅ `compareBalls` 五守衛有效，且診斷資訊量足

```
 兩組都銅球 → ["球種須一銅一木"]
 中途換桌沿 → ["裝置指紋(零件/校準)不同","形狀誤差超限","兩球讀值差超過 3%"]
```

**失敗時一次列出全部相異維度**（不是報第一個就停），符合規格 R-LAB2-05「失敗時列出差異維度」。

### 2.5 ⭐ 放棄重來不會刷到新數字——**反 save-scumming 設計**

`beginSeries` 的 cycle 計算：

```js
var done = s.series.filter(function (x) {
  return x.status === "complete" && x.fingerprint === fp && x.ball === ball;
}).length;
... cycle: done % 3
```

**只數 `status === "complete"`。** 放棄的 series 不推進 cycle，所以**放棄重開會拿到完全相同的三筆讀值**——而每次 `runHeight` 都 `days += 1`。

**玩家不能靠重開刷資料，只會花掉天數。** 這是刻意的，而且比「禁止放棄」高明——它允許玩家放棄（規格要求），但不給任何好處。

### 2.6 ✅ B2-2 尺量墨線 / B2-4 一拋一放 / B2-5 蠟封：判斷都在玩家手上

這三站是 scenes 層的 choice，不經 engine2：

| 站 | 判斷 | 錯誤如何被駁 |
|---|---|---|
| B2-2 墨跡曲線 | 二選一（從第一寸就彎／前段有一小段直） | 伽利略把直尺貼上墨線起段，「尺與墨線之間，漏進一線光」——**用玩家自己的器材駁** |
| B2-4 一拋一放 | 先押木籌 → 扳一次 → 三選一 | 「這個字是哪一列留下的？找得到，就圈給我看；找不到，就別替耳朵補聲音。」 |
| B2-5 蠟封 | 挑出未驗的那張 ＋ 袋面寫什麼（三選一） | 兩個過度宣稱（「桌上實驗已經證明船上也會如此」等）被伽利略駁回 |

**B2-4 的木籌是真的封存**：`q1` 押注 → `q2` 扳門閂 → `np1/q3/q4` 三層逐一揭曉。押注在前、揭曉在後、三層各自確認。

### 2.7 ✅ B3 三柱辯論：weakTo 配對是真判斷

`debate2.json` 每根柱子有 `weakTo`，`narrative.js` 的 `debatePresent` 檢查 `weak.evidence === p.evidence`。玩家要把「哪張證據」對上「哪一句主張」。

**但 `playerCorrect` 由系統代講**（`narrative.js:325`）——這與第五章、第一章相同，**是 `narrative.js` 共用引擎的行為，不是第二章的問題**。修法見我在第五章報告的 P2-C（拆出玩家選收尾句，可逐章導入）。

## 三、找到的問題（四個，全部 P2／P3）

### 🟡 I1（P2-A）`compareBalls` 不以 `f2.law` 為前置——引擎層

Node 實測：

```
 只跑兩組、完全不呼叫 assertLaw：f2.law = false
 compareBalls → ok，f2.ball=true
 結果：f2 = {"law":false,"lawSource":null,"lawConcept":null,"ball":true}
```

**完全跳過概念斷言，也能拿到 F2b。**

**目前安全**——`scenes2.json` 的 embed 依序 gate：

```
B2-3/e1  until {cat: "threeH"}
B2-3/e2  until {f2: "law"}      ← 必須先 assertLaw
B2-3/e3  until {f2: "ball"}
```

玩家到不了 `e3` 之前，一定已經完成 `assertLaw`。

**但這與第三章的 `judgeDossierBlind` 同類**：引擎 API 的安全性依賴 UI 的呼叫順序，而不是自身守衛。存檔遷移、測試、未來 UI 改動都可能踩到。

**建議（1 行）**：
```js
function compareBalls(state0, idA, idB) {
  if (!(state0.evidence && state0.evidence.f2 && state0.evidence.f2.law))
    return err(state0, "law-required");
  ...
```

### 🟡 I2（P2-B）超前完成 25 的台詞錯位

見第一節。`n3` 與 `e2` hint 各加一個變體。

### 🟡 I3（P3-C）F2b 沒有概念選擇——章內不對稱

| | 介面 | 誰說出結論 |
|---|---|---|
| **F2a 射程律** | `assertLaw(seriesId, **conceptId**)`，三選一含兩誘答 | **玩家選** ✅ |
| **F2b 換球** | `compareBalls(idA, idB)`，只有兩個 series id | **伽利略講**：`B2-3/n6`「銅球這樣彎,木球也這樣彎。**重量換了,路沒有換。**」 |

規格 R-LAB2-05 確實只寫守衛條件、沒要求 `conceptId`，**所以合規**；守衛也很嚴（五個維度全同才受理）。**是不對稱，不是繞過。**

但被 NPC 講掉的那一句，正是第二章要駁倒的核心迷思（重量影響拋體）。

**建議**：`compareBalls` 加第三個參數，沿用 `assertLaw` 的模式：
> ✓「換了球重，路沒有換。」
> ✗「木球比較輕，所以飛得比較遠。」
> ✗「兩顆球的路一樣，因為它們一樣重。」

### 🟡 I4（P3-D）`assertLaw` 的 noop 讓 lawSource 無法更新

```js
if (state0.evidence && state0.evidence.f2 && state0.evidence.f2.law)
  return { state: state0, ok: true, noop: true };
```

一旦取得 F2a，再呼叫一律回 `ok:true` 不做事。**若玩家後來做出更乾淨的 series，無法把 `lawSource` 換過去。**

規格 R-LAB2-04 有相容條款（「舊存檔若已有 `law=true` 而無 `lawSource`，視為 legacy 相容資料，不追溯撤銷」），所以現行行為不違規。但這與第四章 `revokeEvidence` 的哲學不一致（那裡改上游會讓下游失效並保留舊紙）。

**建議**：允許用另一組 accepted copper series 重新斷言並更新 `lawSource`，舊的留在 `series` 裡不刪。低優先。
