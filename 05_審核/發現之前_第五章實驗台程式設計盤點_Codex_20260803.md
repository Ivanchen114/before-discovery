## 一、審查範圍與驗證邊界

### 讀取來源

### 方法

每個互動站分四層檢查：

1. **玩家輸入**：玩家實際選了什麼、按了什麼。
2. **引擎判定**：程式真正檢查哪些條件。
3. **可見結果**：玩家是否看見物理事件，而非只看見結論文字。
4. **授證條件**：證據是否由玩家的判斷取得，還是由固定資料／固定配對自動授予。

另以 Node 直接呼叫 `engine5.js` 與 `narrative.js`，重現疑似捷徑。Node 攻擊只用來驗證判定契約；若某個 mutation 不能由正常 UI 做到，本文會明標，不能誤稱為玩家可利用的存檔漏洞。

### 基線

本輪開始時執行：

```text
cd greybox && npm test
139 通過，4 失敗（共 143）
```

四項失敗為：舞台快取鍵一項、第三章走查／生產性失敗／第三柱換尺三項。**沒有第五章測試失敗**。這是多人共享工作樹的現況背景，不是本報告造成，也不能寫成全套綠燈。

本輪沒有做真人瀏覽器完整通關，因此視覺手感、觸控手感與實際等待時間仍屬未驗。

## 二、設計契約：第五章原本要把什麼留給玩家

規格的核心分工其實很清楚：

| 階段 | 規格承諾 | 玩家應擁有的判斷 |
|---|---|---|
| J1 動量帳 | 親手驗證對手確實正確 | 兩種碰法中，帶方向的 `mv` 是否都閉合 |
| J2 活力帳 | 同一批原紙換一本帳，不做新實驗 | 同一事件中，鋼頭與油灰的 `mv²` 是否同進同退 |
| 追一筆 | 殺掉「油灰總是少一半」假規律 | 換質量比後，短少比例是否仍固定 |
| J3 黏土 | 量出壓陷與 `v²` 的尺度 | 數據比較支持線性、平方，還是無固定關係 |
| 三柱辯論 | 工作台供證據，辯論考範圍與問題形狀 | 哪張證據能咬住哪個推論，以及它真正能推出多遠 |
| FR | 同一個盲點第二次出現，玩家要自己負責 | 兩本帳是一本勝出、同物異寫，還是記不同事情 |

規格還明說：「**誘答只在辯論台，不在工作台**」、「NPC 只指欄位，完整診斷由玩家說出」。現行實作保存了證據順序與正確物理數字，卻多次把「完整診斷」交給引擎固定文字。這是本輪最主要的規格落差。

## 三、總裁決

第五章的**資料模型可靠，玩家模型偏弱**。

- 可靠之處：四種碰撞 fixture 正確；J2 強制使用 J1 原紙；4／8 追一筆可達；J3 要求同質量、三種速度；辯論順序 P2→P1→P3；FR 保留正確證據邊界。
- 偏弱之處：工作台的黃金路徑幾乎是照任務卡按固定次數；資料列自動勾選；斷言由引擎依資料形狀直接授予；追一筆的設定與答案都被預先固定；辯論可不追問就直接配對；配對成功後完整論證由系統代旅人說完。

因此，本章目前比較像一套**有扎實科學內容的操作式證明播放器**，而不是玩家真的在做物理判斷的遊戲。FR 是例外：它確實要求玩家親自重寫問題，也是全章最值得保留的互動。

## 四、Node 實測：可重現的捷徑與判定缺口

### 4.1 J1 六筆其實只有兩種完全相同的物理列，仍可取得 J1

操作：高刻度鋼頭連按三次、高刻度油灰連按三次，選六筆後 `assertJ1`。

```text
ATTACK-J1 repeated-identical accepted= true
sources= 6
unique-configs= 2
```

`engine5.js:72-110` 的碰撞沒有讀值誤差；同一配置的三筆，除 `id/day` 外物理數值完全相同。`assertJ1`（117-134）只數鋼頭三筆、油灰三筆、同質量、同速度與動量閉合，因此六次操作實際上只是把兩列複製三份。

這不是非法 exploit，因為規格本來要求重複；但它證明「多做幾次確認讀值重疊」的手感沒有實作。規格 §7-4 提到重複配置應有交替讀值，現行碰撞資料沒有任何交替誤差。

### 4.2 J2 成功後，追一筆的全部設定由系統代選；玩家只剩一個按鈕

Node 結果：

```text
ATTACK-J2 auto-draft=
{"head":"putty","speed":"high","masses":"4/8",...}
phase= followup

ATTACK-followup one-click grant= true
record= putty/4/8
deficit= 96
phase= clay
```

`assertJ2` 在 `engine5.js:151-153` 直接把碰撞頭、高速、4／8 寫入 draft；UI 在 `chapter-ui.js:7411-7419` 又把相關選單鎖住。玩家按「4／8 油灰追一筆」後，`runCollision` 立刻在 106-108 將 `followup=true` 並進入黏土。

這一拍沒有真正的操作錯誤，也沒有先押「仍少一半／比例會變」。它是重要物理反例，但目前只是按鈕播放答案。

### 4.3 J3 的引擎不判斷深度是否跟 `v²` 走

把三種速度的三筆合法 runtime 紀錄深度改成 `99、1、50`，再直接呼叫 `assertJ3`：

```text
ATTACK-J3 arbitrary-depth accepted= true
depths= 99,1,50
evidence= true
```

控制組只留一種速度三筆，會被正確拒絕：

```text
CONTROL-J3 one-speed rejected= three-speeds-required
```

原因是 `engine5.js:180-193` 只檢查：至少三筆、同一球重、至少三種速度。它**完全沒有比較 `depth` 與 `speed²` 的關係**。

必須精確說明：正常 UI 不能任意改寫深度，fixture 會自動產生正確數字，所以這不是現行存檔洗白證明；它證明的是斷言 predicate 沒有承載「平方關係」，平方關係完全由固定 fixture 和成功文案代做。玩家只要照清單做三種高度，不必判讀數據。

### 4.4 探索模式引擎可接受重球，但 UI 正確鎖住

Node 直接呼叫 `setCollisionDraft(ballMass=heavy)` 在 explore state 成功；但 `chapter-ui.js:7400-7401` 對探索模式將選單 disabled，因此一般玩家無法由 UI 使用。這是「引擎未帶 mode 語義、UI 負責守門」的架構債，不列玩家 exploit；若未來新增 caller，需避免繞過。

### 4.5 三柱可完全不「問到底」，直接配對破完

在合法持有 J1/J2/J3 且辯論初始化後，依次直接呼叫：

```text
J1 → p2s3
J3 → p1s3
J2 → p3s3
```

結果：

```text
ATTACK-debate direct-present J1 outcome= correct
ATTACK-debate direct-present J3 outcome= correct
ATTACK-debate direct-present J2 outcome= correct
pillars-broken= 3
press-lines= 0
```

`narrative.js:303-363` 沒有要求目標證詞先進入 `pressed` 狀態。UI 也在未追問時就顯示「用證據回擊這一句」（`chapter-ui.js:1021-1031`）。「問到底」只會揭露 insight 與探索模式的「此句有隙」，不是破柱前置。

更關鍵的是，一旦 evidence ID 與 `weakTo` 配對，`narrative.js:326-333` 會自動播放整段 `playerCorrect`、對手退讓、支柱破裂。玩家只做配對，完整物理解讀由程式代說。

### 4.6 FR 沒找到結構性繞過

直接嘗試最短正解鏈仍須依序完成：

```text
books-split → ruler-not-receipt → different-things
```

結果才是：

```text
status= won
J4= true
```

提前提交 claim 會因當前 step 找不到選項而拒絕；FR 也檢查 J1/J2/J3。此站確實要求玩家做三次概念選擇，沒有發現像前三柱那樣的「不做前置判斷也能直接過」捷徑。

最終正解按下後，系統仍會替旅人播放 127 字的 `honestText`，但短選項本身已包含「兩本帳記不同事情」的關鍵判斷，因此這是敘事展開，不等同前三柱的代理判斷。

## 五、逐站完整盤點

## 5.1 J1｜動量帳

### 玩家實際做什麼

1. 預設高刻度鋼頭，連按三次。
2. 把碰撞頭改成油灰，再按三次。
3. 六筆在產生時已被 `collision5Do` 自動勾選（`chapter-ui.js:7242-7244`）。
4. 按「用勾選紀錄提出斷言一」。

黃金路徑不要求玩家真的挑紀錄；「勾選」的核心操作已由 UI 自動完成。

### 物理映射缺口

引擎保存撞後 A、B 速度（`engine5.js:97-100`），但 UI 表格只顯示撞前 A/B、動量總額、活力總額（`chapter-ui.js:7307-7317`），**沒有顯示撞後兩車各自怎麼動**。

所以玩家看不到：

- 鋼頭：A 停、B 接走速度。
- 油灰：A、B 黏住後同速。
- 方向為何要帶正負。

畫面主圖又是靜態資產；每次執行沒有滑車運動、反彈、黏住或鈴齒節拍。玩家得到的是一列「24→24 ✓」，不是一場碰撞。

### 可見結果是否有因果感

低。動量欄直接加上 `✓`，等於 UI 先替玩家判斷「閉合」。六筆完全相同的重複列又讓前三次／後三次變成點擊成本。

### 裁決

**P0：物理事件沒有被可視化，證據選取又被自動完成。**

### 具體修法

1. 每次碰撞先播放 1–1.5 秒 DOM/SVG 動畫：A 入射、鋼頭交換速度／油灰合體；再展開數值列。
2. 表格加「撞後 A／B」與方向箭頭，不要只給總額。
3. J1 階段只顯示動量帳；活力帳先以封住的第二頁呈現。
4. 新紀錄不要自動勾選。至少在提出斷言前讓玩家親手圈出六張原紙。
5. 若保留三次重複，加入確定性的微小速度讀值誤差與重疊帶；否則改成各一筆，避免六次複製。
6. `assertJ1` 增加玩家判斷參數，例如：

```js
assertJ1(state, ids, claim = "directional-momentum-closes")
```

選錯「只看速度大小／油灰不閉合」時留下可讀的兩車速度對照，不授證。

## 5.2 J2｜同紙重算活力帳

### 值得保留

`assertJ2` 精確要求 J1 的同一組 source IDs（`engine5.js:136-154`），也禁止在 J1 後、J2 前新增實驗（72-75）。這是全章最重要、也實作最完整的資料所有權設計。

### 現行捷徑

第一輪表格從每筆生成起就同時顯示活力帳與短少（`chapter-ui.js:7289-7312`）。玩家在 J1 時已讀過「144→72（短少72）」；J2 並不是翻開第二本帳，而是按鈕承認早已顯示的答案。

此外，J1 的六筆本來就被自動勾著，`collision5Checked` 跨 phase 保留，因此 J2 黃金路徑通常連「勾回同一批」都不用做，只需按一次「用同一批紀錄重算活力帳」。

### 裁決

**P0：資料所有權正確，但揭示與操作設計把核心重看動作抹掉。**

### 具體修法

1. J1 期間完全不渲染 `visViva` 欄；J1 成立後才把第二本空帳推入畫面。
2. 進 J2 時清除 transient 勾選，要求玩家親手把同六張原紙夾到第二本帳；錯紙留在桌上並標出「少／多了哪張」，不要只顯示錯誤碼。
3. 讓玩家選下資料關係：
   - 鋼頭：兩帳都閉合。
   - 油灰：動量閉合、活力短少。
   - 兩帳：沒有同進同退。
4. 成功後才顯示完整 J2 斷言；不要在任務卡、欄名與成功訊息三處重複代答。

## 5.3 lab2｜4／8 追一筆

### 物理價值

高。它用同一種油灰碰撞改質量比，推翻「非彈性總是少一半」，並把短少從固定常數改成待追去向的帳。這是很好的反例設計。

### 玩家實際做什麼

零設定、零預判，只按一顆「4／8 油灰追一筆」。引擎與 UI 已把碰撞頭、速度、質量全部鎖定；按完立即顯示：

> 動量帳 24→24；活力帳 144→48，短少96（三分之二）。

玩家沒有機會先相信「仍是一半」，因此結果不會成為對自己模型的反駁，只是系統示範。

### 裁決

**P0：重要反例被做成一鍵揭曉。**

### 具體修法

在執行前加「封存預測」，不增加 scenes5 choice 節點，可直接做成 embed 內部狀態：

```text
換成 4／8 後，短少比例會：
□ 仍是一半
□ 跟著質量比改變
□ 不再短少
```

封存後才開放碰撞。結果以兩張帳的短少色帶並排，先讓玩家比較 72/144 與 96/144，再問：「哪個說法活下來？」答完才授 `followup`。錯誤不扣分，舊預測留痕。

## 5.4 lab3｜黏土落球

### 玩家實際做什麼

探索模式只能選高度；球重被正確鎖為輕球。玩家依序做一、四、九格各一筆，三列自動勾選，再按提出斷言。

### 物理映射缺口

- 主圖是靜態黏土裝置，沒有球落下與坑深形成動畫。
- 表格只列速度與坑深；沒有把三個坑並排按比例畫出。
- 任務文字已叫玩家「比較坑深與 `v²`」，按鈕成功後直接寫「吻合」。
- `assertJ3` 不計算比例，也不要求玩家在「跟 v／跟 v²／無固定關係」中判斷。

### 裁決

**P0：數據是正確的，但平方關係沒有成為玩家動作。**

### 具體修法

1. 每次落球用 DOM/SVG 畫出可比較的坑截面，三個坑保留在同一盤視圖。
2. 三筆完成後先不顯示 `v²` 欄；讓玩家把三張坑深卡排到「1:2:3」或「1:4:9」尺旁。
3. `assertJ3` 必須接收並驗證 `model`，同時重算資料關係：

```js
assertJ3(state, ids, model = "quadratic")
```

4. 測試需加入「三種速度但深度亂序／不成平方不得授證」。fixture 自動正確不能取代 predicate 測試。
5. 學者模式的重球交叉驗證可保留，但不要讓「換球重」成為另一條主線；它只應擴充範圍註記。

## 5.5 三柱辯論

### 值得保留

- P2→P1→P3 的順序有戲：先承認對手，再保住短少，再拆掉「同物異寫」。
- 錯誤配對不刪資料；中止後已破支柱保留。
- `mistakes` 與 debrief 把失手配對留下來，具有可修復性。
- 第一次誤擊免扣，降低規則學習成本。

### 玩家判斷被繞過的位置

1. 「問到底」不是必要前置；未追問也能選任何證詞與證據。
2. 每柱只有一條 `weakTo`；追問後探索模式還標「此句有隙」。
3. 證據卡本身顯示完整摘要。
4. 一旦 target/evidence 配對正確，完整 `playerCorrect` 由引擎播放；玩家沒有選下推論與邊界。

這使辯論的真實動詞是「找出資料 schema 中的 weakTo 配對」，不是「用證據完成論證」。Node 已證明三柱可零追問直破。

### 裁決

**P0：配對有互動，但最重要的推理句仍由系統代說。**

### 具體修法

最低成本不是強迫三句全問，而是把每柱拆成兩步：

1. 選證詞＋證據。
2. 選「這張證據真正能推出什麼」。

例如 P1 出示 J3 後：

```text
□ 短少已全部找回來
□ 坑深提供可量尺度，但完整去向仍未對平
□ 動量帳因此錯了
```

只有第二項才播放精簡版 `playerCorrect` 並破柱。如此 evidence 配對仍保留，證據邊界則真正交給玩家。

「問到底」可維持選配，但若沒問過，第二步不顯示 insight；玩家仍可憑工作台理解作答。不要把所有追問變成強制清單。

## 5.6 FR｜兩本帳重寫

### 為何是全章最好的一站

- 必須持有 J1/J2/J3。
- 兩個重讀 step 依序開放，不能直接跳 final claim。
- 錯項不消失，可重複提交。
- 研究失信與普通概念錯誤有不同後果。
- 最後四選一真正要求玩家決定兩本帳的關係。
- 正解仍保留「完整去向未對平」。

### 可改進但不應重做

1. 正解按下後 127 字 `honestText` 太長，容易讓玩家覺得系統又替自己發表演說；可切成玩家選項原句＋旅人補一句＋院士回應。
2. 第二步正解文字比錯項更完整，可能形成語體洩題；這是文字層問題，不是引擎繞過。
3. `E3-2/c_j4` 只有一個選項，是簽署儀式，不應偽裝成 choice；可改為「封存卷宗」action，但會碰 scenes5 choice 計數契約，需總監裁決。

### 裁決

**保留核心，不要為了統一格式重做 FR。** 應把前面幾站提升到 FR 的玩家代理權，而不是把 FR 降回配對題。

## 六、跨站系統性問題

### 6.1 `collision5Checked` 是 UI 全域暫存，不在遊戲 state

`chapter-ui.js:7203` 將勾選存在模組全域物件。結果：

- 重繪可保留，符合規格。
- 重新整理／重載存檔後選取消失。
- 同頁重開新局時，舊 ID 勾選可能殘留到同號新紀錄。
- sanitize 與 eventLog 無法知道玩家究竟選過哪些資料。

短期可接受為 UI state，若未來「選紙」要成為學習證據，就必須搬進 `state.lab.selection`，並加入 schema／sanitize／舊存檔處理。

### 6.2 `days` 有累加，沒有可見代價

每次碰撞與落球都 `days++`，但第五章工作台表格不顯示 day，也沒有期限與路線差異。這個欄位目前只是一個不可見計數器，不能形成「多做一次是否值得」的遊戲判斷。

不建議立刻加硬倒數；要嘛刪除玩家不可見的戲劇承諾，要嘛只在清樣期限／研究日誌顯示工時，作為反思資料而非懲罰。

### 6.3 結果與判斷沒有分層顯示

多數成功訊息一次交付：數字、關係、理論意義、證據邊界。玩家看不到「我先看見什麼，然後我怎麼判斷」。應統一改成：

```text
物理結果 → 玩家選解讀 → 系統封存斷言
```

而不是：

```text
按按鈕 → 系統直接宣布斷言
```

### 6.4 自動測試主要驗可達性，沒有驗代理權

現有第五章測試很完整地驗 fixture、同紙重算、phase、證據與 sanitizer，但黃金路徑本身就是：

```js
run×3 → run×3 → assertJ1
assertJ2 → runCollision
runClay×3 → assertJ3
J1/J3/J2 直接 debatePresent
```

因此「測試全綠」只證明自動流程可走通，沒有證明玩家做過核心判斷。Node 攻擊所走的捷徑，部分正是正式黃金測試的路徑。

## 七、建議施工方案

## P0｜先把核心判斷還給玩家

### P0-1 J1 顯示真實碰撞，不提前顯示活力帳

- `chapter-ui.js`：J1 table 只顯示撞前／撞後 A、B 與動量帳。
- 加 deterministic DOM/SVG 碰撞動畫。
- J1 成功後再翻開活力帳欄。
- 風險：中，主要是 UI；engine fixture 不需改。
- 可回退：高，可由 phase render feature flag 控制。

### P0-2 工作台三斷言增加概念參數

- `engine5.js`：`assertJ1/J2/J3` 除 IDs 外接收 claim/model。
- `narrative.js:labAction` 傳入新參數並記入 eventLog。
- `chapter-ui.js`：在資料圈選後顯示 2–3 個平行判讀。
- `sanitize.js`：若判讀成為持久證據來源，需重算或白名單化。
- 風險：高，涉及 state/schema；建議先 shadow 記錄、暫不改 gate，再切換。
- 可回退：中。

### P0-3 追一筆加入封存預測

- `engine5.js` state 增加 `followupPrediction`。
- 未封存不得 run followup；執行後保存 prediction/result 對照。
- 錯預測不扣信譽，只留痕。
- 風險：中；embed 內新增狀態，不必增加 scenes5 choice 節點。
- 可回退：高。

### P0-4 三柱加入「推論／邊界」第二步

- `debate5.json` 每柱增加 `claims` 平行選項。
- `narrative.js` 將 correct evidence pairing 改成 pending pair；選對 claim 才 broken。
- `playerCorrect` 僅在玩家選下正確推論後播放。
- debrief 記錄「配對錯」與「邊界錯」兩種失手。
- 風險：高，需存檔與 sanitizer 配合。
- 可回退：中；可先只在 ch5 開 feature kind。

## P1｜讓操作有物理後果

1. 黏土盤顯示三個保留坑與比例尺。
2. 碰撞表補撞後速度與方向。
3. 決定 J1 三次重複的命運：實作量測差，或改為每頭一筆＋一次玩家復驗；不可維持完全相同的三列。
4. 工作台成功訊息只報結果，不同時報理論結論。
5. J2 phase 清除／封存 UI selection，讓「同紙重算」成為可見動作。

## P2｜清理流程債

1. 把 `collision5Checked` 搬進可序列化 state，或明確在每次新局／載入時重置。
2. 決定 `days` 是工時資料還是無效欄位；不要保持不可見。
3. `E3-2/c_j4` 改成簽署 action，而不是單選 choice（需總監裁決測試常數）。
4. 精簡 FR `honestText`，保留玩家已親自選下的核心句。

## 八、建議新增的自動測試

### 工作台

1. J1 phase 不得輸出活力帳／短少欄。
2. 合法六筆但未選正確 claim，不得授 J1。
3. J2 必須使用 J1 原始 IDs，且要選對鋼／油灰兩帳關係。
4. 未封存 followup prediction，不得執行 4／8。
5. followup 執行後 prediction 與結果都留在 state/eventLog。
6. 三種速度但深度亂序／任意值，不得授 J3。
7. 合法平方資料但選 linear，不得授 J3。
8. 探索模式不能由任何公開 action 切換重球。

### 辯論

9. 只配對 evidence/target 不得立刻破柱。
10. 配對正確、claim 越界仍不得破柱。
11. P1 必須保留「完整去向未對平」。
12. 未追問可以作答，但不應取得 insight／gap badge；追問保持選配。
13. 中止再入要保存 pending pair 或明確清除，不能形成半完成死狀態。

### FR 與回歸

14. FR 仍須依序完成兩步＋final claim。
15. 錯項可重複、普通錯誤不洗掉原紙。
16. J4 只在 correct final claim 後授予。
17. 舊 schema 1 存檔可遷移到新增判讀／預測欄位，不能由孤立 evidence 布林值補造判讀史。

## 九、真人瀏覽器驗收清單

自動測試不能替代以下項目：

1. 玩家第一次碰鋼頭與油灰時，是否先看懂兩車怎麼動，再看數字。
2. J1 完成前是否完全看不到活力帳答案。
3. J2 是否真有「同一張紙忽然說出另一件事」的揭示感。
4. followup 錯預測後，玩家能否只看兩條短少色帶自己修正。
5. 三個黏土坑是否不用 NPC 解說就看得出 1:4:9 尺度。
6. 辯論中玩家能否說出「我選這張證據，因為它只能推出……」。
7. 刪掉 `playerCorrect` 後，玩家的操作仍能表達同一推論。
8. FR 是否仍是高潮，而不是前面已被問過三次的複習題。
9. 手機橫屏下動畫、數據表與推論選項不互相遮擋。
10. reload 在 J2、followup、J3、辯論 pending pair 各一次，狀態不丟失。

## 十、最優先修改的八項

1. **J1 階段隱藏活力帳，J2 才翻開。**
2. **J1 表格顯示撞後兩車速度與方向，補碰撞動畫。**
3. **取消產生紀錄即自動勾選，讓選紙成為玩家動作。**
4. **J3 斷言真正驗證資料關係與玩家 model，不只數三種速度。**
5. **4／8 追一筆先封存預測，再顯示反例。**
6. **三柱正確配對後再讓玩家選推論／邊界，才播放 `playerCorrect`。**
7. **處理碰撞三次重複完全相同的點擊稅。**
8. **保留 FR 主體，僅縮短自動演說。**

## 十一、最終裁決

第五章的物理 fixture、證據順序與 FR 都值得保留；問題不在「內容錯」，而在**玩家只啟動正確答案，沒有完成正確答案**。

最嚴重的四個代理點是：

1. UI 從第一輪就同時算好兩本帳。
2. 新紀錄自動勾選，工作台選紙被代做。
3. J1/J2/J3 的斷言由資料形狀直接授予，尤其 J3 不檢查平方關係。
4. 三柱只需 evidence ID 配對，完整論證由固定 `playerCorrect` 代說。

若只能做一輪修改，應採「**J1 隱藏第二帳＋追一筆先預測＋J3 選模型＋三柱加邊界選擇**」這四刀。它們不增加新物理內容，只把既有內容從系統手上還給玩家。完成後，第五章才會從一張正確的工作單，變成兩本都說真話、而玩家必須親手決定它們各自在說什麼的遊戲。
