# 《發現之前》第六章 互動劇情設計盤點

**審查者**：Claude (Anthropic) ｜ **日期**：2026-08-03
**對象**：`greybox/data/scenes6.json`（13 場 / 237 節點 / 11 個 embed）、`greybox/src/engine6.js`（480 行）、`greybox/src/chapter-ui.js` 第六章區段（7747–8000+）
**方法**：讀敘事層與程式層並用 Node 實跑驗證。所有「玩家做了 X 會怎樣」的斷言都用腳本跑過，不憑讀碼推測。
**維度**：敘事因果鋪陳、核心判斷代理權、前向引用與因果斷裂、錯答收尾、四項核心修法的體驗落實度。

## 摘要

**敘事鋪陳是六章裡最好的。**「來源封條」機制讓每一個工作台都自帶「這一輪在查誰、如果真是他哪裡會先變」的框架 —— 這是結構性的優勢，不是靠個別台詞補救出來的。第四章 K1 那種「為什麼要預測？」的問題，第六章在 11 個互動裡只有 1 個真的犯了。

**但互動層有三個「敘事承諾、程式沒兌現」的落差，而且都落在本章最重要的機制上：**

| # | 位置 | 敘事／契約承諾 | 實際 | 嚴重度 |
|---|---|---|---|---|
| **P0-1** | `model-audit-board`（H3-1，本章高潮判斷） | 「接錯時不亮答案……留下『問的是不同問題』的斷線」 | **UI 按鈕上直接印著答案**（「碎屑來源 ← T1」），接錯不可能發生 | **最嚴重的核心判斷代理** |
| **P0-2** | `continuous-run-bench`（H2-3，本章「新動詞」） | 「盲目續鑽……曲線會折斷、變斜或失去水量基準」 | **三個按鈕效果完全相同**，溫度序列硬編為 `[31,47,65,83,96,100]` 只吃格數 | 本章招牌機制歸零 |
| **P0-3** | `chip-capacity-bench`（H1-1，第一個工作台） | 「兩條紙帶會從不同起點展開，留下肉眼可見的爛對照」 | **故意少放一半碎屑，兩條曲線一個數字都沒變** | 教「控制變因」的那一台自己不控制變因 |

另有 `water-box-bench` 的初溫概念**完全沒有狀態變數**（Q5 要複驗的四項修法之一）、`no-endpoint` 預測帶與被迫判定的邏輯矛盾、T2 授予時點錯位一場。

**核心判斷代理權的總結**：第五章 `assertJ*` 缺 concept 參數的坑，第六章在**引擎層完全補上了** —— 六個判定函式全部收 `concept`／`verdict`／`disposition` 參數，是我認定的參考實作（第二章 `assertLaw`）的正確沿用。**但 UI 層把它作廢了兩次**：稽核板把答案印在按鈕上，四個工作台只給「1 正解 + 1 明顯過度宣稱」的二選一。

## 一、每個互動的敘事鋪陳（Q1：套用第四章 K1／K2 檢查角度）

第四章 K1 的病是：**要玩家預測，但沒說這個預測在回答什麼、也沒給依據**。第六章有一個結構性的解藥 —— **來源封條**。`H0-3` 一開場就要玩家把四個來源掛到實物位置，並且**逐一寫下「如果熱真從這裡來，哪裡會先變」**。這一步做完，後面每一個工作台都自動帶著「我在查誰、我預期看到什麼」的框架。這是六章裡最強的鋪陳設計。

11 個 embed 逐項檢查：

### A-1 ｜`chip-capacity-bench` 的任務行只有 8 個字，把場景建立的框架丟掉了

工作台的任務行是 embed 的 `hint`（`chapter-ui.js:7842` 渲染成 `heat6Goal`）。11 條 hint 裡最短的是 H1-1 的：

> **「配成兩組可比較的量熱紀錄。」**

場景層已經把問題講得很清楚（凱斯勒的「碎屑容納熱的本事就該和原來不同」），但玩家一進工作台，畫面上唯一的目標提示是這句純程序性的話。相較之下 `H2-3/e2` 的 hint 是「判斷哪些來源**沒有兌現自己封存的變化**」、`H3-1/e1` 是「再看**封條寫的變化有沒有出現**」—— 這兩條都把問題帶進工作台。

> **建議**：「這一輪要回答：碎屑裝熱的本事，跟原來那塊金屬一樣嗎？兩邊要等重、同溫、同一桶冷水。」

### A-2 ｜`hint` 出現製作端語言（違反劇本自訂的用語邊界）

`HE-1/joint` 的 hint：「四欄與範圍未決都要保留；**這裡不授予 T5**。」

「授予」＋證據代號是獎勵機制的說法，不是故事裡的事。劇本第 73 行自己規定「玩家可見系統文案不出現 `flag`、`embed`、`run`、`正解卡`、`錯答卡`、`生成` 等製作端詞」，「不授予 T5」屬於同一類。（T 代號本身在台詞裡是合法的 —— `HE-1/c1`「送入 T1 到 T4 的操作和讀數」就很自然，因為那是桌上的紙。差別在「授予」。）

> **建議**：「四欄與範圍未決都要保留。旅人的最後一欄先不簽。」

### A-3 ｜`airtight-bench` 的封存預測有兩份不同步的記錄

`H2-1` 的節點順序是 `n1 → n2 → n3 → c1（選封存哪種曲線）→ a1 → e1（EMBED）→ ...`。

- **場景層**：`c1` 三選一，正解 `air-necessary` 帶 `effects: [{flag:["ch6AirPredictionSealed",1]}]`，兩個誘答有 `w1`/`w2` 駁回。
- **工作台層**：`sealAirPrediction` 另外收一次同樣的三選一（UI 7920–7922 三顆按鈕），寫進 `lab.airBench.prediction`。

兩者之間**沒有任何同步**：`c1` 只寫 flag，不呼叫 `labAction`。Node 實測 `sealAirPrediction` 對三個值一律接受、一律回同一句「空氣封條已封存」，而且 `judgeAirComparison` 只看 `concept`，**完全不看封存的預測是什麼**。

所以玩家可以在故事裡替凱斯勒押「密合後應變慢」，走進工作台再押「密合後應更快」，全程零阻力，最後 T3 照樣成立。這是敘事層與工作台層的因果斷裂：同一個判斷被問兩次，答案可以不一樣，而且第二次的答案不影響任何結果。

> **建議**（成本最低者）：`c1` 的正解加 `labAction: {action:"sealAirPrediction", args:{prediction:"slower-when-sealed"}}`，工作台端改為顯示「凱斯勒已署名的封條：密合後應變慢」的唯讀卡。判斷只問一次，責任歸屬（這是**對手的**預測，不是玩家的猜測）也更清楚。

## 二、核心判斷是否拆成「選資料」與「資料代表什麼結論」兩步（Q2）

### 引擎層：第五章的坑完全補上了，做法正確

第五章 `assertJ1(state0, ids)` 沒有 concept 參數，我當時的結論是「配對正確就直接由系統講出核心判斷」。**第六章六個判定函式全部收概念參數**：

```js
judgeChipComparison(state0, {concept})       // 需 "chips-not-lower-capacity"
judgeFrictionConditions(state0, {concept})   // 需 "contact-and-motion"
judgeDryStrip(state0, {concept})             // 需 "observed-range-only"
judgeAirComparison(state0, {concept})        // 需 "air-not-necessary"
judgeFiniteSource(state0, {source, verdict}) // 需 "not-fulfilled"
setLatentDisposition(state0, {disposition})  // 需 "motion-unresolved"
```

這是第二章 `assertLaw(state, seriesId, conceptId)` 的正確沿用，而且是**唯一一章把它用在每一個判定上**。方向完全對。

### 但 UI 層把它作廢了兩次

#### B-4 ｜`model-audit-board`（本章高潮判斷）把答案印在按鈕上 —— **最嚴重**

`H3-1` 是本章的模型對帳高潮。凱斯勒 `n2` 說「把每一張紙送回它真正回答的那筆債」，`operationContract` 承諾：

> 「接錯時不亮答案：原紙與債務的條件並排，留下『問的是不同問題』的斷線。」

實際的 UI（`chapter-ui.js:7986-7990`）：

```js
[["chips","T1","碎屑來源 ← T1"], ["air","T3","空氣來源 ← T3"],
 ["cannon","T4","炮身有限存量 ← T4"], ["water","T4","水中有限存量 ← T4"],
 ["condition","T2","接觸運動條件 ← T2"]].forEach(function (item) {
  ship3Btn(box, item[2], function () {
    heat6Do("placeAuditEvidence", { slot: item[0], evidence: item[1] }, ...);
  });
});
```

**每顆按鈕的文字就是那一格的正確答案。**引擎明明有 `audit-placement-mismatch` 這個錯誤碼、也有對照表 `{chips:["T1"], air:["T3"], ...}`，但 UI 從不提供一個能觸發它的操作。玩家要做的是**依序點五顆寫著答案的按鈕**。

這是本章最嚴重的核心判斷代理：不是系統代玩家講出結論，是**系統把結論當成按鈕標籤發給玩家**。而且它落在整章因果鏈的樞紐上 —— 三方定案寫的「玩家把各項證據放進三欄卡片」正是這一步。

> **建議**：改成兩段式，兩段都用既有引擎能力，不必動 `engine6.js`：
> 1. **選原紙**：五個來源欄位各有一個空槽，玩家從 T1–T4 的證據抽屜裡挑一張放進去（按鈕只寫「T1 碎屑與薄片的同一把熱尺」，不寫要放哪一格）。錯放時 `placeAuditEvidence` 回 `audit-placement-mismatch`，`heat6Error` 已經有現成文案（「這張原紙查的不是這個來源；把來源問題與實際操作重新對回」）。
> 2. **T2 的陷阱要留著**：`operationContract` 明寫「T2 只建立接觸轉動條件，不能獨自處決任何來源」。目前 T2 有自己的專屬格子「接觸運動條件」，等於題目已經告訴玩家 T2 不歸任何來源。改法：不要給 T2 專屬格，讓它成為四個來源欄位的一個可選誤答 —— 玩家若把 T2 放進「炮身有限存量」，正好觸發那句斷線提示。

#### B-5 ｜四個工作台的推論步驟是「1 正解 + 1 明顯過度宣稱」的二選一，本章自己的修辭洩了答案

| 工作台 | 正解按鈕 | 唯一的誤答按鈕 |
|---|---|---|
| 碎屑 | 碎屑並沒有顯著較低的熱容量 | **碎屑一定製造了更多熱** |
| 摩擦條件 | 接觸與相對運動同時存在 | **只要壓力存在就夠** |
| 乾式紙帶 | 只主張已觀察時段內持續升溫 | **主張永遠都會以同斜率升溫** |
| 密合對照 | 空氣不是升溫的必要來源 | **密合證明空氣仍從縫裡進來** |
| 潛熱處置 | 有限來源版本退下；運動說仍未證明 | **反例已經證明熱就是運動** |

五個判斷裡，正解**全部都是兩者中較謹慎的那一個**。而整章的教學重點、每一句 NPC 駁回、旅人的每一次收斂，講的都是「不要說超過你的紙」。玩家玩到第三個工作台就會學會一條不必碰物理的規則：**兩個選項裡挑語氣小的那個**。

「乾式紙帶」那一組最明顯：「只主張已觀察時段內」vs「主張永遠都會以同斜率」—— 「永遠」這個詞本身就是答案。

> **建議**：每台補第三個選項，且是**收得太窄**的那一種（不是又一個過度宣稱），讓「挑語氣小的」這條捷徑失效。例如：
> - 碎屑：加「**這張紙什麼都排除不了，兩條曲線本來就會差一點**」（收太窄 —— 忽略了兩線在誤差內重合這個真訊息）
> - 乾式紙帶：加「**這張紙只證明馬轉的時候溫度會動，看不出持續不持續**」（收太窄 —— 否認了自己剛量到的持續性）
> - 密合對照：加「**這張紙只能說皮圈換得好，空氣的事還沒碰到**」（收太窄，且與 `w3`/`w4` 那段皮圈過緊的插曲呼應）
>
> 三選一且誘答一寬一窄，玩家就得真的看曲線。這一步只改 UI 按鈕與 `heat6Error` 文案；`engine6.js` 只需把 concept 白名單從「只有一個合法值」改成「三個合法值、其中一個正確」——見 B-6。

#### B-6 ｜引擎分不出「真的想錯」與「亂送資料」，只有潛熱那一步分得出

Node 實測：

```
judgeChipComparison(s, {concept:'chips-create-heat'})  → error: "chip-judgment-mismatch"
judgeChipComparison(s, {concept:'zzz'})                → error: "chip-judgment-mismatch"   ← 同一個
setLatentDisposition(s, {disposition:'proves-motion'})  → error: "latent-disposition-mismatch"
setLatentDisposition(s, {disposition:'zzz'})            → error: "unknown-latent-disposition" ← 分開了
```

`setLatentDisposition` 是唯一寫對的：先用白名單擋掉不存在的選項，再用 `!==` 擋掉存在但錯誤的選項，兩種回不同的錯誤碼。這正是第二章 `assertLaw` 區分 `unknown-law-concept` 與 `concept-mismatch` 的作法。

**四個工作台判定沒有白名單**，所以引擎無法針對「玩家選了哪一個錯的推論」給不同駁回。目前只有 1 個誤答，勉強能用一句通用文案蓋掉；一旦按 B-5 補到三選一，就必須先補白名單，否則兩個不同的誤答會拿到同一句無效的駁回。

> **建議**（每個判定 2 行）：
> ```js
> var CHIP_CONCEPTS = ["chips-not-lower-capacity", "chips-create-heat", "chips-prove-nothing"];
> if (!has(CHIP_CONCEPTS, args.concept)) return fail(state0, "unknown-chip-concept");
> if (args.concept !== "chips-not-lower-capacity") return fail(state0, "chip-judgment-mismatch:" + args.concept);
> ```

#### 做得好的一步：`source-prediction-verdict` 是唯一真正兩段式的判斷

`judgeFiniteSource(state0, {source, verdict})` 要玩家**逐一**對四個來源各下一個判讀，UI 每張卡給三個判讀選項（預測未兌現／本輪尚未走到終點／預測已命中），而且 `sealState` 從 `intact` 轉 `cracked` **只在玩家提交判讀時發生** —— 封條不會自己裂。這是「資料在那裡，但要由你說它代表什麼」的正確形狀，也是全章最好的判斷設計。（但有 B-3 的邏輯問題。）

## 三、前向引用與因果斷裂（Q3）

### C-1 ｜沒有前向引用未定義概念 —— 這一章守得很乾淨

我逐場檢查每個名詞第一次出現的位置：

| 概念 | 首次出現 | 是否先定義 |
|---|---|---|
| 熱質 | `H0-1/c1` 的選項語境 → `H0-3/n2` 凱斯勒完整說明「可以藏在物體裡，也可以在物體之間流動」 | ✅ |

### C-2 ｜「問題問了但下一場不回答」——只有一處，而且是刻意的

`H3-2/n10` 朗福德「那最後一欄呢？你一直不肯替我寫滿的那一格。」→ `n11` 旅人「等所有人簽完再放。今天到這裡為止。下一次從那一格開始。」

這個問題在 `HE-1/x_final` 得到回答（兌換率：未量得）。**不是斷裂，是章內伏筆的正確回收。**

### C-3 ｜T2 的取得通知晚了一場（Node 已驗）

- `H1-2/e1` 的 `until` 是 `{heat:"friction"}`，`gate("friction")` = `evidence.t2`。所以**要離開 H1-2 的工作台，T2 就必須已經成立**。
- Node 實測：`judgeFrictionConditions` 之後 `evidence = {t1:true, t2:true, ...}`；接著 `runDryStrip` + `judgeDryStrip` 之後 evidence **一個字都沒變**（`judgeDryStrip` 只設 `dryBench.judged`，不 grant 任何證據）。
- 但「取得證據 T2」這條系統通知寫在 **`H1-3/t2`**，也就是乾式紙帶判定之後。

於是：玩家在 H1-2 拿到 T2，整個 H1-3 期間證據清單裡都有 T2，然後在 H1-3 尾端才收到「取得證據 T2」的通知。通知把 T2 歸功給了乾式紙帶。

而 T2 的敘述文字「只有接觸轉動才持續升溫。**短時段內未見衰減**，但兩模型尚未分開」確實是兩台的合成物 —— 前半是 H1-2 的、後半是 H1-3 的。所以設計意圖看得出來是「兩台合起來才算一筆證據」，但引擎在第一台就發了。

> **建議**（兩種都可，選一）：
> 1. **把授予延後**：`judgeFrictionConditions` 不 grant，改由 `judgeDryStrip` grant T2；`H1-2/e1` 的 `until` 改看 `frictionBench.judged`。通知位置不動。這比較符合 T2 的文字。
> 2. **把通知搬前**：在 `H1-2` 的 `a1` 之後插一條「取得證據 T2｜只有接觸轉動才持續升溫」，`H1-3/t2` 改成「T2 補註｜短時段內未見衰減，兩模型尚未分開」。

## 五、四項核心修法的體驗複驗（Q5）

### E-1 ｜H2-2 初溫鋪陳：**敘事滿分，互動零分**

**敘事層做得很好。**史坦格 `a1` 把熱平衡基線講得非常具體：

> 「先別開馬。熱水碰冷杯，杯子自己就會暖。炮頭和水若不是從差不多的溫度起步，開機前就先多出一筆熱，那一筆不能算給摩擦。」

`n5` 再給可見狀態：「三支溫度計分別靠近摩擦處、箱壁與水面。在馬匹尚未起步時，三個讀數只差不到一個小格。」`operationContract` 也承諾：「水與炮頭初溫差過大時，未啟動就會先出現一段自然熱交換曲線。」

**互動層完全沒有這個概念。**`waterBench.draft` 只有四個欄位：

```js
waterBench: { draft: { water: 18, sealed: false, leakChecked: false, sampling: false }, ... }
```

**沒有炮頭溫度，沒有水溫可調 —— 連 `water: 18` 都沒有 UI 控制項。**UI 把「起始水溫 18°」印出來，看起來像個可調參數，其實是唯讀標籤。四顆按鈕（扣皮圈／檢漏／放溫度計／封存起點）**任意順序按完就過**，`prepareWaterBox` 硬要求 `water === 18` 而 draft 一開始就是 18。

所以：**玩家聽了一整段「起點沒對齊就會多出一筆不能算給摩擦的熱」，然後做的事情是按四顆沒有先後、沒有錯誤可能的按鈕。**這一課完全靠台詞送達，互動沒有承接。

> **建議**（成本中等，但這是本章教學價值最高的概念之一）：
> 1. `waterBench.draft` 加 `cannonTemp`（初始值故意設成 32，與水的 18 差很多）。
> 2. UI 加兩顆按鈕：「先讓炮頭在水裡靜置到同溫」（把 `cannonTemp` 降到 18）／「不等了，直接封存起點」。
> 3. `prepareWaterBox` 改為：`cannonTemp !== water` 時**仍然放行**（本章的原則是不亮紅燈），但 `addRecord` 標 `preheat: true`，並在 `continuous-run` 的第一格前插一段自然回溫讀數。
> 4. 這樣 `H2-2/w3`／`w4` 那兩條已經寫好的台詞就有了觸發路徑，史坦格「起點沒對齊。這張留著當自然回溫紙」也才成立。

### E-2 ｜預測帶封存機制：機制成立，但有一個邏輯矛盾與一組永久誘答

**做對的部分**（值得當範本）：
- `setFinitePrediction` → `sealFinitePredictions` 兩段式，四個來源全部押完才能封蠟；封蠟後 `sealed` 為真，`setFinitePrediction` 直接 fail。
- `runContinuousSegment` **fail closed**：`if (!state0.finiteSources.sealed) return fail(...)`，並且原始碼註解寫明「R-CH6-01：實驗鍵本身 fail closed，不依賴 UI 是否顯示」。這是我在第一到五章沒見過的謹慎程度。
- 封條 `intact → cracked` **只在玩家提交判讀時轉態**，註解「封條裂而不消失：只有玩家提交判讀才可轉態」。曲線越過預測帶不會自動裂 —— 判斷權真的在玩家手上。
- UI 正確實作了契約的限制：`if (source === "chips" || source === "air") choices.push(["no-endpoint", ...])` —— 「目前無法標出終點」**只對碎屑與空氣開放**，炮身與水被迫在前兩帶擇一，完全符合契約的「不能把有限來源偷放進沒有終點」。

**問題一：`no-endpoint` 與被迫判定互相矛盾（Node 已驗）**

玩家可以把碎屑押進「目前無法標出終點」。長跑結束後，`judgeFiniteSource` 只接受 `not-fulfilled`：

```
cannon 判 insufficient → error: "source-verdict-mismatch"
cannon 判 not-fulfilled → 接受
```

於是玩家對一張自己剛剛聲明「無法標出終點」的預測帶，被迫判定「**預測未兌現**」。一個沒有終點的預測不可能未兌現。而契約自己寫著：

> 「『目前無法標出終點』只能維持未決，不能被記成預測命中，**也不能冒充已遭排除**。」

引擎強迫的正是契約禁止的那個「冒充已遭排除」。

> **建議**：`judgeFiniteSource` 依該來源的 band 決定合法判讀 —— band 為 `no-endpoint` 時只接受 `insufficient`，`soon`／`within-shift` 時只接受 `not-fulfilled`。`finiteSources.complete` 的條件改為「四個來源都有判讀，且至少炮身與水為 `not-fulfilled`」。這樣「未決」才真的是一個可以走的結局，而不是一個必須繞開的陷阱。

**問題二：`insufficient` 與 `fulfilled` 是四張卡上的永久誘答**

UI 每張卡給三個判讀鈕，但 `judgeFiniteSource` 對所有來源都只收 `not-fulfilled`。所以「本輪尚未走到終點」與「預測已命中」在**四張卡上都永遠是錯的**。玩家點第二張卡時就會發現規律。修好問題一同時解決這個。

**問題三：引擎缺 UI 已有的守衛**

`setFinitePrediction` 接受任何 `(source, band)` 組合 —— Node 實測把 `cannon` 與 `water` 放進 `no-endpoint` 都被接受，四個來源全押 `no-endpoint` 也照樣能封蠟。契約的限制只活在 UI 的一行條件式裡。這對正常遊玩沒有影響（玩家點不到那個選項），但存檔匯入或 API 直呼就能繞過。**這與我在跨章存檔盤點提出的原則同類：驗證不能只長在 UI 上。**

### E-3 ｜HE-1 簽名時序：**做得最好的一項，敘事與程式互相咬合**

**程式層**是兩段式且原子成立：

```js
/* R-CH6-03：此 action 只確認暫稿；旅人不簽名、不授 T5、不完章。 */
function prepareJointPage(...) { return { ..., draftReady: true }; }   // :406

/* x_final 原子成立：第二筆債、四方署名、T5 與 complete 不留半成品。 */
function finalizeJointPage(state0, args) {                             // :418
  if (args.rateDebt !== "conversion-rate-unmeasured") return fail(...);
  state.jointPage.rateDebt = args.rateDebt;
  state.jointPage.signedBy = { stang:true, kessler:true, rumford:true, traveler:true };
  state.jointPage.complete = true;
```

`gate("joint-draft")` 要 `scopeDebt` 已寫＋四欄齊全；`gate("complete")` 要 `jointPage.complete && evidence.t5`。**「範圍未決先、兌換率後、且兌換率與四方署名一起成立」被寫成了不可拆的程式不變量。**

**敘事層的鋪陳同樣清楚，玩家看得懂為什麼還不能簽**：
- `n10`「最後只剩旅人的欄。上半已寫著『範圍未決』，下半還是一個空框，**和西雷莊園那頁幾乎一樣**。」—— 用第五章那個未決空白當視覺回聲，玩家不需要解釋就知道這個空框意味著什麼。
- `a2`「旅人把『範圍未決』釘進最後一欄，卻把筆放在空框旁。**第二筆債還沒寫下，這一欄暫時不能簽。**」—— 直接說出理由。
- `t5`「共同頁暫存｜前三欄已署名。旅人欄只有『範圍未決』，第二筆債與最後簽名仍空著。」

三層（狀態機／stage 敘述／system 通知）講同一件事且不衝突。**這一項不必改，唯一的瑕疵是 A-2 的「不授予 T5」用語。**

### E-4 ｜結尾不劇透：**達成，且交棒指向明確**

- 禁用詞實測：焦耳／能量守恆／分子／卡路里／動能 在 `scenes6.json` **各 0 次**。
- `HE-1/c3` 三個選項都是「換 X，比較 Y」的同構形式，正解「換幾套不同裝置，逐次比較機械作用和升溫能否固定對上」指向方法，不指向答案。

- `HE-1/n11` 史實頁補了那行「比熱與量熱方法在熱質框架中成長，後來仍被不同理論沿用。能留下好尺，不等於對尺的解釋永遠正確」，讓沒觸發認識論補刀的玩家也拿到這一課。
- `H2-3/e1` 的 18.77 磅／60°F 是 Rumford 自己的單位，且契約註明「數字只出現在儀器與史實頁，不由角色背成課文」。

**四項修法裡三項落實良好，一項（H2-2 初溫）只落實在敘事、沒落實在互動。**

## 六、其餘互動層落差（Q1／Q2 的延伸）

### P0-2 ｜`continuous-run-bench`：本章的「新動詞」目前是按六次任意鍵（Node 已驗）

三方定案把這一台認定為本章的新動詞：「管理一個**不會自己停下來的持續過程**（工時、鈍鑽、水量、累積熱曲線）—— 前五章量的都是離散試次，本章第一次量連續累積量。」

`operationContract` 承諾：
> 「條件穩定時『續鑽』才能多記下一格；馬速漂移時『校準』、水位下降異常時『修漏』才是合理動作。」
> 「盲目續鑽不扣血：曲線會在相應位置折斷、變斜或失去水量基準，留下可讀後果。」

實際：

```js
var temperatures = [31, 47, 65, 83, 96, 100];
var row = addRecord(state, "continuous-segment", {
  segment: index + 1, action: args.action, minutes: (index + 1) * 30,
  temperature: temperatures[index], horsePace: "steady", pressure: "fixed",
  leak: args.action === "repair-leak" ? "repaired" : "none"
});
```

溫度只吃 `segments.length`。`action` 被記錄但不影響任何數值。`horsePace` 與 `pressure` 是**字面常數** —— 原紙永遠聲稱條件穩定。Node 實測：

```
全程亂按 action ：31/continue 47/calibrate 65/continue 83/calibrate 96/continue 100/calibrate
全程都按續鑽  ：31/continue 47/continue 65/continue 83/continue 96/continue 100/continue
```

**溫度序列完全相同。**沒有馬速漂移狀態、沒有水位狀態、沒有曲線折斷。UI 甚至把「馬速穩定｜壓力固定｜水位刻線可見」寫成硬編字串顯示給玩家。

史坦格 `n2` 說「每半小時你只有三件事可做：續鑽、停下校準、先修漏。**別為了追溫度，把一張壞紙追到底。**」—— 這句話預設了一個會產生壞紙的機制，那個機制不存在。

> **建議**（這是本章投資報酬率最高的一項，因為它是招牌機制）：
> 1. `continuousRun` 加 `drift`（馬速漂移計數）與 `waterLevel`。
> 2. 每段開始時依 `segments.length` 用**決定性**規則（不用 RNG，維持純函式）產生擾動：例如第 2 段馬速漂移、第 4 段水位下降。
> 3. `continue` 在有擾動時仍然放行，但該格 `temperature` 記為 `null`、`gaps: ["horse-pace-drift"]`；`calibrate`／`repair-leak` 清除對應擾動並讓下一格恢復。
> 4. 完成條件從「六格」改為「六格**乾淨**讀數」，壞格保留在原紙不刪。
> 5. 這樣 `H2-3/w1`／`w2`／`w3` 那三段已經寫好的壞紙台詞就有了觸發路徑，史坦格「可我只能簽『煮開』，不能簽這段升溫一路怎麼來」也才有意義。

### P0-3 ｜`chip-capacity-bench`：教控制變因的那一台自己不控制變因（Node 已驗）

`operationContract` 承諾：「質量或初溫不同時不亮紅燈；**兩條紙帶會從不同起點展開，留下肉眼可見的爛對照**。」

Node 實測：

```
乾淨   clean=true   chipCurve [18,26,31,34]   plateCurve [18,25.8,30.9,34.1]
少一半 clean=false  chipCurve [18,26,31,34]   plateCurve [18,25.8,30.9,34.1]
兩次曲線是否完全相同: true
```

`runChipComparison` 的曲線是硬編的，只有第一個元素取 `draft.waterTempA`／`waterTempB` —— 而這兩個欄位**UI 沒有控制項**，永遠都是 18。所以「故意少放一半碎屑」的唯一後果是 `clean` 旗標翻成 false，**畫面上兩條曲線一個數字都沒變**。

而且 UI 只暴露兩顆設定鈕：「故意少放一半碎屑」／「恢復等質量」。按鈕文字自己寫著「故意」，等於告訴玩家這是錯的選項；draft 預設就是乾淨的（4/4、60/60、8/8、18/18），所以玩家**直接按主按鈕就能拿到乾淨對照**，從來不需要自己把三個條件對齊。

朗福德 `n3` 那句「等重、同溫、同一桶冷水。**少一項，他就會說你比較的是兩件事。**」設定了一個任務，工作台已經替玩家完成了。

> **建議**（成本低）：
> 1. `chipBench.draft` 初值改成**不對齊**（例如 `chipMass: 2, plateMass: 4, chipTemp: 60, plateTemp: 45`），讓玩家必須自己對齊三組條件才能拿到乾淨紙。
> 2. `runChipComparison` 的曲線改為由 draft 計算 —— 至少讓起點跟著 `waterTempA/B` 走、讓斜率跟著質量比走，兌現「從不同起點展開」的承諾。
> 3. UI 把「故意少放一半碎屑」改成中性的「碎屑：2 錢 / 4 錢」與「初溫：45° / 60°」兩組切換，不要在按鈕上標示對錯。
