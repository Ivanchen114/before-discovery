# 《發現之前》第六章互動劇情設計盤點（Codex，2026-08-03）

## 一、審查範圍與方法

- 主審 runtime：`greybox/data/scenes6.json`、`greybox/src/engine6.js`。
- 玩家可見互動：`greybox/src/chapter-ui.js` 的 `renderHeat6()`。

- 依 `next`、`options[].next` 與 embed gate 還原實際遊玩順序，不依 JSON 陣列排列推測。
- 每拍都用同一條因果鏈檢查：**上一缺口 → 為何要判斷 → 玩家實際決定什麼 → 可見結果 → 玩家親自說出什麼 → 誰因此改變 → 下一缺口**。

## 二、總裁決

**章的宏觀因果是成立的，但十一座互動台只有約一半真正把判斷交給玩家。** H0 的案件成立、H2-1 的空氣對照、H3-2 的共同頁衝突與 HE-1 的最後交棒都很清楚；最好的拍是結尾 `n13 → c3 → x_pre → x_final`，玩家先看兩頁資料，再親自提出要找跨裝置換法，NPC 沒有提前代答。

主要問題有四類：

1. **UI 先做完結論，劇情再問一次同題**：H1-1、H1-2、H1-3 都中。
2. **預測真的被封存，卻沒有真的控制或約束後果**：H0-3 來源簿、H2-2 預測帶都中。
3. **看似有三種操作，實際都推進同一結果**：H2-3 最嚴重。
4. **劇本寫了可讀失敗，runtime 沒讓玩家進去**：多座工作台的 w 節點沒有任何可達入邊。

若不修，玩家仍可通關，也會讀懂 Rumford 實驗的大意；但他會感到自己在「完成已經寫好的審計清單」，而不是用自己的預測逼兩套模型留下後果。

## 四、P0：動工前必修

### P0-1｜H2-2/n8 → H2-3/e2：預測帶有狀態，卻沒有有效的可否證語意

**現況**

- 玩家可替 `chips`、`air` 選「目前無法標出終點」，替四來源選「很快／本班」並封存。
- `runContinuousSegment()` 不讀預測帶，固定產生 `31, 47, 65, 83, 96, 100`。
- `judgeFiniteSource()` 不看來源與 band，只接受 `not-fulfilled`；連「目前無法標出終點」也能被判為「預測未兌現」並裂封。

**Node 實測**

```text
chips = no-endpoint
跑完六格
judgeFiniteSource(chips, not-fulfilled)
→ ok=true，封條 intact→cracked
```

這不是玩家判錯，而是題目沒有可成立的推理：有限觀測無法推翻「目前無法標出終點」。同時，T1 已讓碎屑版本退下、T3 已讓空氣必要來源退下，H2-2 又把兩者重新當成待押的有限來源，案件時間線倒退。

**建議修法**

1. H2-2 預測帶只處理仍在場的「炮身有限存量」「水中有限存量」；碎屑與空氣保留舊裂封／撤回紙，作為 H3 再使用，不重新下注。
2. 帶子不要猜無依據的分鐘，改押**來源特有的可見後果**：炮身應先冷／斜率應變小；水若供熱應有一處先冷或供不動。
3. engine 依 `band + observed trace` 判定，不得統一只收 `not-fulfilled`。
4. 若保留 `no-endpoint`，正確判讀只能是「本輪不足」，封條保持 intact，不得計入 T4 已排除來源。

### P0-2｜H2-3/e1：三個操作鍵是假的因果選擇

`continue`、`calibrate`、`repair-leak` 都直接增加一格，讀到相同固定溫度。介面沒有先揭示「這一格鼓點亂了／漏水了／條件穩定」，玩家無從判斷，按哪一鍵都通。

Node 實測：

```text
continue   → 31°
calibrate  → 47°
repair-leak→ 65°
continue   → 83°
calibrate  → 96°
repair-leak→100°
```

劇本的 H2-3/w1–w3 描寫漏水、換馬漏記與「只能簽煮開」，但這三節點沒有 runtime 入邊，正常 UI 不可能進入。

**建議修法（優先採 A）**

- A：每格先翻一張可見現場狀態（穩定／鼓點偏／漏水），玩家才選續鑽、校準、修漏。選對留下乾淨格；選錯留下洞，並路由到 w1–w3 的角色反應。舊壞格不刪。
- B（低成本）：若不做事件狀態，就只留「續鑽半小時」一鍵。真實的單一操作勝過三個沒有差別的假選擇。

### P0-3｜H1-1／H1-2／H1-3：工作台已替玩家說完，劇情又重問一次

三座 embed 的 gate 都綁在 `judged`／evidence：

- H1-1 UI 必須先選「碎屑並沒有顯著較低的熱容量」，離開後 c1 再問「這組紙最多支持到哪裡？」
- H1-2 UI 必須先選「接觸與相對運動同時存在」，離開後 c1 再問同一關係。
- H1-3 UI 必須先選「只主張已觀察時段內持續升溫」，離開後史坦格攔下 Rumford，c1 再選同一句。

這使戲劇高潮變成複誦。玩家第一次的判斷留在沒有角色的 UI，第二次只是在對 NPC 重填答案。

**一次修三場的低成本方案**

1. embed 只取得乾淨原紙，gate 改成 `record-ready`，不在 UI 判結論。
2. 回到故事後，讓 c1 成為唯一結論選擇。
3. 正解 option 的 `effects` 呼叫對應 `judgeChipComparison`／`judgeFrictionConditions`／`judgeDryStrip`，再授證或轉 phase。
4. 原 UI judgement button 移除；錯答由現有人物 w 節點承接。

這正好恢復「選資料／產生資料」與「資料代表什麼」兩個獨立步驟，而且不需要新增故事節點。

### P0-4｜H0-3/e1：開場模型承諾沒有被後文使用

玩家把四來源掛到位置、填可見後果、封兩模型；但 engine 只驗非空字串。四來源全部填成同一位置、同一後果，兩模型填任意文字，也能 `sealModels()` 成功。後續 H1/H2 沒有任何函式讀回 `sourceLedger.placements`、`consequences` 或 `modelPredictions`。

Node 實測：

```text
四來源 position =「同一位置」
四來源 consequence =「同一後果」
caloric/motion = 任意非空字串
→ sourceLedger.sealed = true
```

因此第一個模型預測只是入場表單，不是後面被打臉或修補的承諾。

**建議修法**

- 每來源只顯示與實物相符的 2–3 個後果，engine 做 source-specific allowlist。
- H1/H2 的每張新封條都必須顯示「它從 H0-3 哪一筆來源承諾長出來」。
- H3 對帳板直接重用 H0-3 原始來源紙，而不是另建一套固定 mapping。

## 五、P1：重要但可在 P0 後處理

### P1-1｜H2-1/c1 與 airtight embed 重複封同一個預測

故事 c1 已讓玩家選「若空氣必要，密合後應變慢」，a1 又明說凱斯勒寫下並封存；進 embed 後 UI 再問一次同樣三個選項，真正的 `sealAirPrediction()` 只在第二次發生。

**修法**：讓 H2-1/c1 正解直接呼叫 `sealAirPrediction`；embed 只負責開放／密合兩組操作與曲線判讀。故事封條與 engine 封條應是同一次動作。

### P1-2｜H2-2 初溫鋪陳順序正確，但玩家沒有真的對齊初溫

四項核心修法之一在故事圖上已成立：實際順序為 `n4 → a1（熱水碰冷杯）→ c1 → e1`。玩家先有生活類比，再選必記欄位。

但水箱 UI 的水溫預設就是 18°，玩家只能扣皮圈、檢漏、放溫度計；沒有看見炮頭與水從不同溫度靠近，也沒有做「等待到三支讀數接近」的動作。判斷依據說清楚了，操作仍被預設值代做。

**低成本修法**：進台時先顯示三支不同讀數，新增「先靜置一段」；數字逐步靠近後才允許封存起點。答錯仍保留自然回溫紙並接 H2-2/w3/w4。

### P1-3｜H3-1/e1 對帳板把正確配對寫在按鈕上

UI 直接顯示「碎屑來源 ← T1」「空氣來源 ← T3」「炮身有限存量 ← T4」；玩家不是配對，只是逐鍵確認。這與 e1「把每張原紙送回真正回答的債」不一致。

**修法**：畫面左側放未指派的 T1–T4 卡，右側放來源槽；每槽提供多張可信候選，錯配留下卡片位置並由原紙上的變因指出不合。低成本版本可用 select，不必拖曳。

### P1-4｜HE-1/c2 重複 H3-2/c2，沒有新增判斷

H3-2/c2 已由玩家寫下「範圍未決」，並透過 `writeScopeDebt()` 存入 state。HE-1/joint 完成後，c2 又要求選「保留已退下來源，也保留潛熱與未查現象」；正解只檢查同一 flag，不產生新作用。

**不新增節點的改寫**：把 HE-1/c2 改問真正尚未完成的事：

> 旅人的欄現在能簽嗎？

- 「先不簽。第二筆債還空著。」（正解，接 a2）
- 「先簽，第二筆以後再補。」
- 「把空框裁掉，只簽範圍未決。」

這會直接服務已修好的簽名時序，而不是重考範圍。

### P1-5｜共同驗證頁應是責任儀式，不必偽裝成分類題

HE-1/c1、n4–n9 已逐人說明誰能簽什麼；joint UI 再用「史坦格／凱斯勒／朗福德」具名選項填四欄，答案已全在眼前。這不是壞事，但它是**表演責任**，不是新推理。

**修法**：改成把四人的具名簽名牌放入已確立欄位，著重「誰拒簽哪一段」的動畫與聲音；不要提供明知錯誤的姓名選項來假裝解謎。真正判斷保留給 c2 的簽名時機與 c3 的下一年代問題。

### P1-6｜embed 失敗多半只有 UI 文字，劇本的角色後果未接線

以下 active 節點沒有敘事入邊，正常操作不會看見：

- H1-1/w1–w2：髒量熱紙。
- H1-3/w1–w2：漏拍／改條件紙。
- H2-1/w3–w4：皮圈增加摩擦。
- H2-2/w3–w4：未開機先自然回溫。
- H2-3/w1–w3：沸騰但原紙有洞。

**修法**：engine 回傳可持久的 failure kind，embed 退出時依 kind 路由到既有 w 節點；修復後再回工作台。若某種失敗在現行 UI 根本不可能發生，就刪除對應互動承諾或真正做出該狀態，不要讓劇本和 runtime 各自講一套。
