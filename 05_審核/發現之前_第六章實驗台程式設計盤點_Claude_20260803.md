## 摘要

**引擎的骨架是六章裡最好的。** 六個判定函式全部收概念參數（第五章 `assertJ*` 的坑完全補上）、`runContinuousSegment` 明文 fail closed、封條 `intact→cracked` 只在玩家提交判讀時轉態、`finalizeJointPage` 原子成立。這些是前五章沒有的謹慎程度，而且原始碼註解直接標了 `R-CH6-01`／`R-CH6-03` 的法源。

**但十一座台的實作深度差距極大：最好的 4.4 分，最差的 1.0 分。** 而且低分的兩座剛好是本章的招牌機制（長時段續鑽）與高潮判斷（模型稽核板）。

**規格對照的結果比我預期嚴重**：規格 §八 明文寫「不得退化為十一張文字問卷」，而目前第六章區段的 UI 是 **34 個 `ship3Btn` + 6 個 `heat6Select`，零拖放** —— 已經正是規格禁止的那個形狀。同時規格 §五 指定的「兌現／未兌現／不足」三種判讀，引擎只接受一種；`R-CH6-04` 有 2 處實際違例。

**新測出 5 條捷徑**，其中 2 條是這次才發現的：`runAirComparison` 的 `clean` 由呼叫方自己宣告、`setLatentDisposition` 完全沒有前置閘門（全新存檔可直接判潛熱）。

### 各台評分理由

**3｜`friction-condition-bench` 4.2 — 全章最佳，建議當其他台的範本**

三種條件的曲線是真的分開的，而且方向正確：

```js
"rotation-only":  [18, 18.1, 18,   18.1]   // 只轉不碰：室溫漂移
"pressure-only":  [18, 18.2, 18.2, 18.3]   // 只壓不轉：沒有持續增溫
"contact-motion": [18, 23,   29,   36  ]   // 接觸轉動：持續上升
```

`runFrictionCondition` 有 `friction-condition-already-run` 守衛（同一條件不能重跑刷數據），`judgeFrictionConditions` 要求三種全部完成。**物理映射 5 分是全章唯一。**扣分只在推論步驟是二選一（見二-B）。

**11｜`joint-verification-page` 4.2 — 捷徑風險唯一的 5 分**

`setJointColumn` 要求 `args.text === JOINT_VALUES[args.column]`（責任放錯欄直接拒絕）、`prepareJointPage` 只回 `draftReady` 不授證、`finalizeJointPage` 原子寫入 rateDebt + 四方署名 + T5 + complete。`gate("joint-draft")` 與 `gate("complete")` 兩段分離。**R-CH6-03 完整落實，這是全章唯一一座我找不到任何繞過路徑的台。**

**9｜`source-prediction-verdict` 3.8 — 可見後果唯一的 5 分**

```js
/* 封條裂而不消失：只有玩家提交判讀才可轉態。 */
state.finiteSources.sealState[args.source] = "cracked";
```

曲線越過預測帶**不會**自動裂封 —— 判斷權真的在玩家手上，這是「資料在那裡，但要由你說它代表什麼」的正確形狀。裂封後原押記仍在原位。扣分在只接受 `not-fulfilled`（見二-C）。

**4｜`dry-strip-bench` 3.6 — 證明 H1-1 本來可以做對**

`clean` 由 draft 推導、髒紙的曲線真的有洞：

```js
curve: clean ? [18,24,31,39,48] : [18,25,null,28,41],
gaps:  clean ? []               : ["conditions-changed"]
```

**同一個檔案、同一位作者，在這一台把「髒紙留下可見後果」做出來了，在 H1-1 卻沒有。**所以 H1-1 的問題不是判準爭議，是實作漏做。扣分在 T2 授予時點（見三-C）。

**7｜`finite-source-prediction-bands` 3.4**

「如果是有限存量，就該在某個時段前變弱」是可否證形式的正確用法，封存帶後續會壓在長紙下方顯示。扣分在引擎端缺 band 限制（見二-D）。

**5｜`airtight-bench` 2.6 — 捷徑風險 1 分**

**1｜`heat-source-ledger` 2.4 — 敘事上全章最強，機制上唯寫不讀**

## 二、捷徑與繞過路徑（Node 實測）

驗證腳本：`scratchpad/h6.cjs`、`h6b.cjs`、`h6c.cjs`。

### A ｜【新發現】`runAirComparison` 的 `clean` 由呼叫方自己宣告

```js
var clean = args.clean !== false;          // engine6.js:233
```

**這是十一座台裡唯一一座不自己判定紙張乾淨的。**對照組：

| 函式 | `clean` 來源 |
|---|---|
| `runChipComparison` | 由 draft 推導（`chipMass===plateMass && chipTemp===plateTemp && ...`） |
| `runDryStrip` | 由 draft 推導（`horsePace==="steady" && ...`） |
| **`runAirComparison`** | **`args.clean !== false` —— 呼叫方說了算** |

`judgeAirComparison` 要求「一張乾淨 open + 一張乾淨 sealed」，而這兩張的乾淨與否來自參數。存檔匯入或 API 直呼都能宣稱乾淨。UI 目前一律傳 `clean: true`，所以正常遊玩看不出來，但這條路等於把驗證外包給呼叫端。

**同時實測：押錯方向的預測完全沒有代價。**

```
押 faster-when-sealed（錯方向）→ 被接受，airBench.prediction = "faster-when-sealed"
接著跑 open + sealed → judgeAirComparison 仍成立 → evidence.t3 = true
```

`judgeAirComparison` 只看 `concept`，**從不比對 `airBench.prediction`**。封存預測在這一台是純裝飾。

> **修法**：① `clean` 改由引擎依 `state0.dryBench` 的條件卡與本次條件推導（或至少改成 `args.clean === true` 需附條件證明）。② `judgeAirComparison` 加一條：`if (state0.airBench.prediction !== "slower-when-sealed") ` 時走「你替凱斯勒押的方向和他署名的不一致」分支 —— 這一台的預測本來就是**對手的**，押錯應該由對手抗議，這是免費的敘事機會。

### B ｜【新發現】`setLatentDisposition` 完全沒有前置閘門

```
全新存檔（phase=source-ledger、evidence 全 false）直接呼叫
setLatentDisposition({disposition:'motion-unresolved'}) → 接受
  auditBoard.latentDisposition = "motion-unresolved"
```

其他每個判定都有前置檢查（`t1-required`、`t2-required`、`t3-required`、`t4-required`、`long-run-required`…），**只有潛熱處置沒有**。它是本章唯一計入勝負的敗局動作（三方定案的「主擊」），卻可以在玩家還沒看過 S8、還沒做過任何實驗時就先寫進狀態。

`completeAudit` 仍會被 `audit-board-incomplete` 擋住，所以不構成完章繞過 —— 但它讓「玩家親手把潛熱卡歸進未決欄」這個因果鏈的核心動作可以脫離語境發生，也讓存檔可能帶著一個沒有來歷的 `latentDisposition`。

> **修法**（1 行）：`if (!state0.evidence.t4 || !state0.evidence.s8) return fail(state0, "t4-required");`

### C ｜`no-endpoint` 與被迫判讀互相矛盾，且違反規格 §五

規格 §五 對 `source-prediction-verdict` 寫的是：「每來源並排封存帶與曲線，**逐一選『兌現／未兌現／不足』**」—— 三種判讀。

實作只接受一種：

```js
if (args.verdict !== "not-fulfilled") return fail(state0, "source-verdict-mismatch");   // engine6.js:334
```

實測：

```
cannon 判 insufficient → error "source-verdict-mismatch"
cannon 判 not-fulfilled → 接受
```

後果有兩層：
1. **邏輯矛盾**：玩家可以把碎屑／空氣押進「目前無法標出終點」，長跑結束後卻**被迫**判它「預測未兌現」。一個沒有終點的預測不可能未兌現。而 `operationContract` 自己寫著「『目前無法標出終點』只能維持未決，不能被記成預測命中，**也不能冒充已遭排除**」—— 引擎強迫的正是契約禁止的那件事。
2. **永久誘答**：UI 每張卡給三個判讀鈕，「本輪尚未走到終點」與「預測已命中」在**四張卡上都永遠是錯的**。玩家點第二張卡就會發現規律。

> **修法**：依該來源封存的 band 決定合法判讀 —— `no-endpoint` → 只收 `insufficient`；`soon`／`within-shift` → 只收 `not-fulfilled`。`finiteSources.complete` 改為「四來源都有判讀，且炮身與水為 `not-fulfilled`」。這樣「未決」才是一個可以走到的結局。

### D ｜`setFinitePrediction` 的 band 限制只長在 UI 上

實測：

```
把 cannon 放進 no-endpoint → 接受（未擋）
把 water  放進 no-endpoint → 接受（未擋）
四個來源全押 no-endpoint 仍可封存 → true
```

`chapter-ui.js:7950` 有正確的限制：`if (source === "chips" || source === "air") choices.push(["no-endpoint", ...])`。所以正常遊玩點不到，但引擎沒有對應守衛。

**這與規格 R-CH6-01 的原則直接相關**：規格明寫「UI 隱藏按鈕不算守門」。那條原則在 `runContinuousSegment` 上落實了（有明文註解），在 `setFinitePrediction` 上沒有。

> 附帶：這裡還有一組**三份文件互相不一致**，需要一次裁定：
> | 文件 | 對 `no-endpoint` 的規定 |
> |---|---|
> | 規格 §五 | 四個來源都可用三種帶之一 |
> | `operationContract`（H2-2/n8） | 「水或炮身供應」必須在前兩帶擇一 |
> | UI 實作 | 只有碎屑與空氣可選 `no-endpoint`（＝跟契約一致） |
> | 引擎 | 無限制 |

### E ｜`model-audit-board` 把答案印在按鈕上（劇情盤點已述，此處補程式面）

```js
// chapter-ui.js:7986
[["chips","T1","碎屑來源 ← T1"], ["air","T3","空氣來源 ← T3"],
 ["cannon","T4","炮身有限存量 ← T4"], ["water","T4","水中有限存量 ← T4"],
 ["condition","T2","接觸運動條件 ← T2"]]
```

引擎側完全有能力偵測錯放：

```js
var allowed = { chips:["T1"], air:["T3"], cannon:["T4"], water:["T4"], condition:["T2"] };
if (!allowed[args.slot] || !has(allowed[args.slot], args.evidence)) return fail(state0, "audit-placement-mismatch");
```

`heat6Error` 也有現成文案（「這張原紙查的不是這個來源；把來源問題與實際操作重新對回」）。**整條錯誤路徑蓋好了，UI 從不提供能踩上去的操作。**

這同時牴觸規格 §九 出貨檢核第 1 項「11 座互動台均由 engine state 承重，**沒有 UI 直接授證**」的精神：狀態確實由引擎承重，但 UI 把判斷難度歸零，等於變相授證。

> **修法**（不動 `engine6.js`）：按鈕文字只寫證據名稱（「T1｜碎屑與薄片的同一把熱尺」），五個來源欄位各是一個空槽，玩家自己決定放哪一格。**並且拿掉 T2 的專屬格** —— 目前 T2 有自己的「接觸運動條件」格子，等於題目先告訴玩家 T2 不歸任何來源，而 `operationContract` 要的正是「T2 只建立條件，不能獨自處決任何來源」這個陷阱。

### F ｜來源封條的內容零驗證，且從此不被讀取

```
setSourceLedger({source:'air', position:'水箱內', consequence:'完全無關的一句話'}) → 接受
setSourceLedger({source:'air', position:'.',      consequence:'.'})               → 接受
```

`sealModels` 只驗「四個位置與四個後果都是非空字串」。內容既不檢查合理性，也不在後續任何判定裡被引用（全檔搜尋確認：`placements`／`consequences`／`modelPredictions` 只出現在寫入與完整性檢查處）。

實際影響：玩家在 H0-3 寫下「空氣：隔絕後升溫應變慢」，到了 H2-1 密合對照，**引擎不會拿這句話跟結果對照**；`judgeAirComparison` 只認 `concept`。所以「事前登記可見後果 → 事後驗證是否出現」這個本章最重要的認識論迴路，在程式層是斷開的。

> **修法**（中成本，但這是本章的核心迴路）：把 `consequences` 從自由字串改成 enum（UI 已經是 select，值本來就有限），並在對應的 judge 函式裡比對。例如 `judgeAirComparison` 加：若玩家當初給空氣寫的後果是「隔絕後升溫應變慢」，而曲線顯示沒有變慢，就回一個「你登記的後果沒有出現」的成功分支（這正是 T3 該有的意義）；若玩家當初給空氣寫的是「持續輸出後應衰減」，則這一台根本不是在測他登記的東西 —— 那是一個值得存在的錯誤。

### G ｜`chip-capacity-bench` 曲線硬編，不隨配置變

```
乾淨   clean=true   chipCurve [18,26,31,34]  plateCurve [18,25.8,30.9,34.1]
少一半 clean=false  chipCurve [18,26,31,34]  plateCurve [18,25.8,30.9,34.1]
兩次曲線是否完全相同: true
```

曲線唯一的變數是首元素取 `draft.waterTempA`／`waterTempB`，而這兩個欄位 **UI 沒有控制項**（永遠 18）。`operationContract` 承諾的「兩條紙帶會從不同起點展開，留下肉眼可見的爛對照」沒有兌現。

另外 draft 預設就是全對齊的（4/4、60/60、8/8、18/18），**玩家直接按主按鈕就能拿到乾淨對照**，從不需要自己對齊三個條件 —— 而朗福德「等重、同溫、同一桶冷水。少一項，他就會說你比較的是兩件事」設的正是那個任務。UI 的設定鈕還寫著「**故意**少放一半碎屑」，等於在按鈕上標示對錯。

> **修法**（低成本）：① draft 初值改成不對齊（`chipMass:2, plateMass:4, chipTemp:60, plateTemp:45`）。② 曲線改由 draft 計算：起點取各自的 `waterTemp`，終點依 `質量×比熱` 比例。③ 按鈕改中性（「碎屑 2 錢／4 錢」「初溫 45°／60°」）。`H1-1/w1`／`w2` 那兩條已寫好的爛對照台詞就有觸發路徑了。

### H ｜`continuous-run-bench` 三個操作鍵結果完全相同（本章招牌機制）

```js
var temperatures = [31, 47, 65, 83, 96, 100];
var row = addRecord(state, "continuous-segment", {
  segment: index + 1, action: args.action, minutes: (index + 1) * 30,
  temperature: temperatures[index],
  horsePace: "steady", pressure: "fixed",           // ← 字面常數
  leak: args.action === "repair-leak" ? "repaired" : "none"
});
```

實測：

```
全程亂按 ：31/continue 47/calibrate 65/continue 83/calibrate 96/continue 100/calibrate
全按續鑽 ：31/continue 47/continue  65/continue 83/continue  96/continue 100/continue
→ 溫度序列完全相同
```

`action` 被記錄但不影響任何數值。沒有馬速漂移狀態、沒有水位狀態、沒有曲線折斷。UI 還把「馬速穩定｜壓力固定｜水位刻線可見」寫成硬編字串顯示。

三方定案把這一台認定為本章的**新動詞**（「管理一個不會自己停下來的持續過程 —— 前五章量的都是離散試次，本章第一次量連續累積量」）。目前它是按六次任意鍵。

**唯一做對的是 fail closed**（值得記錄）：

```js
/* R-CH6-01：實驗鍵本身 fail closed，不依賴 UI 是否顯示。 */
if (!state0.finiteSources.sealed) return fail(state0, "finite-predictions-required");
```

> **修法**（見第四節，這是投報率最高的一項）。

### I ｜`water-box-bench` 沒有初溫概念，四顆按鈕任意順序

```js
waterBench: { draft: { water: 18, sealed: false, leakChecked: false, sampling: false }, ... }
```

**沒有炮頭溫度欄位。**`prepareWaterBox` 硬要求 `water === 18`，而 draft 一開始就是 18，UI 也沒有控制項（「起始水溫 18°」是唯讀標籤，卻長得像可調參數）。四顆按鈕（扣皮圈／檢漏／放溫度計／封存起點）無先後、無錯誤可能。

`operationContract` 承諾的「水與炮頭初溫差過大時，未啟動就會先出現一段自然熱交換曲線」不存在，`H2-2/w3`／`w4` 兩條台詞不可觸發。

### J ｜髒紙可無限刷、天數從未被檢查

```
連跑 5 張髒紙：髒紙數 5｜days = 5｜cleanRecordIds = []  → 再跑一張乾淨紙即可判定
連跑 400 天後 days = 400｜還能繼續判定 → true
```

`state.days` 被 6 個函式各加 1 次，但**全檔沒有任何地方讀取它做判斷**（只寫進 record 的 `day` 欄位顯示）。

`H0-2` 建立的期限是敘事層很紮實的：史坦格「借到明晚。後天這門炮要進下一道工序。**炮頭一切，就沒有第二塊一樣的。**」＋馬班簿三段空格＋`H0-2/a5` system「**期限成立**｜炮頭拆除前，必須留下可重做、有人願意署名的原紙」。

**但這是三方定案第四節明文擱置的項目**：

> 「**工時是否做成真實資源額度**：claude 在原提案第八節列為待三方定案的問題之一，尚未有人正面回應；建議下一階段先做『敘事壓力優先、資源額度為次要加強』的預設。」

所以目前的狀態**符合定案的預設**，不算實作漏做。要修正的只是那句 system 文案 —— 「期限成立」承諾了一個機械上不存在的東西。

> **修法**（二選一）：① 最省：`H0-2/a5` 改成「**規矩成立**｜炮頭拆除前，必須留下可重做、有人願意署名的原紙」，把「期限」字樣拿掉。② 若要真做額度：`days` 上限 3（對應馬班簿三段），超過時 `runXxx` 回 `shift-exhausted`，髒紙才有代價。**建議先做 ①，②另開 ADR 決議** —— 因為它會改變整章難度曲線，不該在實作層順手決定。

## 五、總評

第六章的引擎**設計方向是六章裡最正確的**：概念參數普及到每個判定、fail closed 有明文法源註解、封條只在玩家提交時轉態、完章原子成立。規格書本身也是六章裡寫得最細的一份 —— 四條阻斷性契約、十一座台的狀態責任表、出貨檢核清單，都具體到可以逐條打勾。

**問題不在設計，在實作進度不均。** 十一座台裡有三座（摩擦條件、乾式紙帶、共同驗證頁）已經照規格做到位，可以直接當範本；有五座只搭了殼，而其中兩座恰好是招牌機制與高潮判斷。最能說明這件事的是 `dry-strip-bench` 與 `chip-capacity-bench`：**同一個檔案、同一位作者，前者把「髒紙留下可見後果」做出來了，後者沒有。**所以這不是判準爭議，是待補的工。

**最該建立的長期機制**：規格 §九 的出貨檢核已經列出了對的項目，但 R-CH6-04 現在是紅的卻沒有測試在看。建議把「237 個節點的全域順序 + 每個 `refutedBy` 必須指向作答前」寫成資料契約測試 —— 純資料、成本極低、一次寫好永久防守，而且這一類「事後來源」錯誤是人眼最容易漏的。同理，11 個 `operationContract` 應當被當成驗收清單逐條核，它們就在資料檔裡，比再寫一份新文件有效。
