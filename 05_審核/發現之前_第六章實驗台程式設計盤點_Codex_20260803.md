### 方法

每座互動台用五個問題檢查：

1. 玩家操作是否對應真正物理變因。
2. 玩家選擇是否改變數據、可見後果或後續主張。
3. 結果是否以實物、曲線、原紙或封條呈現，而不是只顯示成功文字。
4. 每次必要點擊是否支付新判斷、新觀察或責任。
5. 正常 UI、直接 Engine action 或讀檔是否存在跳過判斷的路徑。

另以 Node 直接呼叫 `Engine6`。本文嚴格區分：

- **UI 捷徑**：一般玩家真的能按到。
- **引擎捷徑**：正常 UI 沒有入口，但新的 caller、測試或匯入資料可繞過。
- **固定流程問題**：不是非法 exploit，卻讓玩家不必理解物理也能通過。

### 基線

本輪重新執行：

```text
cd greybox && npm test
156 通過，0 失敗
```

自動測試綠燈證明現有資料契約互相一致，不證明十一座互動台好玩、物理判讀有效或真人看得懂。本文未做瀏覽器與手機真人完整通關。

## 二、設計契約：第六章本來要把什麼交給玩家

規格的分工原則是：**引擎算數值，玩家選資料、解讀資料、限制主張並承擔署名。** 第六章另有三項具體承諾：

- 預測、操作、讀數與判讀要留在同一張可追查的紙上。
- 每個必要按鈕須支付新的判斷或觀察，固定流程不得偽裝成選擇。
- 主要動詞應是掛來源紙、封條、跑紙帶、逐來源判讀與署名，不得退化成十一張文字問卷。

現行 Engine6 的**狀態完整性高於玩法完整性**：T4 不會自動授予、裂封不會消失、T5 與四方署名確實原子成立；但多數互動仍以固定按鈕、下拉選單與成功訊息代替可讀物理後果。

## 三、總裁決

**第六章目前是可靠的里程碑狀態機，但還不是成立的實驗遊戲。**

值得保留的底層骨架有四項：

1. 所有 action 純函式、失敗不改 state。
2. 預測封存後不可改寫。
3. T4 只有四來源逐一判讀後才授予。
4. T5、兩筆未決、四方署名與完章只在 `x_final` 原子成立。

阻斷玩家代理權的問題有五項：

1. H0-3 來源帳只驗非空字串，位置、後果與模型文字都不需正確，也不會被後續實驗重用。
2. H1 多座工作台使用固定 fixture；髒碎屑紙甚至和乾淨紙顯示完全相同曲線。
3. H2-3 三個動作鍵都播放同一條固定曲線，沒有現場狀態可判斷。
4. `judgeFiniteSource()` 不讀來源與預測帶，只接受四次 `not-fulfilled`，可把不可否證的 `no-endpoint` 強制判死。
5. H3／HE 的配對答案直接寫在按鈕或姓名選項上；共同頁「確認暫稿」按鈕可跳過且完全不改 state。

整章最接近好玩法的是**空氣密合對照的概念骨架**：先封存預測，再做開放／密合兩份資料，再縮限來源主張。但現行 UI 把封存預測藏掉、曲線不標條件、引擎也不比較預測，因此尚未完整兌現。

## 五、逐站程式盤點與可執行修法

### 5.1 H0-3｜來源追債台

**程式現況**

- `engine6.js:82–108` 只檢查位置、後果與兩模型預測是非空字串。
- `chapter-ui.js:7849–7882` 給四來源完全相同的位置／後果選單；四張紙可全部掛同一處、寫同一後果。
- 一張紙首次掛上後，UI 立刻隱藏選單，封蠟前也不能修正；Engine 反而允許覆寫。UI 與引擎的承諾不一致。
- 後續 H1–H3 不讀 `sourceLedger.placements`、`consequences` 或 `modelPredictions`。開場承諾只是表單，不是因果變數。

**Node 實測**

```text
四來源 position = 同一位置
四來源 consequence = 同一後果
caloric = 任意字串甲；motion = 任意字串乙
sealModels → ok=true，sourceLedger.sealed=true
```

**修法**

1. 以 source-specific allowlist 或配對表限制每個來源可選位置與可見後果。
2. 封存前保留「拆下重掛」，封存後才不可改。
3. 每個後續工作台標明正在查哪一張來源紙，判讀時讀回原後果，不另寫一套答案。
4. `sealModels()` 驗證模型 enum，不收任意文字。

### 5.2 H1-1｜碎屑量熱

**程式現況**

- `runChipComparison()`（`engine6.js:120–134`）只用條件判 `clean`；曲線幾乎固定，不隨質量、初溫或水量計算。
- `setChipDraft()` 接受任何有限數，包含負質量與極端溫度。
- UI 預設就是乾淨配置，玩家可不做任何設定，直接按「浸入兩杯水」。
- `heat6Records()`（`chapter-ui.js:7793–7804`）顯示曲線時不顯示 `clean` 與完整條件。

**Node 實測**

```text
chipMass=2 的髒紙與 chipMass=4 的乾淨紙
chipCurve、plateCurve 完全相同

chipMass=plateMass=-10、初溫=500、水量=999
仍 clean=true，仍產生固定 26/31/34°C 曲線
```

這是物理映射缺陷，不只是防作弊：玩家故意做壞比較後，看不到壞資料造成的任何數值後果。

**修法**

- 先做最低限度的輸入範圍與守恆型 fixture；若不準備讓質量改變曲線，就不要讓玩家改質量。
- 髒配置至少使平衡溫度或曲線形狀可見不同，且原紙列出質量、初溫、水量與「可否比較」。
- T1 判斷應讓玩家選中一髒一淨或兩張乾淨來源紙再限主張；不能只檢查曾經存在一張 clean record。

### 5.3 H1-2｜三種摩擦條件

**程式現況**

- `engine6.js:146–173` 的三條 fixture 方向清楚：只轉、只壓幾乎不升；接觸運動持續升溫。
- 三種條件各只能跑一次，這是良好守衛。
- 但 `heat6Records()` 只畫 `#id／friction-condition／curve`，完全不顯示 `row.condition`。玩家要靠按鍵順序猜哪條曲線是哪個條件。
- 最後判斷不要求指名哪張紙，只選固定概念字串。

**修法**

- 表格每列以中文標示條件，並讓三條曲線同軸疊圖；錯選時高亮玩家引用的那條，不直接給答案。
- 判斷 action 接受所選 record ID＋有限主張，驗證來源與結論一起成立。

### 5.4 H1-3｜乾式長紙

**程式現況**

- `dryBench.draft` 預設馬速 steady、壓力 fixed、採樣 sixteen-beats；UI 只讓玩家改壓力。
- 玩家直接按一次「讓紙帶走十六拍」即可得到 clean paper，再選正解。
- 規格要求玩家鎖馬速、壓力、採樣節拍；現行只有壓力是真控制，另兩項由預設代做。
- 髒紙有斷點，但表格不顯示是哪一條條件改變，只能看到 `—`。

**Node 實測**

```text
initialState → runDryStrip
clean=true
conditions={horsePace:'steady', pressure:'fixed', sampling:'sixteen-beats'}
```

**修法**

- 若馬速與採樣不打算做成決策，明標「由史坦格固定」並從玩家任務移除；不要用預設值冒充玩家操作。
- 每次只在紙帶上暴露一個真事件：鼓點漏拍、壓力滑動或馬速改變；玩家要依現場選修復／重做，原因留在原紙。

### 5.5 H2-1｜空氣密合對照

**程式現況**

- 先封預測、再做 open／sealed，骨架符合規格。
- `airBench.prediction` 只被存起來；`runAirComparison()` 與 `judgeAirComparison()` 都不讀它。
- 封存後 UI 不再顯示原預測；兩條曲線也沒有 condition 標籤。
- `any-change` 是不可否證的模糊押法，卻與另外兩種預測同等合法。

**Node 實測**

```text
slower-when-sealed / any-change / faster-when-sealed
→ open、sealed 曲線完全相同
→ 三條路都可取得 T3
```

**修法**

1. 封條固定顯示在兩條曲線旁。
2. 移除 `any-change`，或把它標成「沒有提出可分辨預測，不能封存」。
3. `judgeAirComparison()` 接受預測與實得關係，先記命中／偏離，再另問「空氣必要來源版本是否保留」。預測失準不阻擋科學發現，但必須有故事後果。

### 5.6 H2-2｜水箱乾淨起點

**程式現況**

- `prepareWaterBox()`（`engine6.js:268–280`）只檢查水溫恰為 18、三個 boolean 為真。
- UI 沒有炮頭、箱壁、水面三支溫度值，也沒有等待到初溫接近的過程；玩家只按密合、檢漏、放溫度計。
- 水溫預設就是 18°，玩家無法量水或改水量。
- `prepareWaterBox()` 不檢查 `ready`，正常 UI 可重複按「封存乾淨起點」，每次加一天與一張相同原紙。

**Node 實測**

```text
prepareWaterBox 第一次 → ok=true，preparation records=1
同一 state 再按一次 → ok=true，records=2，days 再 +1
```

**修法**

- `ready` 後拒絕第二次封存。
- 讓玩家看見三支初溫並執行「靜置到接近」；若只做流程儀式，就合併成一個「檢查並封存乾淨起點」動作，不要拆三個無失敗按鈕。
- 原紙記水量、三支初溫、檢漏結果與時間，而非只顯示 checkmark。

### 5.7 H2-2｜有限來源預測帶

**程式現況**

- 封存、封後拒絕改押、裂封保留都正確。
- `setFinitePrediction()` 對四來源接受所有三種 band；UI 只對 chips／air 顯示 `no-endpoint`，引擎卻允許 cannon／water 使用。
- 四來源的「很快／本班」沒有量化或 source-specific 可見後果，玩家缺乏做有根據預測的資料。
- T1／T3 已讓碎屑與空氣來源版本退下，本站又把兩者當仍待驗的有限來源重新下注，案件狀態倒退。

**修法**

- 只對仍在場的炮身、水提供新預測帶；碎屑／空氣沿用已裂或已撤回的舊紙。
- 預測內容改成可見後果，不猜無依據的時間：炮身先冷或斜率轉折；水若供熱則局部先降或輸出衰減。
- Engine 使用每來源允許的 band／consequence 表，UI 與 Engine 共用同一來源資料，不維護兩份規則。

### 5.8 H2-3｜長時段六格

**程式現況**

- `runContinuousSegment()`（`engine6.js:303–325`）不論 `continue`、`calibrate` 或 `repair-leak`，都依 index 讀同一列 `31,47,65,83,96,100`。
- 畫面沒有先揭示本格是正常、鼓點偏移或漏水；三個按鈕無從判斷。
- 按「repair-leak」即把原紙寫成 repaired，即使從未有 leak。
- 視覺只在全程完成後換成沸騰圖；中間六格主要靠文字表格，沒有曲線、儀表或器材狀態變化。

**Node 實測**

```text
continue → 31
calibrate → 47
repair-leak → 65
continue → 83
calibrate → 96
repair-leak → 100
```

**修法有兩條路，必須二選一**：

- **低成本誠實版**：刪三選一，改成「記下一格」；六格逐步展開，玩家每格只做新觀察。工程約 3–5 小時。
- **完整玩法版**：每格先揭示現場 event（穩定／鼓點漂移／水位降），正確處置才產生可引用 clean segment；錯動作留下壞格並接既有 w 節點。工程約 16–24 小時，含 fixture、UI、sanitizer 與負向測試。

沒有資源做完整事件系統時，低成本版比保留假選擇更好。

### 5.9 H2-3｜逐來源判讀

**程式現況**

- UI 對每個來源列出 fulfilled／not-fulfilled／insufficient 三個選項。
- `judgeFiniteSource()`（`engine6.js:327–348`）不讀 source、band 或長紙內容；只要不是 `not-fulfilled` 就拒絕。
- 完成條件硬寫成四來源全部 `not-fulfilled`。
- 因此 `no-endpoint` 也能被判為「未兌現」並裂封；有限時段本來無法否證「目前看不出終點」。

**Node 實測**

```text
四來源全設 no-endpoint（引擎允許）
六格跑完
四次提交 not-fulfilled
→ 四封全裂，T4=true
```

**修法**

- 建立 `evaluateFiniteSource(source, band, trace)` 的 source-specific 可否證規則。
- `no-endpoint` 對有限曲線只能得到 `insufficient` 並保持封條完整；不能計入「來源版本已退下」。
- T4 不是「四個都答同一個字」，而是四個都完成**合法判讀**；結論可混合 not-fulfilled／insufficient。
- 章末主張只列確實未兌現者，未決者繼續進 H3 板。

### 5.10 H3-1｜模型稽核板

**程式現況**

- `placeAuditEvidence()` 有正確 allowlist，狀態守衛完整。
- 但 UI 不提供混合候選：按鈕直接寫「碎屑來源 ← T1」「空氣來源 ← T3」等正解。玩家只照字面按五次。
- T4 同時按進炮身與水槽，沒有展開 T4 裡兩張來源判讀；可追溯性只剩證據代碼。
- `setLatentDisposition()` 的邊界判斷是真選擇，應保留。

**修法**

- 左側放未分派 T1–T4 原紙，右側放來源槽；用 select 或鍵盤可操作的 click-to-place，不必拖曳。
- 卡面顯示原條件、觀察範圍與缺口；T4 拆成炮身、水兩張子紙但仍共享 T4 證據包。
- 錯配留在板上並提示「這張紙實際改了哪個條件」，不要直接報正解。

### 5.11 HE-1｜共同驗證頁

**程式現況**

- `setJointColumn()` 與 `finalizeJointPage()` 的責任與原子完章守衛正確。
- UI 每欄只有兩個具名候選，故事前文已逐人說明責任；這比較像簽名儀式，不是新推理。
- `prepareJointPage()`（`engine6.js:401–408`）只 clone state，完全不寫入任何狀態。
- embed gate `joint-draft` 只看四欄＋scope debt；四欄填完時，「回到故事」已解鎖，玩家可以不按「確認共同頁暫稿」。

**Node 實測**

```text
四欄正確＋scopeDebt 已寫
Engine6.gate(state,'joint-draft') = true
prepareJointPage(state) → ok=true，stateChanged=false
```

**修法**

- 若共同頁是責任儀式：移除假分類與空 action，改成依序放入具名簽名牌；人物拒簽不屬自己的欄位是主要演出。
- 若必須保留「確認暫稿」，新增 `jointPage.draftConfirmed` 並納入 gate、schema、sanitizer 與測試；但這只值得在按鈕真的支付新責任時做。

## 九、建議新增的常駐負向契約

1. 四來源同位置／同後果不得封存。
