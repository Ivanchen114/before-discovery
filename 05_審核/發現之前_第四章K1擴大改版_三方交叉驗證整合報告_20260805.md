## 一、⭐⭐ 本輪最重要的發現：K4的「模型聽證會」機制七成已經寫好了，只是UI從未接上

**這是claude獨立發現、我已逐行核對完全屬實的最高優先級問題，規模超過先前K3的「孤兒輸入」一個量級。**

`engine4.js`裡有一整層K4判斷機制完整實作，且`run-node.mjs:7505`已經寫好測試在等它——但`chapter-ui.js`裡對這五個函式的呼叫次數是**零**：

```
engine4.js:1801 setModelProtocol      // 三選一協定：shared-law-observed-initials(正確)／same-start-all／retune-law-per-body(帶patchTags:3)
engine4.js:1824 sealModelPrediction   // 三選一預測：記錄beforeRuns稽核旗標(偵測玩家是不是偷看後才封存)
engine4.js:1838 runModelSuite / :1866 runModel   // 都要求protocolLocked，否則擋下
engine4.js:1884 assertK4
```

**這正是總監想從零設計的「模型聽證會」——渦旋模型若要為每顆行星另設流速就要貼借條（`retune-law-per-body`已經算好`patchTags:3`）、是否觀測揭曉前留下預測（`beforeRuns`旗標已經在記錄「你是不是偷看後才封」）——這些機制不是要新建，是已經建好、測試也寫好，只差把UI接上去。**

**而玩家實際玩到的是完全不同的一套（B代）**：`beginLedgerRow`／`stampLedgerCell`／`addModelLoan`／`declineModelLoan`／`sealModelComparison`。我進一步核對claude標記的「必查」項目，發現B代呼叫的`modelOutcome(model, caseId)`（`engine4.js:1553`）是**一個完全獨立的硬編查表**——`residual: 0.8`、`predictedYears: 6.4, observedYears: 11.9`這些都是寫死的字面值，不是任何模型真的算出來的。**玩家在K4看到的三案結果，從來不是動態跑出來的，是查表查出來的假結果。**

**工程量因此大幅下修**：claude估計**UI接線＋現有機制啟用約2-3人日**（比「從零重寫模型聽證會」的5-7人日便宜一個量級），其中真正需要新寫的邏輯只有「借條要影響後續判定範圍」這一項（約占30%工時，可能需要新state欄位）。

**施工前必查**（claude標記，我尚未查證）：如果`beginLedgerRow`路徑從不呼叫`runModel`（因為`protocolLocked`從未被設True），那B代的三案結果從哪裡冒出來的？已確認是`modelOutcome`的硬編表，這解答了這個疑問，但也代表**現行K4整個「查表蓋章」的體感，根本原因就是走了這條假路徑**。

### ⭐ 追加發現：硬編數字本身是物理正確的，且claude已找出「創造回饋1分」的精確機械成因

claude進一步核算`modelOutcome`裡的硬編數字，發現它們**不是隨手寫的稻草人**：用「均勻流速渦旋（T∝a¹）以火星校準」反推木星週期＝`1.88×(5.203/1.524)=6.42`，跟硬編的`predictedYears:6.4`完全吻合；殘差`(11.9-6.4)/11.9=46.2%`也跟硬編的`residual:46.2`完全吻合。**渦旋說在行星案輸，不是因為被寫成廢物，是同一張流速表從火星推到木星時真的對不上——物理設計是站得住的，接線A代時不需要重新設計模型物理，只需要讓`runModel`從模型定義動態算出這些數字，而不是查表拿到，省掉一整塊設計工作。**

**但這也精確解釋了驅動力矩陣「創造回饋1分」的字面成因**：`modelOutcome(model, caseId)`是一個`model×caseId`的**純常數映射**——意味著`setModelProtocol`的三個協定選項（正解／`retune-law-per-body`貼借條／`same-start-all`）**在B代裡不可能改變任何結果**。渦旋說在「行星」案的`predictedYears:6.4`是寫死的常數，無論玩家選哪個協定，這個數字都不會變，`patchTags:3`（三張借條）永遠不會兌現成任何可見差異。**「理論選擇沒有造成可見差異」不是比喻，是`modelOutcome`回傳一個常數這一行程式的直接結果。**

**修法方向**：接線時讓`runModel`依協定動態計算——`shared-law-observed-initials`路徑可直接沿用現有6.4/46.2/11.9這幾個已驗證正確的黃金值（不用重算），只需新增`retune-law-per-body`路徑的期望值（渦旋若被允許為每顆行星另調參數，會擬合成功但記三張借條）。這樣「借條的真代價」自然落地，不需要另外設計。

**⚠️ 施工前必查（claude標記，尚未查證）**：`inverseSquare`（正解模型）的三個`residual`（0.8/1.6/2.2）無法對應到標準殘差算式，疑似只是「通過」的量級標記，不是真實殘差（真正的平方反比對木星殘差應該接近0.1%以下）。若不修正，玩家把46.2跟1.6並排看時可能誤讀成「平方反比也差了1.6%」，這一項需要在接線前確認清楚。

## 二、K1高山大砲：史實核查、時間線衝突、與spike先行的建議

### 史實核查（三方一致，僅年代精度略有差異）

- **高山大砲**：確實出自牛頓死後1728年出版的《世界體系論》（*A Treatise of the System of the World* / *De Mundi Systemate*）。**但codex與claude都糾正**：1728是出版年，不是思想首次形成的年代——該書源自原擬作《原理》第三卷的通俗稿，寫作時間約在1685年前後，不是1679年虎克通信那年。因此若把大砲放進1679年場景，應標「合理重建」；正式出版圖像應以「後來史料回聲」呈現，不冒充1679年當場產物。
- **《原理》第一卷命題一**：確實用「等時段連續偏折逼近軌道」的幾何方法，但codex提醒表述要精確——命題一的主旨是證明中心力運動的等時掃掠面積，不是「三十拍軌道計算器」；「等時段直走＋中心偏折」是後續論證不可隨玩法一起刪掉的物理骨架，但「剛好三十拍、玩家三拍牛頓補二十七拍、四個下拉選單」確實是現代遊戲化重建。

### ⭐ 三方獨立收斂的關鍵結構事實：現行K1其實在1665年K2之後14年才發生

codex與claude各自查證`scenes4.json`與`engine4.js`，得出完全一致的結論：

```
現行場景順序：D1-1(1665切線紙) → D1-2/e1(1665 K2同尺紙) → D-INT-1(幕間十四年) → D2-1/e1(1679虎克信後，現行K1) → D3-1/e1(1684哈雷，K3)
```

`engine4.js:413`的`k2-required`閘門明確要求K2已完成才能啟動K1；`D2-1/n8-n9`現行劇情也已經讓牛頓拉開「十四年沒開的抽屜」，取出1665年的K2兩張舊紙跟虎克信並排——**這是現有設計刻意做的跨14年伏筆回收**。

**總監原提案的「K1高山大砲→K2地月同尺」節奏，若照字面排序，等於要牛頓在1665年前就想出大砲、才算出地月尺度，會讓這個14年伏筆變成無法解釋的矛盾。** gemini與codex都明確指出這一點，且都建議：**不要把K2搬到大砲之後**，正確做法是把大砲放進現行D2-1（1679年），讓牛頓「把高山大砲紙壓在虎克信旁，再取出十四年前的兩張同尺紙」，維持現行跳轉去K3（哈雷）。若真要把K2搬到大砲之後，就是年代與證據鏈整套重排，codex估計這不是本提案該負擔的必要成本，明確反對。

### 機制評估：新設計方向對，但要避免「三個固定速度按鈕」式的淺化

三方一致：把K1的四個變因（方向/初速/箭長/形狀）縮減成「只操縱初速」**不是天然的倒退**——因為在現行證據鏈裡，中心方向已由虎克信固定、距離律已由14年前的K2固定，此時初速確實是唯一還沒被隔離出來單獨測試的變因。

**但claude提出關鍵警告**：總監的對話雛形已經先說了「慢落近、快落遠」，如果三發預測只是「低/中/高」三個固定按鈕、系統自動畫完，會比現行K1更淺（現行K1至少讓玩家的三拍真的進入牛頓續畫的前三拍，是真因果不是查表）。

**claude的具體建議玩法**（比總監原案更完整，我認為值得採納）：
1. 先做一次不計分的慢速示範砲，建立「向前走同時下落」的基本感知
2. 給三枚不寫結果的火藥包，依序測試「撞地／繞行／逃離」三種可能，每發前封存預測、不顯示正誤
3. 三條預測虛線與實際軌跡疊在同一張圖，錯猜不消失
4. 最後由玩家（不是牛頓）選出「三條路都在下落；繞行是不斷錯過地面」
5. 授證條件是「封存＋三次發射＋最後判讀」，不是押中才過
6. **保留至少一個兩拍的微型判斷**（玩家指出每拍的中心偏折，牛頓重複算），讓逐拍方法不會完全變成純對話演示——這一點呼應了gemini「不要讓玩家從探究者退成純評分者」的提醒

### 工程量（claude與codex獨立估算，數字接近）

- **可玩spike（不處理存檔相容）**：1-2人日
- **正式替換（含無障礙、844×390、遷移與反向測試）**：6-9人日
- 若走此路，需新增ADR明確**取代GB-ADR-033與040的K1三拍部分**（不動K2的030/039/043），並升第四章schema或加入method version（新局走`mountain-cannon-v1`，舊完成/進行中存檔走legacy路徑）
- **`ch04_focus_mountain_cannon_v01`這個美術資產已經存在**（我已核對`assets.json:1736`），目前只是非互動路徑，可以重用

**兩方一致強烈建議：先做1-2人日的spike，經總監真人試玩驗證後，才進入6-9人日的正式替換**，不要一次性直接大改。

### ⭐ claude追查後發現：正式替換的門檻比想像中更高，而且有一個工程量遠低的第三方案

**GB-ADR-040③逐字規定了現行K1**（規則紙/預測紙分區、指向/初速/箭長三變因、三十拍、續畫承接三拍）。其相容邊界寫明：「若要改成『先畫三拍、再押全程』，須另立含中途存檔遷移的結構裁決，不以純文案修訂偷渡。」——**連「把封存與作圖對調」這種遠比替換輕的改動都要正式的結構裁決，整體替換遠遠超過這個門檻。**

**具體工程證據**：
- `tests/run-ch4-migration.mjs:371`已有一條測試專門鎖住「舊自動作圖不可灌入新版手動三拍」——這條測試的存在本身就是**上一次K1改版留下的痕跡**，代表K1已經改版過一次，這次再改會是第三代機制，需要v1→v3與v2→v3兩條遷移路徑
- `tests/fixtures/`目前**只有v1版本的測試素材，沒有v2**，正式替換前得先造出v2 fixture
- **sanitizer對`orbitLab`的引用有71處，比engine本身的53處還多**（我已用grep核對這兩個數字屬實）——sanitizer才是這次改版最重的表面，不是engine

### claude提出的第三方案：只換掉「27拍」的尾段，保留「3拍」的前段——工程量降到約1天

claude指出一個重要的史實與工程雙重理由：**現行K1真正繁瑣、玩家零影響力的部分是「牛頓代畫的後27拍」，不是「玩家親手畫的前3拍」**。前3拍用的`ORBIT_AIM_OFFSETS=[0.47,-0.41,0.53]`刻意不是6°整數倍角度（防止盲按猜中），是全章唯一真正的觸覺互動，值得保留。

**而且史實層面有一個重要發現**：1679年11月虎克來信提出「切向直行＋中央吸引」的複合概念後，**牛頓真的回信畫了路徑圖，而且畫錯了（畫成螺旋），虎克回信指正**——這段有書信可考。也就是說「在1679年那張桌上做逐段偏折作圖、可能畫錯、錯圖留著」**不是現代遊戲化重建，這是史實核心事件**；反而是「剛好三十拍」「四個下拉選單」「玩家三拍牛頓補二十七拍」這些才是重建。**若整體替換K1，淨效果是把錨定在1679年真實歷史事件的互動，換成錨定在1685年前後才成文的《世界體系論》素材，同一個場景年代卻換了對應的史實依據——史實嚴謹度反而是退步，不是進步。**

**claude的方案**：保留規則封存與玩家的前3拍，把「牛頓代畫的27拍」直接換成高山大砲——用玩家自己剛剛封存的規則，發射三種初速，讓大砲成為玩家造物的外推示範，不是外來的獨立示範。**估計工程量約1天，`orbitLab`的資料形狀完全不變，遷移測試不用動。**

**這個第三方案值得總監優先考慮**：它同時解決了「27拍太長太被動」「大砲太淺會退化成三個固定按鈕」「史實從1679退步到1685」三個問題，且工程量遠低於前兩方案。

## 二點五、⚠️ 重要更正：本會議先前對K2的介面修法建議，跟既有ADR裁決正面衝突

**這是claude在本輪追查GB-ADR-030全文後發現的，需要總監重新裁決，不能當成呈現層小修直接施工。**

先前「第四章實驗台互動設計診斷」報告建議把K2的核心幾何圖（`orbit4ScaleGeometry`）從筆記區搬回視覺區，讓圖與判讀對上。**但`GB-ADR-030`③明文規定**：「同尺紙左頁改用兩張完整raster教學重建圖……執行期不得再以SVG／canvas／HTML疊畫」，其驗證條款也鎖定「scale相位走圖片而非`orbit4Svg`」。**現行`renderOrbit`的`if(phase==="scale") orbit4ScaleSheets(visual); else orbit4Svg(...)`是在遵守既有ADR契約，不是失誤。** 把幾何圖移回視覺區會直接違反ADR-030③並打破常駐契約。

而ADR允許的替代路徑（把圖烤進raster）也被同一條ADR的不變邊界堵住：「不得提前畫出仍待玩家判斷的選項答案」——而「哪一段是正矢」正是K2第一步要玩家判斷的東西，不能被raster提前畫出來。

**claude提出的折衷解法**：raster只烤入兩個端點的位置與標籤（`D1-1/ok1b`已公開的內容），不烤連接它們的短差線；玩家選對後由runtime在**右頁**（不是左頁）畫出那條短差。這樣同時守住ADR-030③（左頁不疊畫）、玩家有圖可對照、答案不預畫。**代價是要重出一版raster圖。**

**這是先前報告需要更正的地方，總監裁決時請把這條納入考量。**

## 三、K3盲驗設計：三方一致認為優於原本的「加診斷判斷」修法，且claude發現一個新的潛在風險點

三方一致：總監的「盲驗設計」（距離/理論算出的週期/被遮住的觀測/直覺猜測四張卡分開）確實解決codex先前找到的「孤兒輸入」問題，而且比claude原本設想的「揭曉後加一個診斷判斷」更根本——**孤兒輸入之所以發生，是因為現行設計把「玩家的直覺猜測」跟「理論的事前計算結果」塞進同一個欄位，引擎判定用後者，玩家填的是前者，前者必然孤兒。四張卡把它們實體分開，孤兒就無法復發**（claude的表述）。

**工程量**：codex估計最小修法（沿用現有欄位加一次診斷）約1-2人日；完整盲驗（新增方法、遮蔽、比較判讀、sanitizer與遷移）約3-5人日，claude同意完整版更好——玩家先設計測試再看結果，不只是補授證缺口。

**必鎖三條回歸測試（codex提出，經我確認邏輯完整）**：
1. 直覺押錯＋未做有效比較，不得授K3
2. 直覺押錯＋正確比較，可授K3且錯押留痕
3. **直覺押中＋比較錯誤，仍不得授K3**（防止矇對）

**⚠️ claude發現一個施工前必查的風險**：現行`planetLab.predictions`的列存的是`exponent`（指數），但UI顯示的是「約1.5/1.9/2.3年」這種週期帶——UI問週期帶、引擎記指數，這個映射如果沒處理好，新設計的四張卡可能又對不上state，重新製造一個孤兒。這一項尚未查證到底，列為施工前必查。

**claude的另一個提醒**：四張卡若做成「把卡拖進正確欄位」的呈現，會退化成另一種分類作業；判斷應該是「哪兩張連起來才構成檢驗」，不是「哪張卡放哪格」，建議用類似`sealModelComparison`的「選一句claim」呈現，比拖放格子更安全也符合零拖曳原則。

## 四、K4「玩家是裁判」框架 vs 「借條的認識論價值」：不衝突，且有一個必須守住的條件

三方一致：這兩者不衝突，反而相容——借條的價值本來就是「記下模型借用了什麼，不是解釋了什麼」，裁判的職務正好是記錄雙方各自不得不假設什麼。`D4-1/n25`現行劇情已經有台詞在替裁判角色的正當性辯護（「牛頓不能蓋——規矩是他的。我不能蓋——書是我要印的。這桌帳裡，只有你沒有輸贏」），跟總監的新框架一致。

**唯一必須守住的條件（claude提出）**：借條不能變成分數。如果最終判定退化成「借條少的贏」，就把認識論記錄變成了計分板。總監自己設計的第三個結論選項已經守住這一點（「平方規則……不等於已說明拉力如何穿過空間」）——**建議把這句話的後半段寫進引擎層鎖住的`ledgerClaimText`正解字串，不只靠台詞**，否則保護僅存在敘事層面，容易在後續修改中流失。

**史實/角色一致性風險（codex提出）**：哈雷歷史上是牛頓方案的推進者，不宜演成信奉渦旋說的人。修法是讓他明說「我替最強反方讀案，不替它背書」，而不是讓他變成真正的渥旋說支持者。

**codex另提醒**：不要讓K4三輪聽證變成純評分（玩家只負責打分不動手）——第三輪彗星「玩家先接好星圖再選最有鑑別力的追問」這個動手環節值得保留並推廣到全部三輪，避免玩家從探究者退成旁觀的裁判。

## 五、八驅動力矩陣：三方一致認為「作為診斷工具有用，作為精密評分要小心」

三方一致：矩陣得出的核心診斷是對的且很有價值——「第四章的核心問題不是缺表單，是理論選擇沒有造成可見差異」，claude稱這句話「比任何評分都有價值」。

**要小心的地方**：八個軸不互相獨立（成就與創造回饋大量重疊，稀缺迫切與損失避免同理），48格0-3分的加總若沒有各軸操作定義，跨章排名會不穩，建議當「找出哪個維度塌了」的診斷清單用，不要當「第四章17分低於第二章22分」這種排名工具用。

**「創造回饋1分」是否準確**：claude用完全獨立的方法（逐站檢查「玩家的選擇是否產生看得見、不同的產物」）驗證：K1會（唯一有創造回饋的站）、K2/K3/K4/K5都不會（K4真正該有創造回饋的那一層正是被晾在旁邊的A代機制）。**1/5站有創造回饋→1分準確，而且claude指出這是一個很強的「兩條獨立方法收斂到同一個病灶」的證據**：總監用驅動力矩陣得出的結論，跟claude用失敗率/失敗資訊量分析得出的結論，指向同一個機械成因（K3孤兒輸入、K4孤兒判斷層）。
