## 一、史實核查

### 1.1 高山大砲出自 1728 年《世界體系論》——**成立，但需修正一處**

**正確的部分**：那張砲彈圖確實出現在 *De mundi systemate*／英譯 *A Treatise of the System of the World*，1728 年出版。牛頓 1727 年 3 月去世，所以這是**遺著**。圖的內容也如提案所述：從山頂拋出物體，速度遞增畫出弧 1、2、3……最後繞行不落地。

**需要修正的部分**：**1728 是出版年，不是寫作年。** 這份文稿是牛頓約 **1685 年**寫的《原理》第三卷的早期通俗版本，他後來自己壓下不發，改寫成更數學化的第三卷。所以：

| | 年代 | 與 D2-1（1679）的距離 |
|---|---|---|
| 高山大砲的**構想成文** | 約 1685 | **約 6 年後** |
| 高山大砲的**出版** | 1728（遺著） | 49 年後 |

**這對提案是好消息也是壞消息。**
- 好消息：總監的「不能宣稱牛頓在 1679 年當場畫出這張圖」是對的，而且理由比提案講的更紮實——不是「後來才出版」，是**那個想法本身要到六年後才成文**。
- 壞消息：如果按「史料回聲／歷史顯影」呈現，玩家看到的是一張 1728 年的印刷圖，而場景是 1679 年。**這個時間落差比提案設想的更難處理**，因為它不是「同一時期的想法、後來才印出來」，而是「六年後才想到、四十九年後才印」。

**建議**：若採用，正式原圖的圖說必須同時標出**成文約 1685、出版 1728** 兩個年份，而不只標 1728。只標 1728 會讓熟史的玩家以為這是牛頓晚年的東西，反而誤導。

### 1.2 《原理》第一卷命題一用等時段連續偏折——**成立，但用途需要說清楚**

**正確的部分**：命題一（Proposition I, Theorem I）的證明就是那個構造：把時間切成等份，第一段物體因慣性走 AB；到 B 受一次向心衝量，於是走到 C 而不是 c（其中 Bc = AB）；三角形 SAB 與 SBc 等面積，而 SBc = SBC 因為 Cc 平行於 BS。然後「令三角形數目無限增加、寬度無限減小」，極限就是曲線。**等時段連續偏折逼近軌道，這個描述準確。**

**需要說清楚的部分**：**命題一證明的是「面積與時間成正比」（克卜勒第二定律），那個折線多邊形是證明面積律的工具，不是「畫軌道的方法」。** 構造確實會生出路徑，所以遊戲把它當作圖法是**合理的再用途**，但不是牛頓當時的目的。

**建議**：這不是錯誤，不需要改機制，但設計文件應該記下這一點。若哪天有人問「牛頓用這個方法畫軌道嗎」，準確答案是「他用這個構造證面積律；路徑是構造的副產物」。

### 1.3 提案漏掉的一件事：1679 年**有**一個真實的作圖事件，而那正是現行 K1 的錨點

這是我最想提的一點，而且它影響第 2 題的結論。

1679 年 11 月 24 日虎克來信，提出把「沿切線的直行」與「朝中心的吸引」複合起來。**牛頓回信時真的畫了一張路徑圖——而且畫錯了。** 他畫成向中心收束的螺旋，虎克回信指出應該是一條閉合的橢圓形路徑。這段往返是有書信可考的、被史學界反覆討論的episode。

**所以現行 K1 的處境是：**
- 「玩家在 1679 年的桌上，用逐段偏折的方法親手畫路徑，可能畫錯，錯圖留著」——**這件事本身就是 1679 年真實發生過的**（只是史上畫錯的人是牛頓）。
- 「剛好三十拍」「四個下拉」「玩家三拍牛頓補二十七拍」確實都是現代重建，總監說得對。
- **但「在 1679 年這張桌上做逐段偏折作圖」不是重建，那是史實核心。**

而高山大砲是約 1685 年的文稿內容。**所以整體替換的結果是：把一個錨定在 1679 年真實事件的互動，換成一個錨定在六年後文稿的互動，而場景年代不變。** 這在史實嚴謹度上是退步，不是進步。

現行 `scenes4.json` 的 `D2-1` 已經把這個錨點用得很好：`n3` 直接引虎克 1679-11-24 的信、`n7` 牛頓「他不是這樣看。他說：月亮一直往前，同時一路被扳彎」、`n42`「這條路是照他信上的兩支箭畫出來的」。**作圖互動是這封信的直接後果。** 拿掉它，虎克的信就變成純敘事鋪陳，沒有對應的玩家動作。

## 二、機制評估：不同意整體替換

### 2.1 挑戰的淨損失比提案估計的大

我上一輪用 Node 量過現行 K1：

| 項目 | 現行 K1 | 提案版 |
|---|---|---|
| 搜尋空間 | 3 指向 × 3 初速 × 3 箭長 = **27 組，約 3 組可行**（`earth-center` 是唯一有效指向；程式註解明載三組速度／箭長配對可成近圓） | **1 個變因、3 個值，而且三發都要打** —— 沒有錯誤選擇 |
| 事前封存 | 5 種形狀預測 | 3 發各封一個結果（4 選項） |
| 逐拍判斷 | 3 拍，每拍要重新看當下地心；`ORBIT_AIM_OFFSETS = [0.47, -0.41, 0.53]` rad **刻意不是 6° 的整數倍**，程式註解寫明「避免玩家不看圖只背『每拍固定按三次逆時針』也能過關」；`matchedPreviousEarth` 會判「指向上一拍的位置」為錯 | **無** |
| 失敗留痕 | 幽靈紙（`manualAttempts`）、錯規則路徑紙 | 猜錯的預測與軌跡保留 |

**「三發都要打」是關鍵**：提案的三個速度是依序發射的，所以玩家不需要**選**，只需要**看**。唯一的判斷是事前封存，而一旦理解「快一點＝遠一點」，三個封存幾乎是被迫的。**這比現行的 3/27 少了一整個層級的判斷。**

### 2.2 更嚴重的是丟掉「耦合」，而那是 K2 的物理前提

現行 `D2-1/n27`–`n28` 牛頓說的是：

> 「還有一件。你得先假定它原本跑多快。」
> 「**同樣一扳，對慢的來說太重，對快的來說太輕。扳多少，得配上它跑多快。**」

**這是全章最重要的一句物理。** 它說的是向心偏折的大小必須與速度匹配才能形成軌道——也就是 v 與向心加速度之間的關係。而 K2 整站在做的事（遠 60 倍 → 弱 3600 倍）就是這個關係的定量版本。

**高山大砲只改初速、重力固定，所以它演示的是「結果」（落地 vs 繞行），不是「耦合」。** 玩家會學到「打得夠快就會繞」，但不會學到「扳多少要配多快」。

**後果**：到了 K2，玩家被要求判斷「一秒向內偏折」與「距離平方」的關係，但他在 K1 從來沒有操作過「偏折量」這個變數。**K1→K2 的概念橋會斷一根。**

### 2.3 「軌跡畫在同一張圖上、猜錯保留」——這一點總監是對的，但它不需要靠替換取得

現行版本**已經有錯路留痕**，只是分散在不同紙上：

> `D2-1/n33` stage：牛頓把錯規則的紙逐張攤開：內捲、外張、只朝固定方向彎下的弧線、繞錯墨點的彎路，以及什麼都不改時的切線直路。

**「同一張圖上疊合比分開的紙好比較」——這個判斷我完全同意。** 但它是一個**渲染層改動**（把 `ruleRuns` 的路徑疊畫在同一個 SVG 而不是列成表格），不需要換掉機制。而且 `o.ruleRuns` 已經存了每次的 `target`／`speed`／`strength`／`prediction`／`actualShape`，資料齊全。

### 2.4 我的反案：**保留規則封存與三拍，砲彈當延伸而非取代**

這個版本拿到總監要的三件事，但不丟掉耦合與逐拍判斷：

**(1) 規則紙從 4 個下拉縮成 2 個決定**
- 決定一：**每拍往哪扳**（3 選項）—— 這一項必須留，它是 `earth-center` 那個洞察。
- 決定二：**扳多少要配上多快**——把現在的「初速」與「箭長」兩個獨立下拉合成**成對選項**（例如「慢／短」「中／中」「快／長」「快／短」…），玩家選的是一個**配對**，不是兩個獨立值。搜尋空間 3 × 若干配對，命中率與現在相當，但表單減半，而且**選項本身就在教耦合**。
- 形狀預測紙保留（GB-ADR-040 ③ 要求規則紙／預測紙分區，這樣仍符合）。

**(2) 三拍保留** —— 這是全章唯一的觸覺互動，也是唯一防得住盲按的設計。

**(3) 二十七拍的續畫，換成高山大砲**
玩家三拍站住後，牛頓說「把同一個規矩推到極端」，然後**用玩家自己封存的規則**發三種初速：低速落山腳、中速落更遠、高速繞行。**軌跡疊在同一張圖上，玩家自己的三拍墨跡留在起點附近。**

**(4) 最後的洞察仍由旅人說出** —— 總監的對話雛形這部分可以完整保留。

**為什麼這個版本更好：**
- 砲彈成為**玩家自己造的規則的外推結果**，而不是一個外來的示範。這比「牛頓換一個一眼就懂的問法」更符合「玩家出判斷」的原則。
- 耦合保住了：玩家選過「扳多少配多快」，砲彈只改初速時，他知道自己在固定什麼。
- 二十七拍的繁瑣感消失（那本來就是最不好玩的部分——**玩家對它沒有任何影響力**，是純等待）。
- 史實錨點兩邊都有：1679 的作圖是玩家做的，1685 的砲彈是「同一個規矩推到極端」的顯影。
- **工程量小得多**：`sealOrbitRule`／`nudgeOrbitAim`／`commitOrbitBeat`／`resetOrbitBeats` 全部存活，`orbitLab` 不需要第三代形狀。只有 `continueOrbitRule` 的輸出改成砲彈三發，以及 UI 的合併下拉。

## 三、銜接評估：提案有一處順序錯誤

### 3.1 實跑確認：K2 在 K1 之前

```
只完成 K0 就封規則 → k2-required
K2 完成後 evidence = {"k1":false,"k2":true,"k3":false,"k4":false,"k5":false}
再封規則 → OK（僅 target 名稱錯誤時回 bad-orbit-target）
```

場景順序也吻合：`D0-1 → D0-2 → D1-1（K0 切線）→ D1-2（K2 同尺紙）→ D-INT-1（幕間十四年）→ D2-1（K1 虎克來信）→ …`

**所以玩家走到 D2-1 時，K2 早就拿到了。**

### 3.2 提案的結尾方向是反的

提案對話雛形的最後一步是「**牛頓把月球天文紙移過來銜接 K2**」。但月球天文紙在 `D1-2` 就用完了，K2 已成立。**這一句在現行結構下不成立。**

**兩個可能的解讀，總監需要裁定是哪一個：**

**(a) 提案隱含也要重排章節順序**（把 K1 移到 K2 之前）。這是**更大的結構改動**——`sealOrbitRule` 的 `k2-required` 前置要移除、`D1-2` 與 `D2-1` 的場景順序與 `goto` 要重接、`D-INT-1`（幕間十四年）夾在中間的時間軸也要處理（現在的順序是 1665 果園 → 1665 同尺紙 → 十四年 → 1679 虎克信，這個時間軸是對的；把 1679 的作圖移到 1665 的同尺紙之前會製造史實矛盾）。**我不建議這條路。**

**(b) 結尾改成指向 K3**。K1 之後的下一站是 `D3-1`（哈雷帶木匣，K3 行星週期）。銜接句應該是「同一條規矩，敢不敢碰別的天體」——而 `D3-1/n40` 哈雷已經有這句了（「整本書還得回答另一個問題：同一條規矩，敢不敢碰整片天空？」）。**所以正確的銜接是把砲彈的洞察指向「這條規矩會不會也管火星木星」，而不是回頭指月球。**

**我建議 (b)**，而且它剛好與現有 `D2-1/n13` 牛頓的收尾對上：「先記下。我們只量過月亮。天上還有火星、木星，還有幾十年才回來一次的東西。」——**那句話已經在做這個銜接了。**

## 四、工程量評估：比提案預期的大一個量級

### 4.1 法源：必須廢止 GB-ADR-040 ③，這是提案沒提到的

GB-ADR-040 ③ 逐字規定了現行 K1：

> ③第四章 K1 UI 分成「規則紙」與「預測紙」：**指向、初速、箭長會改變路徑**；形狀預測只留下事前判斷。互動前明說問題是**同一規矩重複三十拍**後會撞回地球、逃出去或繞住。**牛頓續畫必須承接玩家前三拍**，形狀分類改由實際路徑的半徑與結果判讀。

而它的**相容與邊界**還寫了：

> 新 K1 run 標記 `classificationSource=simulated-path-v1`；沒有此欄位的舊 run 仍以原 canonical 分類驗證，**未知來源一律拒絕**。……**若要改成「先畫三拍、再押全程」，須另立含中途存檔遷移的結構裁決，不以純文案修訂偷渡。**

**注意最後那句**：ADR 自己說，連「把封存與作圖的順序對調」這種**遠比替換機制輕**的改動，都需要另立含存檔遷移的結構裁決。**整體替換機制遠超這個門檻。**

它的**驗證**條款還鎖定了一組反向控制測試：

> 行為反向控制採一組「設定相同、三拍仍有效但刻意偏外」的路徑：`medium/short` 不得再按表標成橢圓，實際最大半徑越過外帶時應判為向外張開。

**這條測試是寫在三拍機制上的，替換後整條失效，需要新寫一條等效的反向控制。**

### 4.2 State：這會是 `orbitLab` 的第三代

```
v1 fixture 的 orbitLab（14 欄）：attempt, step, path, velocityVectors, deflectionVectors,
  consequence, tangentRecord, closedRecord, ruleRepeatReady, complete, position, velocity,
  ruleRuns, activeRule
現行 orbitLab（21 欄）：以上 + ruleSeal, aimAngle, manualBeats, manualAttempts,
  firstStepAt, manualComplete, continuedAt
```

而 `tests/run-ch4-migration.mjs:371` 有一條斷言：

```js
assert.equal(result.state.lab.orbitLab.ruleRuns.length, 0, "舊自動作圖不可灌入新版手動三拍");
```

**這條測試存在的原因就是上一次 K1 改版（v1 自動作圖 → v2 手動三拍）。** 再改一次，就需要 v1→v3 與 v2→v3 兩條遷移路徑，而 `tests/fixtures/` 目前**只有 v1 的 fixture，沒有 v2 的**——所以還得先造一個 v2 fixture 才能測 v2→v3。

## 五、對第六章修正方案的意見：**同意總監，我原本的方案是錯的**

### 5.1 總監的批評是對的

「8 格配額」會讓玩家優化**配額**而不是優化**讀數**。這是真的類型漂移，而「經營小遊戲」是準確的命名。我當時把「讓失敗有代價」直接翻譯成「給一個可耗盡的資源」，那是遊戲設計的反射動作，不是這個專案的語言。**這一項我撤回。**

「系統蒙太奇推進例行讀數、只在異常時停下、全程兩三次有意義的決定」——這個形狀對，而且它與第六章既有的節奏一致（`H2-3/n2` 史坦格「每半小時你只有三件事可做」講的就是異常時的三選一，不是每半小時都要選）。

### 5.2 但我要補一個強化：**代價要是證據性的，不是經濟性的**

總監的版本若不指定「判斷錯了會怎樣」，可能又回到「錯了就重做、沒有真代價」。我建議：

**在漂移／漏水發生時若選「續鑽」，該段記 `temperature: null` ＋ `gaps: ["horse-pace-drift"]`，而那個缺口會永久限制長時段曲線在 `judgeFiniteSource` 能否證哪些來源。**

- 缺一段的長紙仍然可以判讀，但**缺口涵蓋的時段不能用來否證任何有限來源**。
- 這正好是第六章自己的倫理：`H2-3/w3` 史坦格「我只能簽『煮開』，不能簽這段升溫一路怎麼來」。
- **代價變成「你的證據更弱」，不是「你的回合更少」** —— 完全避開經營遊戲的漂移，而且它讓那三段已寫好但目前不可觸發的壞紙台詞（`H2-3/w1`／`w2`／`w3`）有了路徑。

這樣「兩三次有意義的決定」每一次都真的有意義，而且意義是科學性的。

**工程量**：比我原本的 8 格配額**更小**（不需要 `shiftBudget` 欄位，只需要 `drift`／`waterLevel` 兩個瞬時狀態與 `gaps` 陣列，而 `gaps` 在 `dryBench` 已有先例）。**可能不需要新 schema 欄位，須確認 `continuousRun.segments` 的既有形狀能否容納 `gaps`。**

## 六、對施工優先序的意見

**提案的順序**：①K3孤兒輸入 ②第一章P3停止代答 ③K1改高山大砲 ④K2圖面位置與提示 ⑤第六章長時段 ⑥第五章可辨識誤差

### 6.1 ①② 排最前面是對的

兩者都是**正確性問題**（孤兒輸入是 bug、P3 代答是代做玩家判斷），而且便宜。不動。

### 6.2 ④ 應該排在 ③ 之前——三個理由

1. **K2 在遊玩順序上比 K1 早**（第三節已證）。玩家先在 K2 迷路，再帶著那個狀態進 K1。先修 K2 等於免費改善 K1 的體驗。
2. **④ 是已確認的缺陷，③ 是設計變更。** K2 的兩項（幾何圖位置、CSS 隱藏 `.todo` chip）是三方都獨立驗證過的實際缺陷；K1 改版是方向選擇。缺陷先修。
3. **成本差 3–5 倍。** ④ 約 30 行純呈現；③ 是 3–5 天（或走我的反案 1 天）。

### 6.3 ⑥ 應該排在 ⑤ 之前

⑥（第五章可辨識誤差）是**第二章已驗證有效的 fixture 指紋模式的直接移植**，`_FIXTURE` 是引擎常數不是存檔欄位，不需改 schema。⑤（第六章長時段）即使採我在第五節的輕量版，仍要新增瞬時狀態並與 `judgeFiniteSource` 耦合。**便宜且低風險的先做。**

### 6.4 一項提案不知道的衝突：④ 撞 GB-ADR-030 ③

**這是我這輪最重要的發現，它直接改變 ④ 的性質。**

GB-ADR-030 ③ 明文：

> ③同尺紙左頁改用兩張完整 raster 教學重建圖；線條、刻度、數字與簡式皆烤在圖內，**執行期不得再以 SVG／canvas／HTML 疊畫**。

它的**驗證**條款還鎖定：

> 常駐契約鎖定兩張 v02 raster 與母版、**scale 相位走圖片而非 `orbit4Svg`**、滿版說明牆退役……

**所以 `orbit4ScaleGeometry`（一個 SVG）出現在筆記區而不是視覺區，不是實作失誤——它是 GB-ADR-030 ③ 禁止在 scale 相位的左頁疊 SVG 的直接後果。** `renderOrbit` 的 `if (phase === "scale") orbit4ScaleSheets(visual); else orbit4Svg(...)` 正是在遵守那條驗證契約。

**這意味著三方（包括我自己）之前把它診斷為「錯放」是不完整的。** 「把幾何圖移回視覺區」的修法會：
- 直接違反 GB-ADR-030 ③
- 打破「scale 相位走圖片而非 `orbit4Svg`」這條常駐契約

而 ADR-030 允許的替代路徑（把正矢幾何烤進 raster）也走不通，因為同一條 ADR 的不變邊界說：**「完整重建圖可以承載本頁已公開的數字與公式，但不得提前畫出仍待玩家判斷的選項答案。」** 而「哪一段是正矢」正是第 1 步要玩家判斷的東西。

**所以 ④ 是一個真正的三方衝突**：ADR-030 要左頁純 raster ／ 互動需要一張玩家判斷時可對照的圖 ／ 答案不能預先畫出。**這需要總監裁定，不能當呈現層小修施工。**

**我建議的解法**（供裁定）：在 raster 底圖上烤入**兩個端點的位置與標籤**（這是「本頁已公開」的資訊——`D1-1/ok1b` 的 stage 已經敘述過兩個端點），但**不烤入連接它們的那條短差線與箭頭**（那是待判斷的答案）。玩家在左頁看到兩個端點，在右頁選「圈弧長」或「連起兩端點」，選對後才由 runtime 在**右頁**畫出那條短差。這樣：左頁仍是純 raster（守住 ADR-030 ③）、玩家有圖可對照（解決迷路）、答案不預先畫出（守住不變邊界）。**需要重出一版 raster，這是真實成本，但不需要廢止任何 ADR。**

### 6.5 我建議的順序

```
① 第四章 K3 孤兒輸入修復              （bug，便宜）
② 第一章辯論 P3 停止代答               （正確性，便宜）
③ K1 介面小修：拿掉「（未預選）」、
   「現在只做一件事」改成下一個動作      （約 20 行，且與 K1 是否改版無關——
                                        若改版，新站也需要這兩格填對）
④ 第四章 K2 圖面與提示                 （先取得 6.4 的裁定；CSS 兩行可立即拿掉）
⑤ 第五章可辨識誤差                     （移植已驗證模式，不改 schema）
⑥ 第六章長時段（第五節輕量版）          （新增瞬時狀態）
⑦ 第四章 K1 改版                       （最後；若走我的反案則可提前到 ④ 之後）
```

**把 K1 改版排最後的理由**：它是唯一需要廢止 ADR 的項目，也是唯一會製造第三代 state 形狀的項目。讓便宜且已確認的修法先落地，可以在真人再試玩一次之後，用更好的資訊決定 K1 到底要整體替換還是走反案。**而且第 ③ 項（介面小修）落地後，總監可能會發現現行 K1 的「不知道要幹嘛」有一大部分來自那兩格填錯的內容，而不是三十拍機制本身。** 那會改變 K1 改版的必要性判斷。

## 七、我最不同意的一句，直說

提案裡有一句我認為需要修正：

> 「K1 是第四章目前最好的一站」不等於「現在的三十拍玩法應該保留」，只是現有選項裡的相對最佳。

**這句話的前半我完全同意，但它推導出的結論不對。** 我上一輪給 K1 高分的依據不是「相對最佳」，是三項可量測的性質：
- 27 組配置只有約 3 組可行（不是猜中間值就過）
- `ORBIT_AIM_OFFSETS = [0.47, -0.41, 0.53]` rad 刻意非 6° 整數倍，程式註解明寫是為了**防盲按**
- `matchedPreviousEarth` 會判「沿用上一拍方向」為錯

**這三項是真實的挑戰設計，不是相對比較的結果。** 而三十拍裡真正繁瑣的是**後二十七拍**——那部分玩家沒有任何影響力，是純等待。**所以要拿掉的是二十七拍，不是三拍。**
