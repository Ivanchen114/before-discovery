## 二、B-1｜B1 的負向契約只掃 `node.text`，掃不到選項——而病灶原本就在選項裡

**位置**：`greybox/tests/run-node.mjs:5650-5654`。

**實際證據**：

```js
const beforeHooke = scenes4.scenes
  .slice(0, scenes4.scenes.findIndex((scene) => scene.id === "D2-1"))
  .flatMap((scene) => scene.nodes.map((node) => String(node.text || "")))   // ← 只取 node.text
  .join("\n");
if (/一門砲|山頂大砲|一直被扳彎|錯過地面|一直往下掉|一直在落|落了一整圈|繞一整圈/.test(beforeHooke))
  throw new Error("1665 場仍在虎克書信前餵出山頂大砲或持續改向框架");
```

`node.options[].text` **完全不在掃描範圍內**。而外部 B1 的原始發現位置是 **D0-2/c0**——那是一個 `type: "choice"` 節點，劇透就寫在**選項文字**裡。

**反向控制（三組，皆在 /tmp 副本、基線 138/0）**：

| 變異 | 結果 |
|---|---|
| 把「月亮一直往下掉，卻永遠錯過地面」放回 **D0-2/c0 的選項** | **138/0——不轉紅** |
| 把「；月亮一直往下掉卻錯過地面」加到 **D0-2/c1 的三個選項** | **138/0——不轉紅** |
| 把「（正解卡）」加到 **D0-2/c1 的三個選項** | **138/0——不轉紅** |

同一寫法出現在 `5646`（`beforeSelfIntro`，牛頓自報姓名前不得認出人物）、`5661`（`d21Text`，C1 術語）、`5665`（`d22Text`），全部只讀 `node.text` 與 `speaker`。D2-1 目前恰好沒有 choice 節點，所以 C1 這條眼下沒有實害；但 D2-1 之前有 **5 個** choice 節點（D0-1/c1、D0-2/c0、D0-2/c1、D1-1/c1、D1-2/c0），B1 這條的漏洞是實的。

**玩家實際會看到的後果**：現在不會看到任何東西——內容是乾淨的，我逐選項掃過。風險在未來：任何人往選項寫回大砲意象或製作術語，測試都會維持 138/0 放行，而審查紀錄第 37 行寫著「均已有對應修復與負向契約」，會讓下一位審查者以為這層有保護。

```js
  ...(node.options || []).map((option) => String(option.text || ""))

```

## 四、C 級兩條

**C-1｜正解「零邊界詞」的殘留相關性，值得試玩時盯著。**
三組正解**都是**邊界詞 0，而錯項至少一組帶謹慎語域。單看這點像是把舊訊號反轉而非消除。但我做了對照檢定：「挑零邊界詞」在 DE-1/c1 與 SC4-R1/c1 都會同時命中一個錯項（`summary_only`、`fill-mechanism`），「最短＋零邊界詞」在 SC4-R1 還會選到錯的 `fill-mechanism`。**所以它不是可靠啟發式，我不把它列為 B。** 但正解一律不使用謹慎語域這件事是真的，而且我的邊界詞表是自訂的、不是法源定義——**這條只能靠真人試玩判定**，機器測不出來。建議試玩時特別觀察 DE-1/c1。

**C-2｜外部審查宣稱的基線 commit 不在本 repo，無法重現。**
審查紀錄第 5 行寫「隔離 repo 唯讀掛載，HEAD `1855d80`」。實查：`git cat-file -t 1855d80` → `fatal: Not a valid object name`；全部 **239 個 commit** 掃描，零命中。最可能是隔離 repo 以複製檔案後 `git init` 建立，因此雜湊與本 repo 無關聯。後果：我無法比對外部審查者當時究竟看到哪個版本，也無法確認送審內容與現行工作樹的差距。修法：在審查紀錄補記隔離 repo 的建立方式，並改用**本 repo 可驗證的錨點**（對應 commit、或送審檔案的內容 hash）。這不影響本輪結論——四項修復我是直接對現行檔案驗的，不依賴那個 hash。
