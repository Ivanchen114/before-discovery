### 3. D0-2/n14｜答對的玩家被當成答錯的訓 ★本輪逐句審新發現

**位置**：`D0-2/n14`。這條是機械掃描不出來、只有逐句跟著分支走才會撞到的。

**實際證據**：`c0` 兩條分支的匯流點是 `n14`。

```
[future-answer 搶答]  → n12a 牛頓質問 → n12b 信譽−1 → n13 旅人收回 → n14
[evidence-boundary 正解] → n12d 信譽+1 ─────────────────────────────→ n14
```

`n14` 原文：**「（抬手止住）那就只說紙上有的。月亮那一段，先留白。」**

在搶答分支上完全正確：越界 → 被質問 → 收回 → 牛頓抬手制止。**但正解分支是直達 n14**——玩家剛剛才自己說了「月亮那一段，我還沒有紙能接」，牛頓卻抬手**制止**他、糾正一個沒有發生的越界。答對的人被當成答錯的訓，而且那正是本章第一個信譽判定，第一印象就歪掉。

**修法**（一句話，零結構）：

> （**把蘋果換到另一隻手**）那就只說紙上有的。月亮那一段，先留白。

制止手勢換成中性動作。搶答分支讀作「牛頓接受你的收回」，正解分支讀作「牛頓同意你的分寸」，兩邊都通。而且蘋果從 n10 一直在他手上，到 n16「把蘋果拋回掌心，轉身要走」動作是連的。

### 4. D4-2/n2｜開場第一句指涉不明

**原文**：印刷工「**兩個窗口。這個月只剩兩個。**稿子進版框後再整頁重排，花的不只一張紙。」

「兩個窗口」沒有前文、也不是玩家能推的行話——第一次讀完全不知道在說什麼，而它是這一場的第一句對白。

**修法**：「這個月只剩兩次上機。稿子一旦進了版框，再改就得整頁重排——花掉的不只一張紙。」

同樣的時間壓力，但玩家第一次就讀得懂。

## 四、我自己犯的一個錯，已修正

第一次寫回 `scenes4.json` 時我用 `json.dump(indent=2)`，把整個檔案重新格式化——**4 處文字改動產生了 4613 行 diff**。那會蓋掉 Sol 並行工作的可讀性，也違反共用工作樹紀律。

實查後發現這個檔案**本來就沒有統一格式**：主體是 1 空格縮排展開式，但 `SC4-R1` 的節點是每節點一行的緊湊寫法（`{"id":"n1","type":"line",...}`），顯然是不同時期用不同腳本寫進去的。所以沒有 canonical 序列化器可用，任何重新格式化都是破壞性的。

修正方式：寫一個還原原有慣例的序列化器，並以 **HEAD 版逐位元組往返**作為它是否忠實的檢驗（`往返完全相同 = True`），再套回我的版本。

結果：`scenes4.json` 的 diff 從 4613 行降回 **265 行**，而那 265 行是 Sol 的 v0.9 修復加我這 4 處——是可以審的規模。

**教訓**：改共用 canonical 資料檔前先確認它的格式慣例，不要假設有標準序列化器。這個檔案的混合格式就是反例。
