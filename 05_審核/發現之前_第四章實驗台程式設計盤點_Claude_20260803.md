## 〇、一句話結論

**第四章最大的參與感落差，是 D2-1 作圖法：玩家親手轉出來的三拍，對最後畫出來的軌道有零影響。**

`continueOrbitRule()` 把玩家的三拍丟掉，從原點 `(1,0)` 重跑一次模擬；最終形狀由 `canonicalOrbitShape(target, speed, strength)` 這張**九格查表**決定。玩家轉了三次鍵，畫面上長出來的那條路跟他轉的角度沒有因果關係。

而 **CANONICAL 原型是做對的**——`spike_ch4_D2-1_construction_v3_CANONICAL.html` 的牛頓續畫是從玩家的 `px, py, vx, vy` 接下去跑，形狀由實測半徑判定。**這是 prototype → production 的退化，不是設計沒想到。** 修復成本相對低，價值最高，建議列為 P0。

## 二、🔴 D2-1 作圖法（`phase: orbit-rule`）——最大落差

### 2.1 目前的實作

**封存拍**（`sealOrbitRule`，engine4.js:348）：玩家一次封存四項——
- `target` ∈ `same-vector`（固定方向）／`ink-mark`（紙上墨點）／`earth-center`（地心）
- `speed` ∈ slow 0.82／medium 1／fast 1.18
- `strength` ∈ short 0.67／medium 1／long 1.39
- `prediction` ∈ line／away／circle／ellipse／crash／wrong-center

**三拍**（`nudgeOrbitAim` + `commitOrbitBeat`，engine4.js:401/412）：
```js
// 每拍開始，瞄準角被刻意設成「正解 + 0.6 rad（34.4°）」
o.aimAngle = orbitTargetAngle(config.target, o.position) + 0.6;
// UI：← / → 每次轉 6°（Math.PI/30）
// 落筆判定：
var valid = currentError <= 18;   // ±18° 容差
```

**續畫拍**（`continueOrbitRule`，engine4.js:823）：
```js
var sim = simulateOrbitRule(seal.target, seal.speed, seal.strength);   // ← 從 (1,0) 重跑
var actualShape = canonicalOrbitShape(seal.target, seal.speed, seal.strength);  // ← 查表
...
o.path = clone(sim.path);          // ← 玩家三拍的 path 被整條覆蓋
o.position = clone(sim.finalPosition);
o.velocity = clone(sim.finalVelocity);
```

而 `canonicalOrbitShape` 是一張硬表（engine4.js:492）：
```js
if (target === "same-vector") return "line";
if (target === "ink-mark") return "wrong-center";
var key = speed + ":" + strength;
if (["slow:short","medium:medium","fast:long"].indexOf(key) >= 0) return "circle";
if (key === "fast:short") return "away";
return "ellipse";
```

### 2.2 問題

**① 玩家的三拍是純手活，而且是同一個手活做三次。**
每拍都被重設成偏 34.4°，容差 ±18°，方向鍵一次 6°。所以每一拍的動作固定是：**按 ←（或 →）三到六次，按 Enter**。三次。角度落在容差內即可，落在 5° 或 17° 沒有任何差別。

**② 三拍與結果之間沒有因果。**
即使玩家三拍都壓在容差邊緣（17.9°）、路徑已經歪掉，`continueOrbitRule` 仍然從 `(1,0)` 重跑一條乾淨的軌道。玩家看到的最終圖形，跟他剛才畫的那三段線在幾何上不連續。

**③ 沒有動畫。** UI 一次把 `o.path` 換成完整路徑再重繪（`orbit4Svg` 畫成單一 `<path>`）。設計文件寫的「牛頓續二十七步」在畫面上是一瞬間的替換，「出力氣」這件事看不見。

### 2.4 建議改法

#### 🔧 P0-A：讓續畫從玩家的終點接下去（engine4.js）

新增一個帶初始狀態的模擬函式，`continueOrbitRule` 改用它：

```js
function simulateOrbitFrom(target, strengthKey, p0, v0) {
  var strength = ORBIT_STRENGTHS[strengthKey], dt = 0.02;
  var x = p0.x, y = p0.y, vx = v0.x / dt, vy = v0.y / dt;  /* 三拍用的是每拍位移，需換回速度 */
  var path = [{x: round(x), y: round(y)}];
  var minR = Math.sqrt(x*x + y*y), maxR = minR, hitEarth = false, i;
  var ink = { x: 0, y: 0.55 };
  for (i = 0; i < 900; i++) {
    var ax, ay;
    if (target === "same-vector") { ax = -strength; ay = 0; }
    else {
      var tx = target === "ink-mark" ? ink.x : 0;
      var ty = target === "ink-mark" ? ink.y : 0;
      var dx = tx - x, dy = ty - y, dm = Math.sqrt(dx*dx + dy*dy) || 1;
      ax = strength * dx / dm; ay = strength * dy / dm;
    }
    vx += ax * dt; vy += ay * dt; x += vx * dt; y += vy * dt;
    var r = Math.sqrt(x*x + y*y);
    minR = Math.min(minR, r); maxR = Math.max(maxR, r);
    if (r < 0.28) { hitEarth = true; }
    if (i % 4 === 3) path.push({x: round(x), y: round(y)});
    if (Math.abs(x) > 2.45 || Math.abs(y) > 2.45 || hitEarth) break;
  }
  return { path: path, minRadius: round(minR,3), maxRadius: round(maxR,3),
           hitEarth: hitEarth, finalPosition: {x:round(x),y:round(y)},
           finalVelocity: {x:round(vx),y:round(vy)} };
}
```

`actualShape` 改由實測導出，取代 `canonicalOrbitShape` 的查表：

```js
function shapeFromSim(target, sim) {
  if (target === "same-vector") return "line";
  if (target === "ink-mark") return "wrong-center";
  if (sim.hitEarth) return "crash";
  if (sim.maxRadius > 2.4) return "away";
  return (sim.maxRadius - sim.minRadius) <= 0.10 ? "circle" : "ellipse";
}
```

**⚠️ 連帶成本**：`orbitRecordAudit`（:507）與 `orbitRunAudit`（:604）目前是拿 `simulateOrbitRule(config)` 去比對存檔，改成從玩家三拍接續後，稽核也要改成「先 replay 三拍、再從該狀態續跑」。**好消息是 `orbitBeatReplay`（:644）已經有 replay 三拍的完整實作**，把它的輸出（position/velocity）餵進 `simulateOrbitFrom` 即可，不必另寫一套物理。這是本項唯一的實質工作量，約半天。

**若要更省**：保留 `canonicalOrbitShape` 決定「敘事上的形狀名稱」，但**畫面上的 `o.path` 改成從玩家終點接續的實測路徑**。這樣稽核不動，玩家看到的路也真的接在自己那三段線後面——**七成的參與感用一成的成本拿到**。建議至少先做這個版本。

#### 🔧 P0-B：加上逐步生長動畫（純 UI，不動 engine）

`continueOrbitRule` 回傳的 `run.path` 有 20–90 個點。UI 目前一次畫完，改成分批揭露：

```js
/* chapter-ui.js：orbit4Svg 畫路徑處 */
function drawPathProgressive(svg, points, cx, cy, scale, cls) {
  var reduced = window.matchMedia("(prefers-reduced-motion:reduce)").matches;
  var node = document.createElementNS(SVGNS, "path");
  node.setAttribute("class", cls); svg.appendChild(node);
  if (reduced) { node.setAttribute("d", fullD(points)); return; }
  var i = 3;   /* 前三點是玩家的三拍，立刻顯示 */
  node.setAttribute("d", fullD(points.slice(0, i)));
  var timer = setInterval(function () {
    i += 1;
    node.setAttribute("d", fullD(points.slice(0, i)));
    if (i >= points.length) clearInterval(timer);

```

**約 15 行，零引擎改動。** 這一項單獨做就能大幅改善「牛頓在出力氣」的體感——玩家會真的坐在那裡看那條線繞回來。原型已經證明這個節奏可行（70ms × 約 30 步 ≈ 2 秒）。

#### 🔧 P1-C：讓三拍的精度留下痕跡，而不是通過／不通過

目前 `valid = currentError <= 18` 是二元的。低成本改法：**保留二元閘門，但把角度誤差畫在紙上**。`beat.angleCurrentDeg` 已經算好且存進 `deflectionVectors`，UI 只要在每支箭旁標一個小數字（「偏 7°」／「偏 16°」），三拍結束後由牛頓給一句分級回饋：

> 三拍都在 8° 內 → 牛頓：「手很穩。這三拍我不必重描。」
> 有一拍超過 15° → 牛頓：「第二拍偏得多。我照你的線接下去——歪一點的起頭，繞出來的圈也會歪一點。」

**若 P0-A 已做**，第二句就不只是台詞，而是玩家真的會在畫面上看到的結果。這兩項有加乘。

#### 🔧 P1-D：切線預測答錯也要畫給玩家看（`sealTangentPrediction`，:206）

目前答錯只回 `consequence: "tangent-prediction-mismatch"`，畫面什麼都不變。**玩家永遠沒機會看到「照圓弧走」長什麼樣。**

而 `consequencePath(kind, p, v)`（:249）**已經寫好了 `outward` 與 `impact` 兩種路徑生成器**，目前只被 legacy 的 `commitDeflection` 用到。低成本改法：答錯時也產生一條淡色的後果路徑存進 `sourceLab.attempts[i].path`，UI 疊在圖上：

> 選「照原來的圓弧繼續走」→ 畫出那條圓弧，走著走著自己飄開 → 牛頓：「你要它彎，可是題目說什麼都不加。誰來彎它？」
> 選「立刻朝地球落下」→ 畫出直墜 → 牛頓：「這是替它多加了一次拉。」

**這符合設計文件「錯路全畫完留紙」的原則，而該原則在 D2-1 的 ghost path 已經實作了，只是沒有沿用到 D1-1。**

## 三、🔴 D3-1 封存火星木星（`phase: planets`）——第二大落差

### 3.1 目前的實作

```js
function predictPlanet(state0, id) {
  ...
  var prediction = Math.pow(PLANETS[id].radiusRatio, (exponent + 1) / 2);   // 引擎算的
  var actual = PLANETS[id].periodRatio;
  var residualPct = Math.abs(prediction - actual) / actual * 100;
  var sealedAt = tick(s);
  var row = { ..., sealed: true, sealedAt: sealedAt, openedAt: null, ... };
  row.openedAt = tick(s);                                    // ← 同一個函式內就開獎
  row.revealedAfterSeal = row.openedAt > row.sealedAt;       // ← 恆為 true（tick 必然遞增）
  s.planetLab.revealed[id] = true;
```

### 3.2 問題

**① 玩家沒有預測任何東西。** 「預測值」是引擎用 `radiusRatio^((exponent+1)/2)` 算出來的。玩家的輸入只有「點下火星」「點下木星」兩次點擊。

**② 封存與開獎在同一次呼叫內完成。** `sealedAt` 與 `openedAt` 相差兩個 tick，中間沒有任何玩家動作。`revealedAfterSeal` 這個欄位**在建構上不可能為 false**——它記錄的是一個永遠成立的事實。

**③ 不可能失敗。** 火星：`1.52^1.5 = 1.874` vs `1.88` → 殘差 0.32%。木星：`5.20^1.5 = 11.856` vs `11.86` → 0.03%。門檻 `pass: residualPct <= 3`。兩顆永遠通過。

**④ 這一站的整個戲劇前提因此落空。** `D3-1/n31` 哈雷說：

> 「我信不過任何人的記性，包括我自己的。看過答案以後，人都會覺得自己早就知道。」

那是全章鋪陳最好的一句動機台詞（我在鋪陳盤點裡也是這樣評的）。但程式把「封存」這個承諾裝置做成了自動的——**玩家從來沒有承諾過任何事，所以也不會體驗到承諾的重量。**

**⑤ 設計文件的正案視覺完全沒有實作。** 定案帳 §三 D2-3 附註：

> 「**紙帶刻痕版為正案**：行星每回到起跑星位打一刻，預測帶與觀測帶並排；刻痕對齊＝規則活著，錯開＝死了；÷距離觀摩＝十年內預測帶打兩刻、觀測帶一刻未到。」

而 `chapter-ui.js` 的 `phase === "planets"` 只畫了兩張卡片，內容是「預測 1.874／觀測 1.88／殘差 0.32%」的文字。**「逐圈累積」這個唯一能讓玩家看懂「木星藏不住」的視覺，沒有畫。**

## 四、🟡 D4-1 對帳桌（`phase: models`）——主體好，借條空轉

### 4.1 做對的部分（不要動）

**原始數據先於蓋章顯示。** `orbit4Svg` 的 models phase 在每一格先畫 raw：
```
拉力帳：殘差 0.8% / 1.6% / 2.2%
渦旋帳：無核對數字 / 6.4 年－11.9 年 / 方向與流向衝突
```
然後才是「章：等你判讀」。**這是「系統不宣告合不合，玩家自己判讀」的正確實作**，符合設計文件 D3-1 v2 第①②③點。

**彗星接法有真的視覺後果。** `connectCometTracks("hard-kink")` 錯選會在 UI 畫出折角並標「紙碰到了，軌道卻折斷」，而且折角**不會被刪掉**（`hadKink` 永久為真）。這是全章少數「失敗留下可見痕跡」的實作，做得好。

**`revokeEvidence` 級聯。** 改動上游決定（重封軌道規則、改比例尺）會讓下游證據全部失效並保留舊紙。這是很強的完整性機制，也讓玩家的決定真的「有份量」。

### 4.2 問題：借條的兩個決定完全不影響結果

```js
function addModelLoan(state0, caseId) { ... ml.loanDecisions[caseId] = "loan"; finishLedgerRow(s, caseId); }
function declineModelLoan(state0, caseId) { ... s.modelLab.loanDecisions[caseId] = "no-loan"; finishLedgerRow(s, caseId); }
```

- 兩者都讓該列完成。
- `sealModelComparison` 的正解仍是 `"actual-ledger"`，**與借條數無關**。
- 唯一差別是 `ledgerClaimText(ml)` 選了四句敘述中的哪一句。

**也就是說：玩家在「要不要給對手一張借條」這個決定上，做什麼都一樣。** 而設計文件把它寫成整個 K4 的勝負軸：

> 「③核心不對稱：距離律靠**殘差**誠實活著；渦旋靠**借條**續命；**解釋成本＝帳上數得出的張數**。」

### 4.3 建議改法

#### 🔧 P1-G：讓「兩張都拒絕」變成一個可被推回的立場（低成本）

拒絕借條 = 主張「漩渦說在這一格就是錯的，不必給它機會」。這在本章的價值觀裡**恰好是哈雷警告過的過度宣稱**（`D4-1/n30`：「別把它寫成『所有漩渦都錯』」）。所以：

```js
/* sealModelComparison 內，claim === "actual-ledger" 時多一個檢查 */
var refusedAll = ["planets","comet"].every(function (id) {
  return ml0.loanDecisions[id] === "no-loan";
});
if (claim === "actual-ledger" && refusedAll)
  return { state: s, ok: false, reason: "loans-refused-overclaim",
           halley: "兩張借條你都不肯給。那你這張紙寫的不是『它欠得比較多』，是『它連欠的資格都沒有』——那是另一句話，而且今天的帳撐不住。" };
```

改完之後：
- 給借條 → 帳面上留下兩張欠條，結論是「同一條規矩，欠得比較少」（誠實比較）
- 拒絕借條 → 被哈雷推回，玩家得回去改決定（**這正是設計文件「死路 B」的精神**）

**成本：約 10 行，`ledgerClaimText` 的四種分支已經寫好，不必新增文案架構。**

#### 🔧 P1-H：把借條數做成畫面上的可見負擔

UI 底部目前只有一行「借條數 N」。改成**在漩渦帳那一欄的格子上真的貼一張歪斜的便箋 SVG**，每貼一張整欄往下沉 4px、透明度降一階。玩家會直觀看到「這本帳是靠補丁撐著的」。

```js
(ledger.loans || []).forEach(function (loan, i) {
  var ci = ledgerCases.findIndex(function (c) { return c[0] === loan.caseId; });
  var y = 92 + ci * 84;
  draw("rect", {x:492, y:y+8+i*3, width:64, height:30, rx:3,
                transform:"rotate(-6 524 "+(y+23)+")", class:"orbitLoanSlip"});
  draw("text", {x:524, y:y+28+i*3, "text-anchor":"middle",
                transform:"rotate(-6 524 "+(y+23)+")", class:"orbitLoanText"}, "借條");
});
```

**成本：約 12 行 SVG，零引擎改動。** 這是全章投報率最高的視覺改動之一——「解釋成本＝帳上數得出的張數」這句設計語言，一眼就看懂。

## 五、🟡 D1-2 同一把尺（`phase: scale`）

### 5.1 目前是四題線性連鎖單選

| 順序 | 函式 | 選項數 | 解鎖條件 |
|---|---|---|---|
| 1 | `sealScalePrediction` | 4（same／÷60／÷3600／幾乎零） | K0 已封存 |
| 2 | `convertMoonTime` | 2（÷60／÷3600） | 上一題已封存 |
| 3 | `judgeScaleRatio` | 4（60／360／3600／36000） | `conversionCorrect` |
| 4 | `judgeScaleRelation` | 3（add／multiply／unknown） | `ratioCorrect` |

答錯只 push 一筆 attempt 並回 consequence 字串，重選即可，**沒有代價、沒有新資訊、畫面不變**。

### 5.2 三個具體問題

**① 第 3 題在第 2 題之後幾乎是同義反覆。** 玩家剛選完「÷3600」，馬上被問「倍數是多少？」，選項有 3600。這一題沒有增加任何判斷。

**② 開蠟不是一個動作。** `convertMoonTime` 內部順手就把封存的預測開了：
```js
if (sc.scalePrediction.openedAt == null) {
  sc.scalePrediction.openedAt = at;
  sc.scalePrediction.matched = sc.scalePrediction.choice === "one-over-3600";
}
```
玩家沒有「掀開蠟封」的那一下。設計文件 D2-2 v3 第 4 步明列「**開蠟對照**：封錯＝蠟條劃線留桌」——這是一個獨立的戲劇拍，被吃進換算裡了。

**③ 答錯 ÷60 時，玩家看不到錯在哪。** 只回 `consequence: "time-not-squared"`。

### 5.3 建議改法

#### 🔧 P1-I：讓錯誤答案「算完給你看」

`convertMoonTime` 選了 ÷60 時，也算出結果並回傳，讓 UI 把兩個數並排：

```js
if (!ok) {
  return { state: s, ok: false, divisor: 60,
           wrongSagMm: round(TEACHING.moonSixtySecondSagM * 1000 / 60, 1),  /* 81.7 mm */
           observedSagMm: round(TEACHING.moonSixtySecondSagM * 1000 / 3600, 1), /* 1.4 mm */
           consequence: "time-not-squared" };
}
```

UI 顯示：**「照你的算法：8.2 公分。月亮那裡量到的：1.4 公釐。差了六十倍。」**
牛頓：「時間縮六十倍，掉下來的距離不是也縮六十倍——第一章那串一、三、五、七，你自己量過。」

**失敗因此有了資訊量**（設計文件文字五查與「失敗只打掉主張，資料保留」同源），而且回扣第一章的奇數律——設計文件 D2-2 v3 第 3 步本來就寫「**第一章奇數律當裁判**」，現在只有這一句話，沒有畫面。

#### 🔧 P2-J：刪掉第 3 題，或把它前移

最省：直接移除 `judgeScaleRatio`，把 `judgeScaleRelation` 的解鎖條件改成 `conversionCorrect`。三題比四題緊。
較好：把「倍數是多少」移到 `convertMoonTime` **之前**當作真正的預測（此時玩家還不知道要 ÷3600，這題就有判斷了），換算變成驗證。

#### 🔧 P2-K：把開蠟做成獨立動作
新增 `openScaleSeal(state0)`，UI 給一個「掀開蠟封」按鈕，封錯時在桌面留下一條劃線的蠟條 SVG（與 P0-E 的行星蠟條共用同一個視覺元件）。

## 六、🟢 D4-2 印刷台（`phase: proof`）——全章最紮實，不要大動

### 6.1 為什麼它是最好的一站

**它有三種不同性質的決定，而不是同一種重複：**

| 決定 | 性質 | 程式 |
|---|---|---|
| 六槽接證明鏈 | 查表配對 | `placeProofLink`，`PROOF_EXPECT` 硬表 |
| 四項署名 | 查表配對 | `assignCredit`，`CREDIT_EXPECT` 硬表 |
| **虎克範圍三選** | **價值判斷**（寫過頭／抹除／精確） | `setHookeScope` |
| **退出作者欄** | **道德動作，唯一帶 rep 獎勵** | `removeTravelerFromAuthorField`，`repDelta: 1` |
| **校樣窗口** | **資源取捨**（短稿 vs 延後，都留痕） | `submitPartialProof` / `deferPress` / `consumeWindow` |

**`removeTravelerFromAuthorField` 是全章唯一一個「玩家主動放棄某樣東西」的機制**，而且 `repReason` 寫得很好（「沒有把參與操作冒充成作者身分」）。這是第四章最有份量的一次互動，程式上也做得乾淨。

**校樣窗口（`reservedWindows: 3`、`scheduleLost`）是全章唯一的資源。** 這是唯一一處「做錯／拖延會有實際成本」的地方。

### 6.2 唯一建議

#### 🔧 P2-L：把「六槽接錯」的後果視覺化
`placeProofLink` 錯放回 `consequence: "geometry-break"`，UI 目前只換文字。既然 `orbit4Svg` 已經在畫六個節點與連線（`orbitProofNode` / `orbitProofLink`），錯放時讓那一段連線**斷開並下垂**（改 `d` 為折線、加 `.broken` class）即可，約 5 行。「證明鏈」這個比喻就在畫面上兌現了。

## 七、跨站的兩個結構觀察

### 7.1 「牛頓出力氣，玩家出判斷」在程式上只兌現了一半

設計文件 §一.4 是全章原則，**每場設計先清點玩家動詞，無判斷＝打回**。逐站清點：

| 站 | 玩家的判斷動詞 | 玩家的手活 | 比例 |
|---|---|---|---|
| D1-1 | 三選一切線 | — | 判斷 100% |
| D2-1 | 四項封存 | **三拍轉鍵（重複 3 次，且不影響結果）** | 判斷 4 次 / 手活 3 次 |
| D1-2 | 四題單選（其中一題同義反覆） | — | 判斷 100%，但線性無分歧 |
| **D3-1** | **無** | **兩次點擊** | **判斷 0%** |
| D4-1 | 6 蓋章 + 2 借條 + 1 接法 + 1 封條 | — | 判斷 100%（借條無後果） |
| D4-2 | 6 槽 + 4 署名 + 範圍 + 退出 + 窗口 | — | 判斷 100% |

**D3-1 是唯一完全沒有判斷的站，而它偏偏是承載「封存承諾」這個主題的站。** 這是清點時該被打回卻沒被打回的一場。

### 7.2 全章只有一處失敗有成本

`consumeWindow` / `scheduleLost`（D4-2 校樣窗口）之外，所有實驗台的失敗都是**免費重試**：log 一筆 attempt、回一個 consequence 字串、重選。

設計文件其實指定過代價的形式——「**封錯＝蠟條劃線留桌**」「錯路全畫完留紙」「舊墨變淡留紙」。這是很好的設計：**代價不是擋路，是留下痕跡。** 目前只有兩處實作了：

- ✅ D2-1 的 ghost path（`manualAttempts` 以 opacity 0.28 疊繪）
- ✅ D4-1 的彗星折角（`hadKink` 永久留存）

建議把同一個模式補到其餘各站，成本都很低：
- D1-1 切線錯選 → 畫出那條錯路（P1-D）
- D1-2 封錯 → 劃線蠟條留桌（P2-K）
- D3-1 押錯 → 劃線蠟條留桌（P0-E）
- D4-2 接錯槽 → 斷裂的連線（P2-L）

**這是全章一致性最高、單位成本最低的一組改動**：一個共用的「劃線蠟條」SVG 元件 + 一個「淡色錯路」繪製函式，四站共用。

## 九、最後：不要動的東西

盤點過程中看到幾個做得很好、容易在重構時被誤刪的機制，特此列出：

1. **`revokeEvidence` 級聯**（engine4.js:95）——改上游決定會讓下游證據失效但保留舊紙。這是本作「證據鏈自己閉合」的核心，也讓玩家的決定有真實份量。
2. **每拍重設瞄準角 +0.6 rad**（engine4.js:397、449）——防止玩家用肌肉記憶連按三次。看起來像刁難，其實是逼玩家每拍重新看「地球現在在哪」，是這個互動唯一真正的物理內容。
3. **`matchedPreviousEarth` 診斷**（engine4.js:437）——分辨「偏離當下地心方向」與「朝的是它剛才的地方」。這是一個**真的幾何判定**（比較兩個夾角），不是猜的，而且對應到一個真實的初學者錯誤。牛頓那句「這一步，你朝的是它剛才的地方」因此站得住。全章最聰明的一段程式。
4. **D2-1 的 ghost path** 與 **D4-1 的彗星折角** ——見 §7.2。
5. **原始數據先於蓋章顯示**（`orbit4Svg` models phase）——系統不宣告合不合。
6. **`removeTravelerFromAuthorField`** ——全章唯一有道德重量的動作，程式與 repReason 都寫得乾淨。
