# 《發現之前》跨章共用底層系統審查

審查者：Codex
日期：2026-08-03
範圍：`narrative.js` 辯論引擎、`sanitize.js` 匯入淨化、跨章無障礙、手機橫屏
性質：唯讀審查；除本報告外未修改專案檔案

## 一、總裁決

目前最值得「一次修復、跨章受益」的不是視覺，而是兩個底層契約：

1. 第一、二章在玩家配對正確證據後，`narrative.js` 會直接用「旅人(你)」播出整段 `playerCorrect`，玩家只選到證據，沒有選到推論。第五章已經用同一套引擎內建的 `responses -> debateReason` 路徑修掉這件事，所以不需要另造新系統，只要把第一、二章資料與測試升級到第五章的推論門即可。
2. `sanitize.js` 的共通弱點不是「少幾個型別檢查」，而是把匯入檔裡的結果欄位、事件列或證據旗標當成可信證明。Node mutation 實測顯示，第一、二、三、五章都能接受至少一種從起點憑空塞入的章證據；第一、五章甚至接受不可能的原始物理讀值。第四、六章已有較完整的「工作台真相 -> 章證據 -> 游標/完章」比對，可作為共用審計模式的參考，但仍不能把目前 sparse event log 說成完整 replay。

無障礙與手機支援則是「共用外殼一致、章內工作台不一致」：舞台有共用全螢幕、橫向鎖定、直拿手機自動旋轉、鍵盤推進及 reduced-motion；但第二章低高度模式把部分控制縮到 28–38 px，第五章沒有 844x390 專屬版面。任何新拖曳方案若成為唯一操作，會違反既有無障礙原則；K1 強制拖曳更直接違反第四章已鎖定的「無拖曳」契約。

### 建議優先序

| 優先 | 工作 | 影響章節 | 理由 |
|---|---|---|---|
| P0 | 將第一、二章改走 `responses -> debateReason`，停止自動播 `playerCorrect` | 1、2；共用引擎 | 直接修復玩家代理權，已有第五章成熟路徑 |
| P0 | 對第一、二、三、五章加章證據、完章、里程碑的投影一致性檢查 | 1、2、3、5 | 目前可憑匯入值跳進度 |
| P1 | 新 schema 開始記錄可重播的 lab/debate action ledger | 全章 | 現有 event log 缺 args，無法做真正 replay |
| P1 | 第五章 sanitizer 注入 `Engine5`，重算碰撞與黏土 fixture | 5 | 現在只驗 finite number，可接受物理上不可能的紀錄 |
| P1 | 修第二章低高度觸控目標、補第五章 844x390 分支 | 2、5 | 實際手機操作風險高於外殼看起來的完成度 |
| P2 | 把拖曳做成可選 adapter，不是唯一輸入法 | 1、2、4 | 保留直接操作感，不犧牲鍵盤、觸控與讀屏 |

## 三、`playerCorrect` 自動代講

### 3.1 共用呼叫鏈

`stage.html:2983-3017` 先依章節替換 `DATA.scenes`、`DATA.debate`、`Engine`，再於 `stage.html:3022-3023` 載入同一份 `narrative.js` 與 `chapter-ui.js`。因此第一、二、五章不是三套辯論引擎，而是同一個 factory 搭不同資料。

| 章 | debate 資料 | 共用程式 | 實際推論行為 |
|---|---|---|---|
| 第一章 | `debate.json` | `debatePresent` | 無 `responses`，正配後自動播 `playerCorrect` |
| 第二章 | `debate2.json` | `debatePresent` | 無 `responses`，正配後自動播 `playerCorrect` |
| 第五章 | `debate5.json` | `debatePresent` + `debateReason` | 三柱都有 `responses`，正配只建立待推論，玩家再選推論 |

關鍵分岔在 `narrative.js:331-346`：

- pillar 有 `responses` 時，程式只寫入 `pendingReason`，並顯示「證據已對上，還差一步」。
- pillar 沒有 `responses` 時，程式直接 `say(state, "旅人(你)", playerCorrect)`，隨即打破支柱。

`narrative.js:380-412` 的 `debateReason` 已經具備正確推論、錯誤推論、扣對位、重試與打破支柱的完整狀態機；`narrative.js:737-762` 會把選項投影給 UI，`chapter-ui.js:1019-1032` 已會渲染推論選項。因此修復第一、二章不需要新 widget。

### 3.2 Node 實測

測試做法：各章從實際 `debate:init` 節點建立辯論，給目前支柱正確證據，再呼叫 `debatePresent`。

| 章 | outcome | pendingReason | pillar broken | transcript 結果 |
|---|---:|---:|---:|---|
| ch1 | `correct` | false | true | 旅人先出示 E4，隨後自動說完整 `playerCorrect` |
| ch2 | `correct` | false | true | 旅人先出示 F4，隨後自動說完整 `playerCorrect` |
| ch5 | `reason` | true | false | 只顯示證據已對上，尚未替旅人下結論 |

這不是文字呈現的小問題。第一、二章的玩家動詞實際是「選對證據」；第五章才是「選證據，再決定它能推出什麼」。前者把全章最重要的認識論工作交給系統代做。

### 3.3 三、四章是否共用

三、四章不使用這套 `playerCorrect` 辯論：

- `scenes3.json`、`scenes4.json` 沒有 `system:"debate"` 或 `debate:"init"`。
- 第三章用 `Engine3` 的 dossier/debate 狀態與 `answerDossierDebate`、`setDossierP3Premise` 等 action。
- 第四章用 `Engine4` 的 K4 model ledger、K5 proof/archive action。
- 三、四章仍透過共用 `N.labAction` 分派到章引擎，但不走 `debatePresent/playerCorrect`。

所以修 `playerCorrect` 會直接惠及第一、二、五章的共用辯論契約，不會自動修復三、四章已發現的代理判斷問題；後者仍需在各章 action 中處理。

### 3.4 建議修法

#### 資料契約

每個要由玩家完成推論的 pillar 明列：

```js
reasonMode: "player",
responsePrompt: "這張證據最多能推出哪一句？",
responses: [
  { id: "...", text: "...", correct: false, reply: "..." },
  { id: "...", text: "...", correct: true },
  { id: "...", text: "...", correct: false, reply: "..." }
]
```

第一、二章各三柱補齊同句型、近似長度的推論選項。`playerCorrect` 不再是玩家台詞的執行來源；可保留為通關後筆記中的參考整理，或在 schema cutover 後刪除。

#### 引擎 fail-closed

`debatePresent` 不應再以「有沒有 responses」暗中決定代理權。建議改成：

```js
if (def.reasonMode === "player") {
  if (!Array.isArray(def.responses) || !def.responses.length)
    return { state: state0, error: "本支柱缺少玩家推論資料" };
  // 建立 pendingReason，不打破支柱
} else {
  // 僅 legacy 資料可暫走舊 playerCorrect
}
```

這能避免未來資料漏填 `responses` 時，系統悄悄退回代講。

#### 事件帳

目前正確推論只留下 `pillarBroken`，錯誤推論主要留在 `mistakes`；建議新增 append-only 事件：

```js
{ t:"debateAction", seq:17, action:"present", pid:"P1", target:"s2", evidence:"E4" }
{ t:"debateAction", seq:18, action:"reason", pid:"P1", option:"bounded-cause" }
```

這不只方便學習分析，也讓 sanitizer 有可能從選擇歷史重算辯論投影。

#### 驗收測試

1. 第一、二章正配證據後 transcript 不得包含 `playerCorrect`。
2. 正配證據後 pillar 不得破，必須有 `pendingReason`。
3. 錯誤推論不得破柱，並留下 mistake/event。
4. 正確推論才打破支柱。
5. 中斷、重入、舊存檔在 `pendingReason` 前後皆可恢復。
6. 三章的正確選項不可因長度、分號或「證據邊界」術語洩題。

## 四、`sanitize.js` 跨章審計

### 4.1 現有共用層

`sanitize.js:14-42` 的 `scrub` 是通用結構防線：限制深度、節點數、字串/陣列長度，拒絕非 finite number 與 `__proto__/constructor/prototype`。這層有價值，但它只能回答「資料長得安全」，不能回答「遊戲進度是真的」。

`sanitize.js:205-834` 的 `sanitizeReputationLifecycle` 是目前最接近正確共用審計的部分：它按章節白名單檢查 rep 事件、來源、前置 choice、修復循環與先後順序，並從初始 3 點重播信譽。這個設計應該被推廣到證據、辯論與完章，而不是再增加零散欄位檢查。

章別入口如下：

| 章 | 函式 | 是否注入章引擎 |
|---|---|---:|
| 1 | `sanitizeImport` (`:837`) | 否，只收 patterns |
| 2 | `sanitizeImport2` (`:901`) | 是，Engine2 |
| 3 | `sanitizeImport3` (`:1153`) | 否 |
| 4 | `sanitizeImport4` (`:1661`) | 是，Engine4 |
| 5 | `sanitizeImport5` (`:3636`) | 否 |
| 6 | `sanitizeImport6` (`:3764`) | 是，Engine6 |

### 4.2 Node mutation 實測

#### 章證據旗標

測試從各章 `initialState` 出發，只把一個後期證據旗標設為 `true`，再交給對應 sanitizer。

| 章 | 注入旗標 | 結果 |
|---|---|---|
| ch1 | E5 | 接受 |
| ch2 | F4 | 接受 |
| ch3 | G5 | 接受 |
| ch4 | K5 | 拒絕：章證據與工作台狀態不一致 |
| ch5 | J4 | 接受 |
| ch6 | T5 | 拒絕：章證據與工作台真相不一致 |

這個測試不主張所有旗標都由工作台產生；它證明的是：第一、二、三、五章可以在沒有取得事件、沒有通過里程碑、甚至仍在章首時，直接信任匯入檔自稱擁有的後期證據。

#### 原始物理紀錄

第一章先用引擎生成一筆合法斜面紀錄，再把讀值改成 `[999,1,999,1,999]`；`sanitizeImport` 仍接受。原因是 `sanitize.js:855-871` 只驗 config enum 與 finite number，沒有重算 fixture。

第五章先用引擎生成一筆合法碰撞，再把撞前/撞後速度與兩本帳改成互相矛盾的有限數字；`sanitizeImport5` 仍接受。原因是 `sanitize.js:3676-3686` 只檢查 enum 與 finite number，沒有用 Engine5 重建紀錄。

#### 對比

第二章會用封閉 fixture 重算 series 與 `_judgeRaw`，第四章會比對 `state.evidence` 與 `lab.evidence` (`sanitize.js:2969-2975`)、游標里程碑 (`:3609-3614`) 及完章 (`:3616-3617`)；第六章也會比對 T1–T5、S8、共同頁與完章 (`:3904-3914`)。這些是可重用的方向，但不能因此宣稱第四、六章已完成全 action replay。

### 4.3 共通根因

根因可分成三層：

| 層 | 現況 | 問題 |
|---|---|---|
| 結構 | `scrub` 與章別 enum/長度檢查 | 能防壞形狀，不能證明進度 |
| 自洽 | 例如 `evidence.j1 === assertion.j1.done` | 攻擊者可同時偽造兩邊，仍然自洽 |
| 衍生 | 少數章從 fixture/lab 重算 | 只有衍生驗證能證明結果源自可接受操作 |

所以漏洞不是單純「相信匯入值」五個字，而是把未受信任的 projection 當作 source of truth：

- `state.evidence` 是投影，不是原始事實。
- `debate.status/idx/pillars` 是投影，不是原始選擇。
- `ended` 是投影，不是完章證明。
- `eventLog` 也是匯入資料；若沒有完整 action args 與可重播序列，它只是另一份可偽造聲明。

現行 `narrative.js:1270-1281` 寫入 lab event 時，大多只記 `{t, action, at}`。只有第四章少數 assert action 另外記 args 與 sequence。這代表現在無法對所有舊存檔做完整 replay；修 sanitizer 前必須先承認這個資料缺口。

### 4.4 共用審計函式模式

建議把匯入流程固定為五層，所有章只提供 adapter：

```text
1. sanitizeEnvelope       結構、章別、schema、原型污染
2. normalizeLegacy        只做明列遷移；不得補造證據或事件
3. validateRawRecords     封閉 fixture、enum、單位、來源 ID
4. deriveCanonical        從 raw records/action ledger 重算 lab/debate/evidence
5. compareProjection      比對 evidence、flags、cursor、ended；不符整包拒絕
```

建議 API：

```js
auditChapterImport(state, scenes, engine, {
  chapter: "ch5",
  normalizeLegacy,
  replayAction,
  validateRawRecord,
  projectEvidence,
  projectDebate,
  milestones
})
```

共用 helper：

```js
auditEvidenceProjection(stateEvidence, derivedEvidence)
auditDebateProjection(savedDebate, derivedDebate)
auditMilestoneCursor(cursor, derivedMilestones)
auditEndedProjection(ended, derivedCompletion)
auditAppendOnlySequence(events)
```

`sanitizeReputationLifecycle` 可保留為第一個成功 adapter，逐步併入同一框架。

### 4.5 新舊 schema 過渡

#### 新存檔

每個真正影響狀態的操作記錄：

```js
{
  t: "action",
  seq: 42,
  scene: "E2-2",
  node: "lab2b",
  action: "setCollisionJudgment",
  args: { key:"followup", value:"changes-with-mass" }
}
```

載入時從章引擎 `initialState()` 逐筆 replay，再生成 projection。事件 sequence 必須連續、不可重複；未知 action、非法 args 或 engine error 都拒絕。

#### 舊存檔

舊 event log 缺 args，不可假裝能重播。相容策略只能二選一：

1. 從封閉 raw records 可確定的部分重算，清除無法證明的後期 projection，游標退到最後可驗證里程碑。
2. 若退回會破壞玩家進度且沒有安全映射，保留原始書信碼備份並拒絕匯入，要求舊版完成/匯出後再轉換。

不可根據孤立 `evidence:true` 或自稱完成的 event row 補造歷史，否則遷移層本身就是洗白器。

### 4.6 章別修復路徑

| 章 | 最小修復 | 完整修復 |
|---|---|---|
| 1 | 重算 runs/claims；證據、debate、ended 對里程碑 | action ledger replay |
| 2 | 保留 series fixture 重算；補 F1/F3/F4、debate 與 cursor 投影 | action ledger replay |
| 3 | 對 G1–G5 建 evidence projection；G5/完章與 dossier 真相綁定 | Engine3 action replay |
| 4 | 保留既有 evidence/cursor/ended 稽核；補足所有 action args | 完整 sequence replay |
| 5 | `sanitizeImport5` 注入 Engine5；重算 collision/clay/assertions/debate/J4 | action ledger replay |
| 6 | 保留 T1–T5/joint/cursor 稽核；確認 raw records 都由 engine 可重建 | 完整 sequence replay |

## 五、無障礙系統

### 5.1 現行操作盤點

| 章 | 主要輸入 | 鍵盤等價 | 觸控尺寸現況 | 判斷 |
|---|---|---|---|---|
| 1 | select、number、checkbox、button | 原生控制可用 | button 44 px；select/input 基線 36 px | 基本可用，但未全達 44 px |
| 2 | select、number、checkbox、button | 原生控制可用 | 低高度自訂 CSS 把部分控制縮到 28–38 px | 明確不一致，優先修 |

共用層優點：

- `stage.html:240` 有全域 `:focus-visible`。

- 第二章低高度 CSS 的 `.catPartBtn` 32 px、校準鈕 30 px、select 28 px、預測 input 38 px，與 44 px 原則直接衝突（`stage.html:997-1008, 1042, 1071-1073`）。
- 第五章工作台 CSS 沒有為 select/checkbox 建立明確 44 px 觸控盒。
- 原生 checkbox 本體小，若沒有把整列 label 做成可點擊熱區，手機容易誤觸。

### 5.2 新拖曳方案是否違反第四章裁決

第四章現行法源很明確：

- `第四章重設計_定案帳` 的 runtime 取代註記寫明主操作為「轉鍵＋逐拍落筆，不採拖曳」。
- `第四章v0.8存檔遷移表與契約測試:83` 明訂 D2-1 不得綁 `pointerdown/pointermove`，方向只能由轉鍵或左右鍵改變。
- 同文件 `:108-110` 再確認主操作=轉鍵、拖曳已移除。

因此：

| 提案 | 是否違反 |
|---|---|
| K1 把拖箭頭重新設為必要操作 | 是，直接違反已鎖契約，需總監另立 ADR 才能改 |
| K1 保留轉鍵/鍵盤，另加可選拖曳 | 仍會讓既有「不得綁 pointer」契約轉紅；需裁決，但無障礙風險較低 |
| K2 紙尺拖疊作為唯一操作 | 未必逐字撞 D2-1 條款，但違反同一裁決的可達性理由，不建議 |
| K2 紙尺可點格/按鍵折疊，拖曳只是可選 adapter | 可行；引擎只收離散 fold/overlay action |
| 第一、二章可拖預測旗，另有鍵盤/點格等價 | 不受第四章專屬契約約束，符合全系列無障礙原則 |
| 第一、二章只能拖預測旗 | 不可接受；鍵盤與精細動作障礙玩家無法完成 |

### 5.3 建議的跨章輸入架構

不要讓章引擎知道「滑鼠拖了幾公分」。引擎只收語意 action，輸入層提供多個等價 adapter：

```text
pointer drag ┐
tap slot     ├──> setPredictionBand("far") ──> engine/state
arrow keys   ┤
button step  ┘
```

具體規則：

1. 不使用 HTML5 drag-and-drop；用 Pointer Events 時必須處理 cancel/capture，但不能是唯一入口。
2. 拖曳物件必須可 focus，方向鍵能移到同一組離散位置，Enter 封存。
3. 每個停靠點至少 44x44 px，具清楚 label 與 `aria-pressed`/`aria-valuetext`。
4. 不要求像素級精準；採 snap-to-slot，物理判斷由離散區間承載。
5. 所有 adapter 呼叫同一個 action，改變設定後要撤銷舊揭曉/證據，避免 UI 與 state 分叉。

對 K2，「紙尺折疊」應做成三個可聚焦折點或兩段尺的對齊槽，而不是自由拖到 1.4 mm；玩家操作的是「把同一比例套兩次」，不是手眼精度。

## 六、手機橫屏

### 6.1 共用舞台能力

共用外殼支援是存在的：

- `stage-ui.js:1361-1422` 以能力偵測呼叫 Fullscreen API，成功後嘗試 `screen.orientation.lock("landscape")`，失敗時不阻斷遊戲。
- `stage.html:537-549` 在 `(orientation:portrait) and (pointer:coarse)` 時把整座 16:9 stage 旋轉 90 度，處理不能鎖向的手機。
- `stage.html:1406-1445` 對 844x390/932x430 類低高度視窗另做一、二章實驗/辯論排版。
- 第三、四章各自有低高度 media query，主控制多數回到 44 px。

但 `stage-ui.js` 沒有共用 `visualViewport` 尺寸協調器，也沒有能替章內工作台保證「當前物件、操作、回饋同屏」的 layout contract。現在主要靠一大批章別 CSS media query，因此不能用「外殼有橫屏」推論每章工作台都完成手機驗收。

### 6.2 章別落差

| 章 | 低高度支援 | 主要風險 |
|---|---|---|
| 1 | 有共用 lab/debate 分支 | number/select 小於 44 px；長表格需捲動 |
| 2 | 有 catapult 專屬分支 | 為塞版而把控制縮到 28–38 px，觸控風險最高 |
| 3 | 有 ship 專屬分支 | 雙欄+工作區內捲動；range slider 與頁面捲動需避免手勢衝突 |
| 4 | 有 orbit 專屬分支 | 兩欄最小寬 265+430；新增圖層容易把轉鍵/落筆推到摺頁外 |
| 5 | 只有 `@media(max-width:840px)` | 844x390 剛好不命中單欄，仍是雙頁；沒有低高度專屬密度與固定操作區 |

第五章是最清楚的跨章不一致：`stage.html:2638-2642` 只有寬度 840 的斷點。真機常見 844x390 正好留在雙欄，工作台又有 120 px 圖、三張斷言、330 px 表格與操作區，雖可捲動，不代表玩家看得到「設定 -> 原紙 -> 判讀 -> 提交」的因果鏈。

### 6.3 新設計的手機風險

| 新設計 | 風險 | 修法 |
|---|---|---|
| K1 拖箭頭 | CSS 旋轉舞台、工作台捲動與 pointer 座標/手勢衝突；手指遮箭頭 | 不重啟必要拖曳；保留轉鍵/鍵盤，圖只顯示結果 |
| K2 紙尺自由拖疊 | 小尺標、手指遮住 1.4 mm、拖曳與水平捲動衝突 | 離散折點、點格、按鍵；放大局部尺窗，不要求像素對齊 |
| 第一章預測旗 | 斜面表格已高，新增軌道會擠掉數據 | 將旗放在數據列內，三個離散槽；封存後收成一行 |
| 第二章 H=25 預測旗 | catapult 低高度控制已過小 | 先修 44 px 與版面，再用四格射程帶；禁止自由精細拖曳 |

### 6.4 手機驗收矩陣

每個新互動至少要分開驗：

| 層 | 尺寸/方式 | 驗收 |
|---|---|---|
| 桌機 | 1536x960 | 物件、控制、回饋同屏；鍵盤完整通過 |
| 真橫屏 | 844x390、932x430 | 無遮擋、無不可達控制、觸控 >=44 px |
| 直拿自動旋轉 | 390x844 coarse pointer | 點擊/滑動方向正確，沒有座標偏移 |
| 文字放大 | 200% | 不靠縮到 10–12 px 塞版；可捲但順序清楚 |
| 動態 | reduced-motion | 狀態差異保留，不靠動畫時間判定 |
| 輸入 | touch、keyboard、screen reader | 所有核心 action 等價可完成 |

## 七、一次修復惠及多章的施工切片

### Slice A：推論代理權（低風險、高收益）

1. 新增 `reasonMode` 資料 lint。
2. 第一、二章補 `responses`。
3. 共用 `debatePresent` fail-closed。
4. 加 transcript/支柱負向測試。
5. 瀏覽器走三柱與中止重入。

### Slice B：投影一致性護欄（中風險、高收益）

1. 先加 `auditEvidenceProjection`、`auditEndedProjection`、`auditMilestoneCursor`。
2. 套第一、二、三、五章，阻止章首直接注入後期證據。
3. 第五章 sanitizer 注入 Engine5，重算 record fixture。
4. 第一章從 patterns 重算 readings/claims。
5. mutation 測試固定成常駐契約。

### Slice C：可重播 action ledger（高風險、必要基建）

1. 新 schema 記 `seq/action/args/scene/node`。
2. engine action 全部走單一 dispatcher 並輸出 canonical event。
3. sanitizer 從 initial state replay。
4. 舊存檔走明列 legacy adapter，不補造歷史。
5. projection 不符整包拒絕或退最後可驗證里程碑。

### Slice D：無障礙與橫屏（可獨立施工）

1. 修第二章低高度所有控制至 44 px。
2. 補第五章 844x390 專屬排版。
3. 建共用 semantic-control adapter，拖曳只作增強。
4. K1 保持現行轉鍵裁決；K2/預測旗做離散槽。
5. 完成實機與讀屏驗收後才宣稱可用。

## 八、最終判斷

1. `playerCorrect` 是已證實的跨章代理權問題，但也是最低成本可修的問題：第五章已經把答案放在同一引擎裡，第一、二章直接跟進即可。
2. `sanitize.js` 需要從「章別白名單集合」升級成「可信原始操作重播 + 投影比對」框架。短期先補 evidence/cursor/ended 守衛，長期才做新 schema action ledger；不要宣稱只加幾個 `if` 就完成。
3. 第四章「拖曳已移除」不是美術偏好，是手機與鍵盤風險裁決。K1 不應倒退；K2與一、二章可以有拖曳感，但只能是多輸入 adapter 之一。
4. 手機支援不是五章一致完成。第二章觸控尺寸、第五章 844x390 是當前最明確的跨章缺口；任何新互動都應先過這兩處再擴散。
