# 《發現之前》跨章共用系統——三方交叉驗證最終報告

**日期**：2026-08-03
**性質**：唯讀審查，均未修改runtime。範圍：`narrative.js`辯論引擎、`sanitize.js`存檔清洗器、無障礙設計、手機橫屏體驗——四個橫跨多章、此前只在各章脈絡裡順便提到、從未整體審查過的系統。

## 一、🟢 好消息：playerCorrect問題「已經有答案」，只是還沒推廣到全部章節

**claude與codex互相驗證confirm同一件事**：第五章的「配對正確證據後系統自動代講完整論證」問題，**引擎裡其實已經修好了**——`narrative.js`有一套`responses→debateReason`機制：若某柱宣告了`responses`，配對正確後不會立即破柱，而是掛起`pendingReason`，玩家要自己再選一次「這張證據能推出什麼」，選對才真正破柱。**第五章三柱都已經填好這個資料，現在真的是玩家自己選推論。**

**Node實測結果（codex）**：
| 章 | outcome | pendingReason | pillar broken |
|---|---|---|---|
| 一 | correct | false | true（自動代講） |
| 二 | correct | false | true（自動代講） |
| 五 | reason | true | false（玩家自己選推論） |

**真正還沒修的只剩一章的P1/P2支柱、二章的三柱**。三、四章不共用這套系統（各自用dossier/K4等獨立機制，這套修法不會自動惠及三、四章）。

**修法極其便宜**：引擎的分岔邏輯本來就寫好了，**只要幫一、二章的柱子補齊`responses`資料（一個正解+兩個誘答+回應台詞，約25句台詞），不需要新寫任何UI元件**。codex估計整批（含fail-closed硬化、事件記錄、驗收測試）約2-3個工程日，claude估計核心部分「0行程式+25句台詞」。**這是本輪所有發現裡，投報率最高、風險最低的一項。**

**建議引擎順便做的硬化**（codex）：把「有沒有responses」的暗中判斷改成明確的`reasonMode:"player"`宣告+fail-closed，避免未來新章節資料漏填時又悄悄退回代講。

## 二、sanitize.js：不是「少幾個檢查」，是把「投影當成事實」

**codex的Node mutation矩陣**（從各章初始狀態直接注入一個後期證據旗標，看sanitizer擋不擋）：

| 章 | 注入旗標 | 結果 |
|---|---|---|
| 一 | E5 | **接受**（章首直接跳到後期進度都會過） |
| 二 | F4 | **接受** |
| 三 | G5 | **接受** |
| 四 | K5 | 拒絕 |
| 五 | J4 | **接受** |
| 六 | T5 | 拒絕 |

**更嚴重的是原始物理數據也能造假**：codex把第一章一筆合法斜面紀錄的讀值改成`[999,1,999,1,999]`、第五章一筆合法碰撞改成撞前撞後速度互相矛盾，**兩個sanitizer都照樣接受**，因為它們只驗證資料格式（enum、是否為有限數字），沒有用引擎重新計算驗證資料本身是否合理。

**根因（codex提出的三層框架，很有解釋力）**：
- **結構層**：能防「格式壞掉」，不能證明「進度是真的」
- **自洽層**：例如檢查`evidence.j1 === assertion.j1.done`——但攻擊者可以同時偽造兩邊，一樣自洽
- **衍生層**：只有從原始紀錄重新算出來的驗證，才能證明結果真的來自合法操作——**目前只有二、四章做到這層**

**claude修正codex一個具體誤解**：`sanitizeImport2()`其實**有**重算series與F2（逐筆重判每個衍生欄位），**它不是漏洞，是全專案的標準答案**，二章的做法應該被當範本推廣，不是被列為問題。

**claude獨立發現的新洞（codex報告未提及）**：第五章的存檔遷移段會**由`evidence`布林反推`judgments`**（`j1: evidence.j1 ? "both-close" : null`），而另一段檢查又要求「`evidence.jN`為真則`judgments.jN`必須等於正解」。**兩段合起來：偽造一個`evidence.j1=true`且故意不帶`judgments`的存檔，遷移段會主動幫你把缺的判讀資料補齊，然後通過檢查**——等於遷移路徑親自把偽造資料的拼圖補完整。修法約5行。

**共用修法方向（codex提出的五層架構，claude認同「稽核骨架可以共用，稽核內容不能」）**：
```
1. sanitizeEnvelope     結構、章別、schema、原型污染
2. normalizeLegacy      只做明列遷移，不得補造證據或事件
3. validateRawRecords   封閉fixture、enum、單位、來源ID
4. deriveCanonical      從raw records重算lab/debate/evidence
5. compareProjection    比對evidence/flags/cursor/ended，不符整包拒絕
```

**⚠️ 有先後依賴，順序不能顛倒（claude提醒）**：一章的第五段預測是循環認證的（`target=9*avg[0]`，怎麼算都對），**這個bug沒先修掉，一章的「衍生層」稽核就沒有可比對的真值**——必須先修引擎再補稽核，不能反過來。

**六章是唯一免回填的一章**（claude）：它還在劇本階段，`sanitizeImport6`目前只做存在性檢查、沒有真的呼叫`engine6`重算，這是把「衍生層稽核」寫進規格的唯一免costly-migration機會。

## 三、無障礙：現況比想像中健康，但這代表我們先前的重新設計方案需要調整

**claude的關鍵發現（推翻先前假設）**：**全專案目前完全沒有任何拖曳互動**——搜尋`chapter-ui.js`/`narrative.js`的pointer/drag/touch事件處理，結果是**零**。第四章「拖曳已移除、只能用轉鍵」不是單一章節的美術偏好，**codex確認這是手機與鍵盤風險的正式裁決**（`第四章v0.8存檔遷移表`明文規定D2-1不得綁定pointerdown/pointermove）。

**這意味著：我們先前提出的所有拖曳類設計（K1拖箭頭、K2紙尺疊合、一二章拖曳預測旗），會是這個專案第一段pointer事件程式碼**，風險比原本設想的高。

**codex給出的逐項裁決表**：
| 提案 | 是否違反現行裁決 |
|---|---|
| K1把拖箭頭設為必要操作 | **是**，直接違反已鎖契約 |
| K1保留轉鍵/鍵盤，另加可選拖曳 | 仍會讓「不得綁pointer」的契約轉紅，需裁決 |
| K2紙尺拖疊作為唯一操作 | 不建議 |
| K2可點格/按鍵折疊，拖曳只是可選adapter | **可行** |
| 一二章可拖預測旗，但要有鍵盤/點格等價方案 | **符合原則** |
| 一二章只能拖預測旗 | **不可接受**——鍵盤與精細動作障礙玩家無法完成 |

**claude已經把先前的設計方案改寫成不需要拖曳的版本**：
- K1形狀預測 → 三選一形狀卡按鈕（本來就是三分類問題，不需要連續自由度）
- K2同一把尺 → 直接複用第四章既有的轉鍵元件，轉一格同步顯示「距離倍數/弱化倍數」
- 一章第五段、二章H=25 → 離散刻度按鈕列，選中即預覽落點

**codex提出的通用架構**：引擎只收語意動作（如`setPredictionBand("far")`），輸入層可以有拖曳/點格/方向鍵/按鈕步進四種等價adapter同時存在，不要讓引擎知道「滑鼠拖了幾公分」。

## 四、手機橫屏：共用外殼一致，但章內工作台覆蓋率嚴重不均

**兩方都確認**：共用外殼（全螢幕、橫向鎖定、直拿自動旋轉、reduced-motion）做得不錯，**iOS Safari不支援`screen.orientation.lock`這件事，作者已經用「把portrait也算進小螢幕規則」的方式處理了**，這點是對的。

**但章內落差很大（claude的實測數據）**：
| 表面 | 小螢幕媒體區塊覆蓋率 |
|---|---|
| 四章orbit | 24% |
| 共用Sheet | 26% |
| **五章collision** | **0%** |
| **二章Series** | **0%** |

**codex補充具體風險點**：
- **第二章低高度模式把部分控制縮到28-38px**（低於44px無障礙原則），觸控風險最高
- **第五章只有`max-width:840px`這一個斷點**，真機常見的844×390解析度剛好「差一點」不觸發，導致工作台還是雙欄擠在一起，玩家看不清楚「設定→原紙→判讀→提交」的因果鏈

**新設計的手機風險排序（claude）**：疊合台/並排比較類設計風險最高（兩物並置最容易撐破520px高度限制，且五章這類介面完全沒有可繼承的既有規則）；離散刻度按鈕列中等風險；K1形狀卡與K2轉鍵風險最低（可以直接複用覆蓋率最高的orbit介面既有規則）。

## 統計

四個跨章系統中，**playerCorrect是投報率最高、可以立即動手的一項**（第五章已經示範了正確做法，一二章只要跟進）；sanitize.js的問題最根本但修復工程量最大（建議分Slice B/C兩階段）；無障礙現況其實比預期健康，但意味著先前提出的多個拖曳類重新設計方案都需要補上非拖曳的等價操作；手機橫屏的兩個明確缺口（二章觸控尺寸、五章844×390斷點）建議在任何新互動設計上線前優先修復。
