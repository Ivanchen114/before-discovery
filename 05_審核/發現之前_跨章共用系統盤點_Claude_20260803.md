## 一、`narrative.js` 辯論引擎的 `playerCorrect` 自動代講機制

### 1.1 一、二、五章是同一套邏輯嗎？——是，同一個函式

三章共用 `narrative.js:306 debatePresent()`。關鍵分岔在 L332：

```js
if (isCorrect) {
  if (Array.isArray(pillarDef(pid).responses) && pillarDef(pid).responses.length) {
    d.pendingReason = { pid, target, evidence, subitem };
    say(state, "旅人筆記", "【證據已對上】還差一步：這張紙究竟推得出什麼？");
    outcome = "reason";                    // ← 玩家還要再選推論
  } else {
    say(state, "旅人(你)", pillarDef(pid).playerCorrect);   // ← 系統代講
    say(state, opponentSpeaker(), pillarDef(pid).breakReply);
    d.pillars[pid].broken = true; d.idx += 1;
    outcome = "correct";
  }
}
```

配對正確後若該柱宣告了 `responses`，就不破柱，而是掛起 `pendingReason`，等玩家呼叫 `debateReason(optionId)`（L380）。`debateReason` 的行為：

- 選錯 → 教練駁回 + `debatePersuasion(state, -1, "debate.reason")` + `rememberMistake(kind:"reason")` + `outcome:"retry"`，**證據不收回、柱不破**，可重選
- 選對 → 才輪到 `breakReply`、破柱、`d.idx += 1`

也就是說：**「玩家親選推論而非系統代講」的機制已經完整實作，而且是純資料開關。** 引擎那半已經寫完了。

### 1.2 資料側現況：只有第五章開了

| 章 | 支柱 | `responses` 數 | 有 `playerCorrect` | 實際走哪條 |
|---|---|---|---|---|
| 一 (`debate.json`) | P1 / P2 | 0 / 0 | 有 / 有 | **系統代講** |
| 一 | P3 | 0 | 有（且 `useLegacy: true`）| **不走 `debatePresent`**，走 `engine.js` 的 legacy 單柱路徑 |
| 二 (`debate2.json`) | P1 / P2 / P3 | 0 / 0 / 0 | 有 / 有 / 有 | **系統代講** |
| 五 (`debate5.json`) | P1 / P2 / P3 | **3 / 3 / 3** | 有（成為 fallback，實際不觸發）| **玩家親選推論** |

所以 general 與 codex 的分歧在這裡可以完全收束：codex 說「五章的 `playerCorrect` 是系統代講」在**引擎讀法上**是對的（那行程式確實存在），但在**執行路徑上**已經不成立了 —— 五章三根柱都宣告了 `responses`，L340 那行對第五章是死碼。真正還在自動代講的是**一章 P1/P2 與二章 P1/P2/P3**。

### 1.3 三、四章是否共用？——都不共用，且四章確實沒有傳統辯論

用資料層驗證，不靠推測：

- `data/` 底下只有 `debate.json` / `debate2.json` / `debate5.json`。三、四章**沒有 debate 資料檔**。
- `scenes3.json` 的 embed 節點只有一個：`C1-1/e1: ship`。三章的三柱辯論在 dossier 內部（`engine3.js`），與 `narrative.js` 的 `debatePresent` 完全獨立。順帶一提，dossier 的辯論本來就是逐步問答，玩家本來就在選，**三章沒有這個病**。
- `scenes4.json` 的 embed 節點是 `orbit` ×7（D1-1、D1-2、D2-1、D3-1、D4-1、D4-2、DE-1），沒有任何 debate。**四章確實沒有傳統辯論，general 的猜測正確。**

### 1.4 修法：純資料撰寫，零引擎改動

要修的只有 5 根柱（一章 P1/P2、二章 P1/P2/P3），每根柱補一個 `responses` 陣列：

```json
"responses": [
  { "id": "r1", "text": "<正解推論，玩家口吻>", "correct": true },
  { "id": "r2", "text": "<過度外推的誘答>", "reply": "<教練：這張紙沒說到那麼遠>" },
  { "id": "r3", "text": "<收得太窄的誘答>", "reply": "<教練：那你剛才那張紙就白出了>" }
]
```

- **工程量**：0 行程式。資料約 5 × (3 選項 + 2 條 reply) ≈ 25 句台詞。
- **風險**：極低。未宣告 `responses` 的柱維持原流程（L332 的 `Array.isArray` 守衛），這是天然的向後相容，舊存檔不受影響。
- **一章 P3 是唯一例外**：它 `useLegacy: true`，走 `engine.js` 的 legacy 路徑，補 `responses` 不會生效。要修得先把 P3 收斂進 `narrative.js`，那才是真的引擎工作。**建議先做一章 P1/P2 + 二章三柱（純資料），P3 單獨列一項。**
- **撰寫時的品質要求**：誘答不能比正解口語。我在二～五章各查到一例、六章劇本查到 10/13 例的「正解比誘答書面化」洩題，這批新資料是同一個坑，寫的時候要把三個選項的語域壓平。

## 二、`sanitize.js` 存檔清洗的漏洞

### 2.1 先修正一個前提：三個洞不是同一個根因

各章 sanitizer 的規模差 30 倍，這個落差本身就是結論：

| 函式 | 起始行 | 行數 | 重算呼叫數 | 防護層級 |
|---|---|---|---|---|
| `sanitizeImport`（一） | 837 | **64** | **0** | **T1 形狀＋enum** |
| `sanitizeImport2`（二） | 901 | 252 | 3 | **T3 物理重算** |
| `sanitizeImport3`（三） | 1153 | 508 | 0 | T2 交叉一致性 |
| `sanitizeImport4`（四） | 1661 | **1975** | 9 | **T3 物理重算** |
| `sanitizeImport5`（五） | 3636 | 128 | 0 | T2 交叉一致性 |
| `sanitizeImport6`（六） | 3764 | 179 | **0** | **T1 形狀＋enum** |

三種層級的實際內容：

**T3 物理重算（二、四章）** —— 從原始讀值重跑判定，比對每一個衍生欄位：

```js
var judged2 = engine2._judgeRaw(readings, sr.prediction);          // sanitize.js:1094
if (sr.accepted !== judged2.accepted || !sameNumber2(sr.kHat, judged2.kHat) || ...)
  return fail(...);
```

F2 更是三重交叉：`lawSource` 必須指向一筆 `status==="complete" && accepted` 的 series；`validBallPair2` 由 `engine2.compareBalls` 對所有 series 兩兩重算；然後 `hasF2Lab2`（實驗推出來的）必須等於 `hasF2Story2`（存檔自稱的），還要在 eventLog 裡有**恰好一筆** `{t:"evidence", id:"F2", at:"lab2"}`。

**這是全專案的標準答案。** 所以要修正 codex 的說法：`sanitizeImport2()` 並非「不重算 series/F2」—— 它重算得比任何其他章都徹底。它不是洞。

**T2 交叉一致性（三、五章）** —— 不碰物理，但強制欄位互相咬合。五章：

```js
if (lab.evidence.j1 !== lab.assertions.j1.done || ...) return fail(...);      // ~L3720
if ((lab.evidence.j1 && lab.judgments.j1 !== "both-close") || ...) return fail(...);
lab.assertions.j3.sources.some(id => !clayIds[id])                            // sources 必為真實 run
```

偽造 `evidence.j1` 會被 `assertions.j1.done` 擋下，`sources` 也必須指向真實存在的碰撞紀錄。這是有效防線，只是擋不住「連 assertions 一起偽造、sources 指向真實但讀值不支持結論的 run」。

**T1 形狀＋enum（一、六章）** —— 一章 64 行從頭到尾只驗結構與 enum：`mode`、`rep` 範圍、`cursor.scene` 存在、每筆 run 的 `config` 四維在 `patterns` 裡、`readings` 是有限數字、transcript 長度。**它一次都沒有碰 `lab.evidence` 或 `state.flags`。** 所以「憑空自稱 F2」不是 F2 專屬的洞 —— **一章所有證據布林與所有 flag 都是無條件信任的**，F2 只是最容易示範的那一個。

### 2.2 我這次新發現的第五章洞：遷移路徑洗白偽造證據

`sanitize.js:3657-3661`（`sanitizeImport5` 開頭的 legacy 相容段）：

```js
if (lab && !lab.judgments) lab.judgments = {
  j1: lab.evidence && lab.evidence.j1 ? "both-close" : null,
  j2: lab.evidence && lab.evidence.j2 ? "steel-close-putty-short" : null,
  j3: lab.evidence && lab.evidence.j3 ? "speed-squared" : null,
  followup: lab.evidence && lab.evidence.followup ? "legacy-unsealed" : null
};
```

這段**由 `evidence` 反推 `judgments`**。而 L3733 那條檢查是「若 `evidence.jN` 為真，則 `judgments.jN` 必須等於正解」。兩段合起來：一份偽造了 `evidence.j1 = true` 且**故意不帶 `judgments` 欄位**的存檔，會被遷移段主動補上合法的 `judgments.j1 = "both-close"`，然後順利通過那條檢查。**遷移路徑替偽造資料補齊了它缺的那塊拼圖。**

修法很小：遷移時把補出來的判斷標記為 `migrated: true`，或者遷移段只在 `state.schemaVersion` 低於當前值時執行（現在是只看欄位有無）。

### 2.3 真正的共同根因

不是「信任匯入的布林值」—— 二、四章不信任，五章半信任。真正的根因是：

> **沒有任何共用契約要求一章宣告自己的 sanitizer 實作到哪一層。**

證據：ch2 的作者把原則寫下來了，就在 `sanitize.js:899-900`：

```js
/* 第二章白名單：工坊資料與第一章 runs/claims 形狀不同，禁止拿第一章 sanitizer 硬套。
   這裡驗結構與 enum；fixture 成敗仍由 Engine2 重算，不相信匯入檔自稱 accepted。 */
```

**這條原則是對的，但它活在一個函式上方的註解裡，不在共用程式碼裡。** 所以它沒有傳染給三、五、六章。層級高低變成「誰寫的、什麼時候寫的」的偶然結果，不是設計決策。

### 2.4 共用修法：table-driven 稽核骨架

各章的 lab 形狀是真的不同（一章 runs/claims、二章 slots/series、三章 dossier、四章 orbit、五章 collisions），所以不可能有一個 drop-in 函式吃下全部。**能共用的是稽核骨架，不是稽核內容。**

```js
/* 共用：每章宣告一張表，骨架強制三條不變量 */
function auditDerived(lab, eventLog, spec) {
  for (var key in spec) {
    var s = spec[key];
    var claimed = !!(lab.evidence && lab.evidence[key]);
    // 不變量 1：衍生值必須能從原始資料重算出來
    var derived = s.recompute ? !!s.recompute(lab) : null;
    if (derived !== null && derived !== claimed)
      return fail(key + " 故事證據與實驗紀錄不一致");
    // 不變量 2：來源必須指向真實紀錄
    if (claimed && s.sources && !s.sources(lab))
      return fail(key + " 的來源紀錄不存在");
    // 不變量 3：eventLog 必須有恰好一筆取得事件
    if (s.eventAt) {
      var n = eventLog.filter(e => e.t === "evidence" && e.id === key && e.at === s.eventAt).length;
      if (n !== (claimed ? 1 : 0)) return fail(key + " 缺少唯一的取得事件");
    }
  }
  return { ok: true };
}
```

- 二、四章已經有 per-chapter 的那一半（`_judgeRaw`、`canonical*`、`compareBalls`），改成填表即可，行為不變 —— 這步是重構，不是新功能，可以先做來驗證骨架。
- 一章要新寫 `recompute`。但一章有個先決問題：它的第五段預測是循環的（`target = 9 * avg[0]`，`predDev` 恆為 0，我已用 Node 驗過 42/54 組 `predHit=true` 而 `consistent=false`），**在預測循環修掉之前，一章的 `recompute` 沒有可比對的真值。** 這兩件事有依賴關係，順序是先修引擎再補稽核。
- 五章補 `sources`（已有一半）與 `eventAt`（沒有）。
- **六章是唯一能一開始就內建、不用事後回填的。** 現況：`sanitizeImport6` 已經把 `engine6` 收進參數，但只用來做存在性檢查（`typeof engine6.gate !== "function"` 就 fail），**從頭到尾沒有呼叫它重算任何東西**；同時它信任 `lab.chipBench.judged`、`lab.frictionBench.judged`、`lab.dryBench.judged`、`lab.airBench.judged` 四個布林。六章還在劇本階段，這是把契約寫進規格、而不是六個月後再回頭補的唯一時機。

值得肯定的是，六章已經有兩條**同類型**的交叉檢查了：「來源已否證但封條未裂」、「未判讀封條被提前改變」。作者的直覺是對的，只是還沒推到 evidence 布林上。

## 三、無障礙一致性

### 3.1 現況盤點：全專案沒有拖曳

實測各檔的 pointer/drag/touch handler 數量：

| 檔案 | `pointerdown`/`pointermove`/`dragstart`/`draggable`/`touchstart` |
|---|---|
| `src/chapter-ui.js`（7871 行，五章實驗台全在這） | **0** |
| `src/narrative.js` | **0** |
| `src/stage-ui.js` | 2 —— 都是 `unlockAudioOnce`（L1887/1893），解鎖音訊用，不是互動 |

**五章實驗台的每一個操作都是按鈕、下拉、或轉鍵。沒有一處拖曳。** 四章那條裁示（總監 2026-07-28：避免 pointer 事件的無障礙與橫屏問題）不只在四章生效，它事實上是全專案的實作慣例。

鍵盤與 aria 覆蓋：`chapter-ui.js` 54 處、`stage-ui.js` 33 處（`keydown`/方向鍵/`role="slider"`/`aria-*`）。也就是說既有互動全部走原生可聚焦元素，鍵盤操作是免費得到的，這是「只用按鈕與下拉」的直接紅利。

### 3.2 所以我要撤回一批設計的載體

被影響的是我先前提過的四項：

| 我提的設計 | 問題 | 改用什麼 |
|---|---|---|
| K1（D2-1）形狀預測改拖曳 | 會是專案第一段 pointer 程式 | 三選一的形狀卡按鈕（圓／橢圓／不閉合），本來就是三分類問題，不需要連續自由度 |
| K2「同一把尺」拖曳撥盤 | 同上；gemini 的撥盤也同 | **轉鍵**（四章既有元件，可直接複用）：一格一格轉倍率，每轉一格畫面同步顯示「距離 ×N ／ 弱化 ×N²」，把盲猜換成看得見的連動 |
| 一章第五段預測旗（沙盤插旗） | 同上 | 既有的**離散刻度按鈕列**：把 9×avg 的候選值排成一列可聚焦的刻度鈕，選中即預覽落點 |
| 二章 H=25 預測旗（木槽釘鈴） | 同上 | 同上，或沿用二章既有的 series 面板加一列候選鈕 |

**設計意圖一項都不必放棄** —— 「把數字輸入換成看得見的空間判斷」這個目標，用轉鍵與離散刻度鈕都達得到，而且不用付 pointer 事件的無障礙代價，也不用付下面第四節要講的小螢幕代價。轉鍵已經在四章跑過一輪，複用成本比新寫拖曳低一個量級。

需要補回鍵盤/純數字替代的地方：目前**沒有**。既有五章都是原生元件。這條在專案裡是健康的，要守住的是別讓新設計破壞它。

## 四、手機橫屏

### 4.1 斷點慣例：高度一致，這點做得好

`stage.html` 有 40 個 `@media`、22 個含 orientation/max-height 的小螢幕區塊，其中絕大多數是同一條：

```css
@media (max-height: 520px),
       (orientation: portrait) and (pointer: coarse) and (max-width: 520px) { ... }
```

同一條字串重複約 18 次。這是**很好的一致性** —— 有一個明確的「手機橫屏」定義，而且大家都用它。少數變體 `(max-height:520px) and (min-width:701px)` 是刻意區分平板橫放的。

各章的 lab 樣式落點也清楚：`stage.html` 負責 shell 與四、五章的實驗台外觀，`chapter-ui.js` 幾乎不寫樣式（全檔只有 5 處 style 相關）。

### 4.2 覆蓋率不均：五章碰撞台 0%

用腳本量測「該章選擇器有多少比例落在小螢幕媒體區塊內」：

| 章 / 表面 | 全檔選擇器數 | 在小螢幕區塊內 | 覆蓋率 |
|---|---|---|---|
| 四章 `orbit` | 391 | 92 | 24% |
| 五章 `collision` | 35 | **0** | **0%** |
| 二章 `Series` | 11 | 0 | 0% |
| 共用 `Sheet` | 43 | 11 | 26% |

**五章碰撞台在 `stage.html` 裡有 30 個選擇器，一個都不在任何小螢幕媒體區塊內。** 二章的 series 面板同樣是 0。四章雖然只有 24%，但 391 個選擇器裡有 92 個做了橫屏處理，量體最大也照顧得最多。

三章 dossier 反而最安全：`stage.html` 裡 **0 命中**，`chapter-ui.js` 裡 57 處但該檔幾乎不寫樣式 —— 它完全吃共用外殼，所以自動繼承了 shell 的所有橫屏規則。這是「不做客製」的紅利。

### 4.3 橫屏鎖定在手機 Safari 上實際無效

`stage-ui.js:1383-1389`：

```js
function lockLandscape() {
  try {
    if (screen.orientation && screen.orientation.lock) {
      var lock = screen.orientation.lock("landscape");
      if (lock && lock.catch) lock.catch(function () {});
    }
  } catch (e) {}
}
```

兩層限制：只在 `standalone()`（PWA/全螢幕）情境呼叫；`screen.orientation.lock` **iOS Safari 不支援**。所以在手機 Safari 上，橫屏完全靠 `#playAdvice` 的勸告文字，實際版面必須自己在直立下也能用 —— 這就是為什麼那條 media query 把 `(orientation: portrait) and (pointer: coarse) and (max-width: 520px)` 也算進「小螢幕」的原因。作者已經處理了這個現實，這點是對的。

### 4.4 新設計的小螢幕風險

| 提案 | 風險 | 說明 |
|---|---|---|
| K2 疊合台／並排比較 | **高** | 「兩物並置比較」在 `max-height: 520px` 下最容易撐破。而且它屬於五章家族 —— 上表已證明 `collision` 有 0 條既存橫屏規則可繼承，等於得從零寫 |
| 一/二章離散刻度鈕列 | 中 | 橫向刻度列在 520px 寬度下要能橫向捲動或折行；二章 `Series` 覆蓋率也是 0% |
| K1 三選一形狀卡 | **低** | 三顆按鈕，任何斷點下都能直排。這是四項裡最安全的 |
| K2 轉鍵 | **低** | 轉鍵是四章既有元件，而 `orbit` 是覆蓋率最高（24%、92 條）的表面，有現成規則可抄 |

風險排序剛好支持第三節的結論：**改用轉鍵與離散按鈕，不只省下 pointer 事件的無障礙代價，也落在既有橫屏規則覆蓋最好的地方。** 疊合台若要保留，得先替五章 `collision` 補一整組橫屏規則，那是獨立的一項工作。
