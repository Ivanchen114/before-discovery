## 二、B 層 B-1｜「40 筆 ADR 均有 CURRENT 落點」是形式合規，章別語意落點零約束力

**位置**：`greybox/tests/run-design-governance.mjs:81-91`。

**契約實作**：

```js
const concatenated = currentTexts.map((entry) => entry.body).join("\n");   // 八份 CURRENT 全文串接
…
const uncovered = active.filter((id) => !concatenated.includes(id));
if (uncovered.length) fail(`active ADR 未被 CURRENT 規格引用：…`);
else pass(`${active.length} 筆 active／partially-superseded ADR 均有 CURRENT 規格落點`);
```

判準是**單一子字串是否出現在八份文件串接後的全文任一處**。它不問出現在哪一份、不問是否在對應章別、不問是否有語意。

**實測落點分佈**（我用與測試相同的 active 判定邏輯重算）：

| 項目 | 數量 |
|---|---|
| active／partially-superseded ADR | **40** |
| 出現在 `跨章runtime與治理規格_v1.0.md` 的 | **40（全部）** |
| **只**出現在該份跨章規格的 | **19** |
| 有兩份以上落點的 | 21（刪任一份都不會轉紅） |
| 完全無落點的 | 0 |

也就是說：**那一份跨章規格單獨就讓全部 40 筆通過**，其餘七份 CURRENT 的引用在契約上完全多餘。而該份文件裡的形式是索引表：

```
| GB-ADR-001～GB-ADR-008 | 第一章灰盒、資料鏡像、證據與辯論的初始基線 |
| GB-ADR-014～GB-ADR-023 | 行動裝置、系列入口、第二章流程、美術與修復路由 |
```

**反向控制（任務書 B 第 2 組）**：我從 `03_規格/發現之前_第四章功能規格書_v0.2.md` 移除 `GB-ADR-040` 的落點（該處原文本身也只是一行列舉：`**現行裁決**：GB-ADR-030、GB-ADR-032、…、GB-ADR-040、…`）。

結果：**治理測試全綠、exit 0**，且照樣印出「40 筆 active／partially-superseded ADR 均有 CURRENT 規格落點」。

**為什麼重要**：這條契約的宣稱是「每筆現行決策都在現行規格裡有落點」，實際保證的只是「編號字串在某處出現過」。日後任何人把某章規格裡的 ADR 依據整段刪掉、或把章別語意換成純列舉，測試都會放行，而治理紀錄會寫成「40 筆均有落點」。**任務書 §八 已明示「若第 2 組不紅，請直接判治理契約缺口；不要因現行內容恰好正確就放過」——照此判 B。**

**最小修法**：把覆蓋檢查從「全文串接」改為「章別歸屬 + 語意鄰近」兩段。

```js
// 1) 每筆 active ADR 必須在 registry 指定的「歸屬 CURRENT 文件」中出現，而非任一份
//    需要在 decisions.md 的 ADR 區段或 current-specs.json 增設 scope 欄位（ch1..ch5 / shared）
const owner = adrScope[id];                        // 例：GB-ADR-040 → ch4
if (!byPath[owner].body.includes(id)) fail(…);

// 2) 該落點不得只是列舉：同一行不得同時出現 3 個以上 ADR 編號
const line = lineContaining(byPath[owner].body, id);
if ((line.match(/GB-ADR-\d{3}/g) || []).length >= 3)
  fail(`${id} 在 ${owner} 只有列舉式落點，缺語意說明`);
```

**可失敗的驗證條件**（兩項都要成立才算修好）：

1. 從 `第四章功能規格書` 移除 `GB-ADR-040`，測試**必須**轉紅（現況不會）。
2. 把某章規格裡 `GB-ADR-040` 的語意段落換成一行三個以上編號的列舉，測試**必須**轉紅。
3. 修好後基線必須仍全綠——**注意：依現況內容，第 2 項條件套上去會立刻紅**，因為第四章那處落點本身就是列舉。所以這條 B 同時包含「文件要補語意段落」，不只是改測試。

## 四、C-1｜`active` 的判定方式使 partially-superseded 與 active 無法區分

**位置**：同檔 `83-88`。

```js
if (!/^\*\*狀態\*\*：superseded\b/m.test(section)) active.push(row.id);
```

只要狀態不是字面 `superseded` 就算 active，所以 `partially-superseded` 被歸入同一池。契約名稱寫「40 筆 active／partially-superseded」已誠實揭露這點，所以不是誤導；但後果是 **B5 要求的「被取代的部分不能藉 CURRENT 重新生效」無法由這條契約分辨**——partially-superseded 的 ADR 只要編號出現就算覆蓋，不會檢查「僅未被取代的部分被引用」。

**最小修法**：把 `partially-superseded` 拆成獨立集合，並要求其 CURRENT 落點必須同時出現 `supersededBy` 指向的接手 ADR 編號。**可失敗的驗證條件**：把某 partially-superseded ADR 的落點改成不提接手者，必須轉紅。
