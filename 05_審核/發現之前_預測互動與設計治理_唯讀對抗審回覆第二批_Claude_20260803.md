## 二、B-1｜「形狀不得退回設定查表」沒有任何契約擋得住，而唯一能區分的結果是玩家可押的選項

**位置**：`greybox/src/engine4.js:520-540`（`canonicalOrbitShape`／`orbitShapeFromSimulation`）、`542-546`（`orbitShapeForRun`）。

**變異**：把

```js
return run && run.classificationSource === "simulated-path-v1"
  ? orbitShapeFromSimulation(seal.target, sim)
  : canonicalOrbitShape(seal.target, seal.speed, seal.strength);
```

改成永遠 `return canonicalOrbitShape(...)`。**結果 149/0，完全不轉紅。**

**我先排除了「空變異」的可能**，逐項實算兩函式的值域：

| 函式 | earth-center 九種組態的輸出 |
|---|---|
| `canonicalOrbitShape` | `circle`、`ellipse`、`away` —— **僅此三種** |
| `orbitShapeFromSimulation` | 同上，外加 **`crash`**（`sim.minRadius < 0.28`） |

`ORBIT_SHAPES` 宣告六種（`line`／`away`／`circle`／`ellipse`／`crash`／`wrong-center`）。逐一比對後，**canonical 永遠無法產生 `crash`**——那正是兩者唯一的語意差。

**而 `crash` 是玩家可押的選項，不是內部狀態**：

```js
// chapter-ui.js:6631
["ellipse", shapeLabels.ellipse], ["crash", shapeLabels.crash]
// chapter-ui.js:6609
ellipse: "閉合橢圓", crash: "切入地球"
// chapter-ui.js:5978
crash: "它切得太深，撞進地球。"
```

**測試對 `crash` 的覆蓋是 0**：`tests/run-node.mjs` 中 `"crash"` 出現 **0 次**（對照：`circle` 14 次、`line` 5 次、`away` 2 次、`ellipse` 1 次）。

**玩家實際會看到的後果**：玩家可以押「切入地球」。若分類器退回查表（或那條 `classificationSource` 三元式在未來被改壞），實際撞進地球的路徑會被命名成 `circle`／`ellipse`／`away`——**押對的玩家會被判成押錯，而「它切得太深，撞進地球」這句話永遠不會出現**。這正面違反 A4「形狀名稱不得退回設定查表」與 A3「玩家要知道自己押的是撞回、逃走或繞住」。

**最小修法**：補一條契約，用實際會 crash 的模擬結果斷言分類器行為，而不只斷言字串存在。

```js
// 正向：simulation 分類器必須能產出 crash
if (Engine4._orbitShapeFromSimulation("earth-center", { minRadius: 0.1, maxRadius: 1.0 }) !== "crash")
  throw new Error("K1 形狀分類器無法辨識切入地球的路徑");
// 負向：canonical 表不得被當成新 run 的分類來源
const canonShapes = new Set(allEarthCenterConfigs.map(canonicalOrbitShape));
if (canonShapes.has("crash"))
  throw new Error("canonical 查表意外可產生 crash，兩層分類已混用");
// 行為：走一條會 crash 的完整 run，斷言 run.actualShape === "crash"
```

**可失敗的驗證條件**：把 `orbitShapeForRun` 改成永遠用 canonical，**必須**轉紅（現況不會）。另需確認至少有一組合法 (speed, strength) 真能走出 crash；**若走不出來，那 `crash` 押注選項本身就是不可能達成的選項，那是另一條問題**——我沒有實跑完整 run 確認可達性，見 §五。

## 三、B-2｜舊 `predictPlanet`（封存即揭曉）仍可經 narrative 派送，契約只擋 chapter-ui 的 planets 切片

**位置**：`greybox/src/engine4.js:1379-1406`（`predictPlanet`）、`src/narrative.js:1157`（派送）、契約在 `tests/run-node.mjs:7795-7798`。

**現行契約寫得對**——正負兩向都有：

```js
if (!planetsUi.includes('doOrbit("sealPlanetPrediction"') ||
    !planetsUi.includes('doOrbit("revealPlanetPredictions"') ||
    planetsUi.includes('doOrbit("predictPlanet"'))          // ← 負向：不得含舊入口
  throw new Error("行星桌沒有先封兩張粗估紙再一起揭露，或仍走看一張算一張的舊入口");
```

**但它只掃 `chapter-ui.js` 的 `planets` 切片。** 而 `narrative.js:1157` 仍在派送：

```js
else if (action === "predictPlanet" && Engine.predictPlanet) r = Engine.predictPlanet(state.lab, args.id);
```

`predictPlanet` 本體在**同一次呼叫內**封存又揭曉——`sealedAt = tick(s)` 之後緊接 `row.openedAt = tick(s)`、`s.planetLab.revealed[id] = true`，而且 row 直接帶 `actual` 與 `residualPct`。

**變異**：我在 `scenes4.json` 任一 active `line` 節點加上

```json
"effects": [{ "labAction": { "action": "predictPlanet", "args": { "id": "mars" } } }]
```

**結果 149/0，完全不轉紅。**

**玩家實際會看到的後果**：目前 `scenes4.json` 對 `predictPlanet` 命中 0，所以現在無害。風險是任何人（或任何自動生成的節點）從資料層掛上這個 action，就能繞過雙封閘門、一顆一顆看答案，而 A5「兩張都封存後才一起揭曉」的契約完全不會響。**這與我在第四章、第三章連續抓到的是同一類**：契約只守 UI 呼叫端的字面，沒有守 action 派送面。

**最小修法**（二選一，建議第一個）：

1. 在引擎層退役——`predictPlanet` 直接 `return err(state0, "use-seal-and-reveal")`，或從 `api` 移除並讓 `narrative.js` 的分支消失。舊存檔相容由 `sanitize` 處理，不需要保留可呼叫的舊寫入路徑。
2. 契約擴大到 action 派送面：斷言 `narrative.js` 不得派送 `predictPlanet`，且 `scenes*.json` 任一 `labAction.action` 不得為 `predictPlanet`。

**可失敗的驗證條件**：在任一 `scenes4` active 節點掛上 `labAction: predictPlanet`，測試**必須**轉紅（現況不會）。

## 四、C-1｜K3 雙封閘門轉紅靠的是 TypeError，不是具名契約

**位置**：`greybox/src/engine4.js:1437-1444`（`revealPlanetPredictions`）。

拔掉 `two-planet-predictions-required` 守衛後，測試確實轉紅，但訊息是

```
Cannot read properties of undefined (reading 'revealedAfterSeal')
```

——那是程式崩潰，不是契約說「雙封閘門不見了」。後果：下一位審查者看到這條紅燈會去 debug undefined，而不是知道「先押後揭的紀律被拆掉」。而且崩潰是路徑巧合，若日後 `revealPlanetPredictions` 加了防禦性檢查，這條紅燈就會消失而閘門仍然沒有契約。

**最小修法**：加一條具名斷言——只封一顆就呼叫 `revealPlanetPredictions`，必須回 `two-planet-predictions-required`。**驗證條件**：拔掉守衛後，紅燈訊息必須指名雙封閘門，而非 TypeError。
