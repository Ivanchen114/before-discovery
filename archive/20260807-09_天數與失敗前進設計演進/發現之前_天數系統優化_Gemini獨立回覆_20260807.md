# 發現之前_天數系統優化_Gemini獨立回覆_20260807

## 十題獨立審查回覆

### 1. 科學性
**本提案「條件連續性，不以日差直接判可比性」是否正確？有沒有章節反例？**
**判斷：正確。**
**Runtime 引用：** 在第一章 `src/engine.js` 的 `checkSelection` 中，決定實驗能否被選取比較的判準是 `diffDims`（檢查球、槽面、傾角、計時是否受控），完全沒有檢查 `state.days` 或實驗之間的日差。在第三章 `src/engine3.js` 比較兩張紙（`dossierDualTransformData`）時，比對的是 `beat` 與 `t` 的殘差，也並未以日差做為阻擋比較的硬性條件。科學上，條件連續性（是否維持相同器材與操作環境）才是可比性的核心，以單純天數判定可比性是錯誤的。

### 2. 玩家取捨
**第三章「同船立即續做」對「借船多一天換船型範圍與獨立見證」是否真的兩邊都合理，還是存在明顯最佳解？**
**判斷：兩者皆合理，不存在絕對最佳解。**
**Runtime 引用：** 根據 `src/engine3.js` 137-152 行 `DOSSIER_VESSELS` 的定義，`captain` 船（同船）的 `borrowDays` 為 0，而 `small` 與 `large` 船的 `borrowDays` 為 1，且其 `rowingCrew`（見證人）與 `hardAcceleration` 均不同。若玩家選擇同船，可以最快速度（0 額外天數）完成同條件的複驗，取得最高精度的重複數據；若玩家選擇借船，雖然多了 1 天成本，但能獲得不同的獨立見證人（例如「六名貨船水手」）並證明定律在不同船型（加速度不同）下皆成立。兩條路徑產出的實質物理意義不同，且在遊戲中都有其對應的敘事與邏輯價值。

### 3. 證據邊界
**借船後的紙應支持哪一類有限主張？哪些紙絕對不能直接合併？**
**判斷：支持跨條件普遍性主張；不能直接合併為同條件複驗。**
**Runtime/邏輯引用：** 借船後產生的原紙（其 `vesselId` 會變為 `small` 或 `large`），可用來支持「慣性/共同運動定律不因船隻大小或加速度而異」的廣泛主張。然而，這些紙絕對不能與原船（`captain`）的紙直接合併作為「同條件複驗」的證據，因為 `src/engine3.js` 中明確定義了不同船隻的 `hardAcceleration` 不同（0.70, 0.57, 0.50），其運動學參數（`mastX`, `stoneX`）的基準也隨之改變。合併這兩張紙宣稱「在相同條件下測量精確一致」將會是科學上的偽證。

### 4. 敘事自然度
**研究時間帳會不會像管理介面或行政表格？如何讓它仍是故事中的紙、簽名或人物回應？**
**判斷：若處理不當會有行政表格感，需包裝於敘事載體中。**
**設計建議：** 不應將其設計為右上角的 UI 統計面板。應對應各章的敘事物件：如第一章可做為「伽利略的私人實驗手記」上的隨筆日期；第三章可作為「航海日誌」或「港務局借船登記表」；第六章則是「工坊輪班與交接日誌」（如 `src/engine6.js` 中的 `timeLedger` 概念）。這樣時間的流逝便自然成為劇中人物簽署與回應的一部分，而非冷冰冰的系統數值。

### 5. 跨章一致性
**第四章隱藏天數、改顯示校樣窗口，是誠實分工還是破壞跨章 HUD 一致？**
**判斷：是誠實分工，不會破壞深層一致性。**
**Runtime 引用：** 在 `src/engine4.js` 中，雖然有 `s.days += 1` 的遞增，但推動第四章核心壓力與故事進展的是出版的「校樣窗口」（Proof window）。強迫各章 HUD 在表層上統一顯示「天數」，反而掩蓋了各章玩家實際面臨的真實限制。跨章一致性應建立在「時間都會轉化為某種機會成本或證據」，而非強求 UI 變數名稱的統一。顯示校樣窗口才是對玩家最誠實的設計。

### 6. 第一章物理
**報告提出的新提示能否正確區分脈搏抖動與水鐘系統偏差？請直接用引擎跑兩趟／三趟驗證，不接受手寫簡化模型。**
**判斷：能正確區分。**
**實測驗證：** 直接呼叫 `greybox/src/engine.js` 的 `initialState` 與 `runExperiment` 執行：
*   **脈搏（銅大/打磨/中）：** 三趟測數值分別為 `[20.3, 37.5, 80.0, 87.5, 143.0]`、`[16.3, 57.0, 56.0, 106.8, 107.3]`、`[13.0, 24.0, 91.3, 91.0, 141.5]`。可見數值跳動極大，屬於隨機抖動（Jitter）。
*   **水鐘（銅大/打磨/中）：** 三趟測數值分別為 `[15.4, 42.3, 70.3, 98.7, 126.2]`、`[15.4, 41.5, 70.5, 97.3, 125.7]`、`[15.5, 42.4, 70.6, 97.6, 126.5]`。數值極度穩定，但與理論基礎值 `[14, 42, 70, 98, 126]` 相比，第一格有穩定的系統偏差（多出 1.4~1.5）。
引擎實測證明，水鐘的系統偏差不會因多次重做而消除，而脈搏的巨大隨機抖動可以透過多次測量看出趨勢。「有些抖動能靠多做幾趟看清；固定偏差不會因為重複就消失」的提示完全符合 Runtime 事實。

### 7. 資料真相
**P1 章末時間帳是否能從六章現有紀錄可靠推導？哪些章必須先補事件帳，不能只靠現行 `days`？**
**判斷：不能完全可靠推導，第四、六章必須補事件帳。**
**Runtime 引用：** 在第一、三章，時間花費較易從 `runs` 或 `records` 陣列的長度與 `config` / `vesselId` 回推。但在 `src/engine4.js` 與 `src/engine6.js` 中，存在許多如 `state.days += 1` 的裸加操作（例如純劇情推進或無明確產出原紙的檢視動作），這導致總 `days` 與實質產出的證據/行動無法完美對齊。若要實作時間帳，必須先將這些裸加動作替換為結構化的事件帳（Event Ledger），否則無法避免「未分類研究日」甚至產生倒推矛盾。

### 8. 舊存檔
**第三章試點最小遷移面是什麼？`legacyBaseline` 是否足夠，會不會產生雙真相？**
**判斷：`legacyBaseline` 是必須且足夠的，能避免雙真相。**
**架構建議：** 最小遷移面是：載入舊存檔時，將既有的 `days` 數值封存為不可變的 `legacyBaseline` 記錄（標記為「早期未分類研究時間」）。之後的所有新時間增加，只透過全新的 `timeLedger` 事件推進。總天數 `deriveDays` 應動態計算為 `legacyBaseline + sum(timeLedger.dayCost)`。如此一來，舊存檔的時數得以保留，且不會同時存在 `days` 整數欄位與 `timeLedger` 陣列兩個可以各自修改的 Truth Source，避免了雙真相的問題。

### 9. 系列結尾
**六章天數分章並列、不顯示精確總和，是否比立即建立 `seriesDays` 更穩？若主張可以總計，請先提出統一單位與防偽方式。**
**判斷：分章並列更穩，強行總和沒有意義。**
**邏輯引用：** 如提案所述，各章的「一天」代表的物理與敘事意義差異巨大。第一章的一天是推一次斜面，第六章的一天是一整個輪班的熱力學觀測。將它們相加成為 `seriesDays` 就像把蘋果與橘子相加。在尚未統一天數換算單位（且敘事上也不需要強行換算）前，分章並列（例如：「你在斜面旁花了 X 天，在船上借了 Y 天的船」）能最自然地總結玩家的足跡，同時免去複雜的跨章防偽檢驗。

### 10. Go／No-Go
**上述六項真人試玩門檻是否足以阻止錯誤機制擴散？還缺哪一條可觀察指標？**
**判斷：基本足夠，但缺乏對「產出物品質變化」的觀察指標。**
**補充指標：** 應增加一條：「**玩家多花時間取得的證據，是否真的在最終報告/對話中形成了結構性不同的論述？**」如果玩家多花了天數借船、獲得了獨立見證，但在最終過關對話中，他們只是把該原紙當作過關的勾勾，而無法（或遊戲系統不支援）利用它去反駁特定質疑，那這多花的時間在遊戲機制上依然是空洞的。必須確認玩家能感受到「多花的時間化為了更強的武器」。
