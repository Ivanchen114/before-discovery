# 第一章 branch map v0.3｜Sol 快速可施工性複核

**日期**：2026-08-08  
**審查者**：GPT-5.6 Sol（ADR-015：runtime、狀態、存檔與成本邊界）  
**範圍**：唯讀核對第一章 incline 工作台、場景流、資料尺度與既有對話演出掛點；未修改 runtime。  
**結論**：**A 級 0、B 級 3、C 級 1；CHANGES REQUIRED，但方向通過。** v0.2 的 fixture 與史實兩個阻擋已完整解除，「現行第五段數值押錯→世界留下後果→玩家修正」可以成為 A2-2 的 F2 岔口。以下三項會直接改變台詞所描寫的動作與場景位置，應先修成 v0.3.1，再寫完整劇本；都是文件級修正，不需要新增 engine、schema 或 flag。

## B-1｜六拍誤用了歸一化數字，也倒置了現行實驗時序

- 現行工作台顯示並要求玩家輸入的是原始刻度；fixture 基準例如緩坡為 `12／36／60／84／108`，UI 也直接把 `run.readings.slice(0, 4)` 放進表格。`1／3／5／7／9` 是離開 embed 後，`A2-2/qOdd` 才由玩家整理出的比例。因此 v0.3 §3 的「前四段 1、3、5、7」「押 7／11／13」不能寫進工作台六拍。
- `runExperiment()` 執行時已一次產生五段讀值並存入 run；畫面只遮住第五段。玩家之後選 1–3 筆既有 run、輸入預測，`judge()` 才揭露所選 run 的第五段平均值。故「押值→第一次放球→球停在／越過記號」不符合現行時序；若堅持這場活球演出，就不再是 engine 零變更。
- **零 engine 修法**：把六拍改成「選 1–3 張原紙→依畫面上的原始前四段押第五段原始增量→在被遮住的第五欄覆一張可移除的預測透明紙／蠟紙→先讓押線看起來像合理延伸→翻開封存的第五欄→押線與實測刻痕錯開→玩家重押」。錯法不要硬寫數字，寫成「照抄第四段原值／只延伸最後一次差額／任意押值」。UI 可由既有 `claim.prediction`、`claim.observedFifth` 與 `claim.runIds` 畫出押線和實測線。
- 工作台現已有 `sayIntoDialogue()`／`sayWorkbenchCorrection()`，能在 embed 內依序播放人物台詞並等待玩家收隊。因此這 6–10 拍應標為**工作台對話／演出稿**，不是 `scenes.json` 節點；狀態仍由既有 claim 留存。

## B-2｜A3-1 在大講堂，讀回物必須可攜且由既有 claim 保證

- `A2-2` 是工作室，`A3-1` 明定為「帕多瓦大學大講堂」。辛普里奧不能在講堂「掃視工作室」並指向仍留在「斜面邊」的錯線。
- 讀回條件只由既有 `consistent && !predHit` claim 派生；它能保證押值紙與實測值存在，不能保證舊存檔玩家曾看過新 UI 的裝置錯線。若台詞只認 claim，仍可維持零新 flag 與舊存檔相容。
- **修法**：預測痕跡定為可帶去講堂的押記紙／透明覆紙，不選接球盤或裝置本體作唯一載體。A3-1 改成辛普里奧以書脊壓住講台上的那張押記紙，例如語意為「押錯的也帶來了？貴工作室的紙，比人誠實。」確切文句由 Fable 打磨。

## B-3｜選擇盤點把 `qOdd` 誤算成岔口，實際 F2 發生在 `e1/judge`

- v0.3 表格把 `A2-2/qOdd` 標為 F1→F2，但新方案明確養的是 embed 內自由輸入的第五段預測。修復後才匯回 `qOdd`；`qOdd` 自身仍是「錯項一拍糾正重選」的 F1。
- **修法**：表格第 13 項保留 `qOdd=F1`；另在工作台盤點補一列 `A2-2/e1｜judge：consistent && !predHit｜F1→F2`。全文「斜面錯讀存活」統一改稱「第五段押值失手存活」，避免日後施工錯接到 scenes choice。
